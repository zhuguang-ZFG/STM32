# 完善 spec 规范补全计划

## 目标与授权

把 `.trellis/spec/` 的补全工作整理为有仓库证据、明确边界、可逐批验收的计划，供后续会话直接执行。

用户于 2026-11-05 确认「可以，创建任务并完善计划」，随后要求继续。规划文档完成并审阅后，用户于同日要求「执行 spec 计划」；任务已 `start` 并完成 B1–B6 规范实施，结果见 [research/validation.md](research/validation.md)。未执行的检查与该轮的规划边界仍在验证报告中分列。

## 已确认背景

现有规范按四层组织，真实维护面还包括书籍、公共取证、RTOS 与 GD32；完整覆盖情况见 [research/spec-audit.md](research/spec-audit.md)。审计登记 S01–S10 十项补全工作及 F01/F02 两个实现疑点，优先完善可执行接口、产物验证与入口路由。具体方案和顺序分别由 [design.md](design.md) 与 [implement.md](implement.md) 维护。

## 需求

- R1 覆盖真实维护面：站点与内容、书籍生产、STM32/ESP32/GD32、C 与工具链取证、RTOS、共用协议与记录器、视频生产与发布边界。
- R2 每个缺口提供现有规范、实现或测试证据，区分完全缺失、入口不可达、陈旧描述和已有覆盖。
- R3 以当前源码、测试和 CI 为核对依据；保留历史任务的验收记录，不把历史数值改写成当前事实。
- R4 每项补全写明目标文件、优先级、依赖、验收断言和适用命令，明确执行环境及命令副作用。
- R5 跨层或命令接口契约采用可执行合同深度：适用场景、签名、数据/环境约束、错误矩阵、正常与边界及失败案例、测试断言、错误与正确做法。
- R6 现有稳定规范只补缺口和入口；各项事实设唯一维护位置，其他层以链接引用。
- R7 区分本轮计划验证、后续规范验收与产品行为回归，未执行的命令不得记为通过。

## 约束与非目标

- 本轮只修改当前任务的规划、研究和元数据，不修改产品代码、正文、图片、视频产物、现有规范与 CI。
- 不自动提交、推送、部署、平台发布、烧录硬件或重渲已发布视频。
- 保留现有工作区修改，尤其 `11-02-skill-remaster` 的 `specs.md`、交付图片及 PPT；它们只作历史参考。
- 工具缺失、检查跳过、宿主模型或静态反汇编均不能等同于硬件实测通过。
- 只描述仓库已有行为；发现产品实现或 CI 缺陷时登记候选问题，不借补规范扩大为修功能。
