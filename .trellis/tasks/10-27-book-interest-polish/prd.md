# 书籍趣味性提升：增强叙事、互动与记忆点

## Goal

在不降低技术密度、不改写事实与代码契约的前提下，让《通往单片机之路》更愿意让人继续读下去：抽象概念有悬念，长章有节奏，实验有即时反馈，结论有能复述的记忆钩子。

本任务与 `10-26-prose-polish` 分工明确：既有任务负责去 AI 口癖和句子精修；本任务负责章节级阅读体验，包括开场张力、故障叙事、互动挑战、阶段反馈与收束回扣。

## Requirements

### R1 工程侦探式叙事

- 优先采用“异常现象 → 常见误判 → 证据采集 → 真正原因 → 可迁移结论”的结构。
- 故事必须来自章内可复现事实、仓库事故记录或明确标注的思想实验；不得虚构板上实测、人物经历或厂商行为。
- 保留作者已有的直给短句、反问和工程口语，不把全书改成文学散文。

### R2 互动与即时反馈

- 每个改造章至少新增或强化一个可在 5–10 分钟内完成的互动：预测输出、二选一判断、最小复现、找错、读寄存器/反汇编或观察现象。
- 互动必须紧邻答案或证据，不让读者跨越大段正文才能得到反馈。
- 不要求额外购买硬件；无板章节优先使用宿主机、编译器、静态文件或思想实验。

### R3 记忆点与回扣

- 每章选一个主比喻或主问题贯穿开头、正文转折和结尾，不堆叠多个互相竞争的比喻。
- 章末“记忆锚点/你做到了/下一站”须回扣开场问题，形成闭环，而不是只罗列知识点。
- 口诀必须能解释边界，禁止为了押韵牺牲准确性。

### R4 技术契约不退化

- 代码围栏、行内代码、表格数据、寄存器地址、位号、版本号、单位数值、手册章节号和链接目标不得因趣味化而漂移。
- 未经上板验证的内容继续明确标注“待上板实测”，不得把推演写成实测。
- 不修改既有 H1/H2/H3 文本；避免破坏页内锚点和交叉引用。新增小节须使用新且稳定的锚点。

### R5 先试点再扩展

- 首批选 6 个不同类型的长章：`c/02-pointer.md`、`build/07-build-system.md`、`stm32/10-dac.md`、`rtos/freertos/03-scheduler.md`、`esp32/02-gpio-matrix.md`、`gd32/01-rcu-clock.md`。
- 试点通过后，按“抽象基础 / 构建工具 / 外设 / RTOS / ESP32 / GD32 / 综合项目”分批扩展；单批不超过 10 章。
- 已经具备强事故叙事的章节只做缺口补齐，不机械套模板。

## Acceptance Criteria

- [ ] 6 个试点章均形成“开场问题—证据推进—结尾回扣”的完整闭环。
- [ ] 每个试点章至少有 1 个 5–10 分钟互动，且答案或可观察证据紧邻出现。
- [ ] 每章只保留 1 条主叙事线；新增趣味段落能服务技术结论，删除后会损失理解或记忆，而非纯装饰。
- [ ] 试点前后报告列出：开场钩子、互动点、主比喻、回扣位置及新增字数；单章净增正文原则上不超过 12%。
- [ ] `prose_guard.py` 的事实 token/受保护区检查通过；代码、表格、链接目标和标题无非预期变化。
- [ ] `npm run docs:build`、书稿相关测试与印前检查通过；页内锚点和站内链接零新增错误。
- [ ] 用户抽评 2 个试点章，确认“更有趣但不油腻、不幼稚、不稀释技术密度”后，才扩展到全书批次。

## Constraints

- 不与在途的印前工艺、题图、逐章去 AI 味和 AI 新部任务争抢同一职责。
- 不新增无法维护的角色世界观、连续剧情或拟人化吉祥物。
- 不用 emoji 数量、段子数量或字数增长冒充趣味性。
- 当前工作树包含大量在途改动；落盘前逐文件确认基线，禁止覆盖其他任务的修改。

## Non-goals

- 不重写技术结论，不重排全书章节，不改变书名与视觉体系。
- 不为所有章节强行加入同一种“事故故事”模板。
- 不在本任务内制作大批新插图；若文字试点证明某处必须配图，再单独列出需求。
