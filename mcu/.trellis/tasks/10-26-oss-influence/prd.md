# PRD：从开源项目与社区摄取影响，补充整书项目层

## 背景

书稿已有 47 个与章节一一对应的可编译工程（`code/`，CI 全量验证，附录 B 登记门禁），
但**与开源世界脱节**：读者学完看不到"真实项目长什么样、该读哪段源码、按什么许可用"。
用户要求：从 GitHub 开源项目与开源社区摄取影响，在**整个项目层面**补充。

## 目标（分层交付，按此顺序）

### P1 附录 B 增补「开源项目地图」（无需硬件，先落地）

- 六类：RTOS / 文件系统 / 网络与协议栈 / 图形与驱动框架 / 工具链与调试 / 测试与质量
- 每类 5–8 个**真实存在**的项目，逐条给：仓库地址、许可证（必须核实）、维护活跃度（最近提交/发布）、
  "该读哪一段代码"、与本书章节的映射
- 验收：每条链接可用、license 核实（不猜）；构建器契约不破（附录为独立单元，不受 projects.json 门禁约束）

### P2 现有 47 工程「上游对照」（无需硬件）

- 每个工程加 1–3 行：在某个 OSS 实现里的对应位置（如 `heap_4.c` 的合并逻辑 ↔ 我们的 probe 断言）
- 验收：`code/projects.json` 与附录 B 索引保持一一对应；不改任何工程源码；对照行的事实可核（文件/函数名真实存在）

### P3 新增实战项目章（需要工程 + CI）

- 候选（每章一个可编译工程）：迷你抢占式调度器、日志式文件系统（仿 littlefs）、轻量显示驱动（仿 LVGL 子集）
- 验收：新工程登记 `code/projects.json` + 附录 B + CI 类型校验；章节走既有 12 门 + 题图 + guard 契约

### P4 工程方法论对齐社区

- 抽样社区实践（提交规范、版本钉死、许可边界、可复现构建、CI 矩阵），出「我们已有 / 我们缺」清单并落地
- 验收：清单条目逐条给证据（指向本项目文件或社区文档），落地项有验证

## 约束

- **所有开源项目信息必须核实**：仓库存在、license 准确、链接可用；不许凭记忆编造
- 引用边界：只做"导读与映射"，不复制 OSS 代码进书（许可风险）；正文引用代码位置用文件+符号名
- 不改动现有 47 个工程的源码与 `projects.json` 结构（除非 P3 新增条目）
- 构建契约：附录单元改动需过 `build_html.py` 审计与 12 门；新增章节需过 prose_guard/text_audit/art_guard

## 非目标

- 不做开源项目的 fork/二次分发
- 不为每个 OSS 项目写长篇分析（导读定位，非源码解析）
