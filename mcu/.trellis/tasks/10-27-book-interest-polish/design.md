# 设计：书籍趣味性提升

## 1. 阅读体验模型

每个目标章按五个槽位检查，但不要求五段机械排布：

1. **钩子**：一个具体异常、反直觉问题或预测题。
2. **下注**：让读者先选答案或写下判断。
3. **取证**：用代码、寄存器、反汇编、日志或图示推进。
4. **翻案**：指出常见直觉为什么错，给出边界。
5. **回扣**：章末回到开场，说明读者现在能解释什么。

这一模型只控制信息节奏，不替代现有章节骨架。现有“本章精髓、先修、先跑起来、小节结构、记忆锚点、短自测、你做到了”继续保留。

## 2. 内容改造类型

| 章节类型 | 推荐趣味机制 | 避免 |
|---|---|---|
| C/ABI/构建 | 预测编译结果、反汇编侦探、最小翻车样例 | 空泛生活比喻 |
| 外设 | 症状工单、寄存器排查顺序、波形/日志预判 | 把待实测写成已实测 |
| RTOS | 时间线推理、调度竞猜、竞态复盘 | 把并发问题拟人成闹剧而丢失时序 |
| ESP32/GD32 | 平台差异陷阱、迁移失败案例、能力边界竞猜 | 用 STM32 经验强套结论 |
| 综合项目 | 约束冲突、故障树、设计取舍 | 只讲成功路径 |

## 3. 改动边界

- 尽量修改散文段落和现有钩子/quick win/记忆锚点/自测，不动受保护技术区。
- 标题文本冻结；需要新结构时新增三级小节，并检查锚点唯一性。
- 真实事故需能指向仓库文件、测试或既有任务记录；无法取证时改写为“假设场景/思想实验”。
- 单章正文净增设 12% 软上限，防止趣味化把书拖长；超过时必须通过删减重复说明抵消。

## 4. 试点选择

- `c/02-pointer.md`：抽象概念，验证“预测 + 内存现场”是否有效。
- `build/07-build-system.md`：工具链说明章，验证“构建事故工单”是否能改善节奏。
- `stm32/10-dac.md`：外设章，验证“症状 → 寄存器 → 波形预期”。
- `rtos/freertos/03-scheduler.md`：并发章，验证“时间线竞猜”。
- `esp32/02-gpio-matrix.md`：平台特性章，验证“路由误判与能力边界”。
- `gd32/01-rcu-clock.md`：迁移/对照章，验证“熟悉经验害人”的翻案结构。

## 5. 守卫与评审

每章改前保存结构摘要和关键 token；改后运行既有 `prose_guard.py` 与链接/构建检查。人工评审不只看“好不好笑”，而看三件事：是否更想继续读、是否更容易预测/解释、是否仍像工程书而非段子集。

试点报告采用统一表格：文件、开场钩子、互动、主叙事、回扣、净增字数、守卫结果、风险备注。

## 6. 回滚

改动按章独立，任何章抽评失败即可只撤回该章。若用户认为整体风格过度，则保留互动和证据顺序，撤回修辞性叙事；技术守卫不随风格决策放宽。
