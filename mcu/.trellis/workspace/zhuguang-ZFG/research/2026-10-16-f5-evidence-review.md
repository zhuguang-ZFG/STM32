## 2. 本轮新量到的一件事：本probe 唯一那处配置偏离，不移动任何一个数

`code/rtos/05-sem-mutex/FreeRTOSConfig.h:64` 把 `configUSE_TIMERS` 设成 0，而 lab 的 `code/rtos/01-freertos-lab/FreeRTOSConfig.h:44` 是 1。这是屏上所有偏移/字节数与"那块板子的固件"之间唯一的口径差。V11.1.0 的 `TCB_t`（`kernel/tasks.c:358-436`）里没有任何 `configUSE_TIMERS` 门控的成员，`Queue_t` 也没有——但这句话不该由我说，所以直接按 lab 的配置重编了同一件仪器：

```sh
cd code/rtos/05-sem-mutex
mkdir -p build/labcfg && cp ../01-freertos-lab/FreeRTOSConfig.h build/labcfg/
arm-none-eabi-gcc -O0 -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard -std=c11 \
  -Ibuild/labcfg -I<kernel> -I<kernel>/include -I<kernel>/portable/GCC/ARM_CM4F \
  -ffunction-sections -fdata-sections -c sizes_probe.c -o build/labcfg/s.o
arm-none-eabi-nm --print-size build/labcfg/s.o | grep -E 'probe_sizeof|probe_off_(T_|ucQueue|pcHead|u_)'
```

结果与 `build/sizes/s.o` 逐项相同：`sizeof(Queue_t)=0x50`、`sizeof(TCB_t)=0x58`、`uxPriority` 偏移 44、`uxBasePriority` 72、`uxMutexesHeld` 76、`ucQueueType` 76。**屏上那张偏移表在 lab 的真实配置下也成立**，第 4 项"80 字节"与板子固件之间没有口径差。

这条当天就从"我手工跑过一次"变成了脚本里的断言（`probe.sh:348-387`，第 4 步最后一道）：`build/labcfg/` 里按 lab 那份 `FreeRTOSConfig.h` 重编同一件仪器，再把 **32 项** sizeof/偏移逐个与默认档比相等，一处不差就打印 `[中]`，差一项就把差在哪一项连同两边的数一起打出来并置 `FAIL=1`。

其中一句是这条对照的命门，所以单独钉死：**先证明那份配置真的被吃进去了**。`sizes_probe.c:69-72` 新增 `probe_configUSE_TIMERS`，默认档量到 0、lab 档量到 1（`probe.sh:355-356` 两条 `eq`）——没有这两条，下面 32 项相等完全可能只是两个档都编了同一份配置的假象（`#include "FreeRTOSConfig.h"` 的搜索顺序本来就可能让 `-I.` 那份赢）。

负例也做了：把 lab 的 `configUSE_TIMERS` 临时改成 0 再跑整份取证，`[失] lab 档量到的 configUSE_TIMERS：实测 0，期望 1`、脚本 exit 1；改回来重跑 exit 0。注意负例只打掉了那一条"吃进去没有"的断言，32 项相等照旧通过——这正说明后者量的是内核的形状、不受那颗旋钮影响。

### R3 / 中（同日已改）：那句"中断里不能拿互斥锁"挂错了凭据，而且不止一处

`publish.zhihu.intro` 里原本写：

> 判（tasks.c:6589 两问，holder 为 NULL 就不继承——这就是「中断里不能拿互斥锁」的技术含义）

`tasks.c:6589` 那条 `if( pxMutexHolder != NULL )` 说的是**没有持有者就没有可继承的对象**，它不是"ISR 不能拿互斥锁"的理由。ISR 那条路对得上的证据在别处：`semphr.h:675` 把 `xSemaphoreTakeFromISR` 展成 `xQueueReceiveFromISR`，而 `queue.c:2035` 起的这个函数从头到尾不写 `xMutexHolder`、不比较 `uxQueueType`、不调 `xTaskPriorityInherit`（本轮 grep 过，命中 0 处）。**也就是说：中断里"拿"成功了也不会建立所有权，因而永远没有回落。**
