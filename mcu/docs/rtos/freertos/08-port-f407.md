# F8 移植 FreeRTOS 到霸天虎：从裸机工程到多任务

> 🎯 前面七章的机制，这一章全部落地：在我们的寄存器工程上，让 FreeRTOS 跑起来。移植的本质是**三个异常函数的改名接管**：SVC 启动第一任务、PendSV 切换、SysTick 报时，其余全是体力活。

## 本章精髓

1. 移植 = 拿对 port 层 + 改三处异常向量：`ARM_CM4F` 的 `port.c`/`portmacro.h` 拿来即用；FreeRTOS 用 `vPortSVCHandler`/`xPortPendSVHandler`/`xPortSysTickHandler` 三个名字，与我们启动文件的 SVC/PendSV/SysTick 向量对上即可（改向量表或 `#define` 映射两法）。
2. 中断优先级两组配置别踩：`configKERNEL_INTERRUPT_PRIORITY`（内核相关：PendSV/SysTick 必须最低）与 `configMAX_SYSCALL_INTERRUPT_PRIORITY`（能调 API 的中断上限），数值越大优先级越低，搞反全系统灵异。
3. heap 与栈是两套预算：heap 供任务栈/TCB/队列，与裸机 main 栈（链接脚本 `_Min_Stack_Size`）是两笔账，RTOS 化的 RAM 总账要重算。

- **能理解**：`nm` 出来的 `SVC_Handler` / `PendSV_Handler` / `SysTick_Handler` 三个符号，它们的**地址落在 `port.o` 里**：内核函数只是被 `#define` 换了名字。
- **能用**：拿到任意 Cortex-M4 工程，按"port 层 + 三个向量 + 两份优先级 + 一笔 heap"清单一遍过，`make` 出可跑镜像。

## 一、port 层怎么选：先对型号，再对 FPU

FreeRTOS 的移植代码全在 `portable/` 下按"编译器 × 架构"分目录。本工程用的是：

```text
portable/GCC/ARM_CM4F/port.c
portable/GCC/ARM_CM4F/portmacro.h
```

**为什么是 `ARM_CM4F` 而不是 `ARM_CM4`**：最后的 `F` 表示 **FPU**（Floating Point Unit）。Cortex-M4F 带单精度硬件浮点，任务切换时必须**额外保存浮点寄存器**，所以端口代码不同。

这正好呼应 [C6 硬浮点 ABI](../../c/06-abi-stack.md) 讲的：`-mfpu=fpv4-sp-d16 -mfloat-abi=hard` 下 `double` 走 `d0/d1`。**端口选择错了（拿了不带 F 的 `ARM_CM4`），编译器照过、运行起来浮点寄存器被踩。**

本工程的 `Makefile` 里三项参数必须一致：

```makefile
MCU      := -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard
INC      := -I. -I$(FREERTOS_KERNEL)/include \
            -I$(FREERTOS_KERNEL)/portable/GCC/ARM_CM4F
```

也正因为 `-mfloat-abi=hard`，端口才是 CM4F 版本。**MCU 参数与端口目录是一对绑定关系**，改一个必须改另一个。

## 二、三异常接管：移植的全部核心

先把"三个异常改名"画出来：SVC 起死回生、PendSV 换魂、SysTick 报时。

![FreeRTOS 三异常接管动画](/anim/freertos-port.svg)

内核的三个关键动作各挂在一个 Cortex-M 异常上：

| 内核函数（`port.c` 行号） | 挂在哪个异常 | 干什么 |
|---|---|---|
| `vPortSVCHandler`（260 行） | SVC（异常号 11） | 启动第一个任务：手工恢复它的现场，从此不再返回 |
| `xPortPendSVHandler`（505 行） | PendSV（异常号 14） | 上下文切换：保存当前任务、恢复下一个任务 |
| `xPortSysTickHandler`（562 行） | SysTick（异常号 15） | 系统节拍：递增 tick、必要时挂起 PendSV 请求切换 |

`port.c:138-140` 处就是这三个函数的声明，其中两个带 `naked` 属性，和 [S16 的 `HardFault_Handler`](../../stm32/16-debug-hardfault.md) 同理：**现场必须手工管理，不能让编译器插桩**。

但**名字对不上**：我们的启动文件里向量表写的是 CMSIS 标准名：

```asm
  .word SVC_Handler        ; startup_stm32f407xx.s:108
  .word PendSV_Handler     ; :111
  .word SysTick_Handler    ; :112
```

于是有**两种接法**：

**（A）改向量表**：把启动文件里的名字改成 `vPortSVCHandler` 等。侵入启动文件，将来换内核版本要再改。

**（B）`#define` 映射**：本工程用的就是这个，写在 `FreeRTOSConfig.h:74-77`：

```c
#define vPortSVCHandler     SVC_Handler
#define xPortPendSVHandler  PendSV_Handler
#define xPortSysTickHandler SysTick_Handler
```

**（B）的好处**：启动文件保持标准 CMSIS 命名，内核函数在编译期被预处理改名，两边都不用为对方妥协。

### 实测：三个向量真的落在 port.o 里

光看 `#define` 不够，得证明**链接结果**确实如此。`nm` 一下产物：

```text
08003180 T SVC_Handler
080032b0 T PendSV_Handler
08003318 T SysTick_Handler
```

三个符号都是 `T`（在 `.text` 里、已定义），它们**不是**启动文件里的 `IRQ_DEFAULT` 弱符号，而是被内核实现**顶替**了。地址间距也印证了上面的分工：`PendSV` 到 `SysTick` 相距 `0x68` 字节。

> 顺带看两个参照符号：`main` 在 `0x080010c4`，`prvIdleTask` 在 `0x08002080`（小写 `t` = 内核内部的 local 符号），`pxCurrentTCB` 在 `0x20000a7c`（`B` = `.bss`），**TCB 指针在 RAM 里**，正是 F2 讲的"换魂"要读的那个变量。

## 三、两份优先级：数值越大优先级越低

这是 Cortex-M 的经典迷惑点（[S4](../../stm32/04-nvic-exti.md) 已建立概念），FreeRTOS 把它浓缩成两个宏。

FreeRTOS 使用**全部 4 位**作抢占优先级（`configPRIO_BITS = 4`）：**0 = 最高，255 = 最低**。

`FreeRTOSConfig.h:60-63` 的真值：

```c
#define configKERNEL_INTERRUPT_PRIORITY         255  /* 最低（4 位域全 1） */
#define configMAX_SYSCALL_INTERRUPT_PRIORITY    (5 << (8 - configPRIO_BITS))  /* 0x50 */
#define configMAX_API_CALL_INTERRUPT_PRIORITY   configMAX_SYSCALL_INTERRUPT_PRIORITY
```

**（1）`configKERNEL_INTERRUPT_PRIORITY = 255`：内核中断必须最低。**

PendSV 和 SysTick 在**每个**任务切换点都要跑。如果它们优先级偏高，会打断用户的临界区；更要命的是，**低优先级的临界区保护就失效了**：FreeRTOS 进临界区靠 `BASEPRI` 屏蔽，而 `BASEPRI` 只能屏蔽"不高于某阈值"的中断。数值 255 意味着它挡不住任何用户中断，这正是设计意图：内核让路给所有应用中断。

**（2）`configMAX_SYSCALL_INTERRUPT_PRIORITY = 0x50`：能调 API 的中断上限。**

`5 << (8 - 4)` = `5 << 4` = `0x50` = 80。含义：**优先级数值 ≥ 80 的中断才允许调用 `...FromISR()` API**；数值 < 80（即更紧急）的中断**不许**碰任何 FreeRTOS API，因为它不受内核临界区保护。

`(8 - configPRIO_BITS)` 这个移位是把 4 位逻辑优先级"抬"到 8 位硬件寄存器的**高 4 位**：与 [S4](../../stm32/04-nvic-exti.md) 讲过的 `IP 字节 = 逻辑优先级 << 4` 是同一件事（NVIC 寄存器只有高 4 位有效）。

**搞反会怎样**：把 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 配成比 `configKERNEL_INTERRUPT_PRIORITY` 还"高"（数值更小），内核临界区就盖不住能调 API 的中断，队列/信号量内部链表被并发改写，症状是**随机死机**，且极难复现。这就是原文里"搞反全系统灵异"的机制。

## 四、配置逐项：`FreeRTOSConfig.h` 的真值

本工程配置（`code/rtos/01-freertos-lab/FreeRTOSConfig.h`）逐条读，每个数字都是正文结论的基准：

| 行 | 宏 | 真值 | 说明 |
|---|---|---|---|
| 16 | `configCPU_CLOCK_HZ` | `16000000UL` | **本工程跑 HSI 16MHz，不启 PLL** |
| 17 | `configTICK_RATE_HZ` | `1000UL` | 1ms 一个节拍（= [S5](../../stm32/05-systick.md) 的 SysTick 1ms） |
| 18 | `configPRIO_BITS` | `4` | F407 的 NVIC 实现 4 个优先级位 |
| 21 | `configUSE_PREEMPTION` | `1` | 抢占式调度开 |
| 23 | `configMAX_PRIORITIES` | `5` | 优先级 0..4，**数字越大越高** |
| 27 | `configMINIMAL_STACK_SIZE` | `128` | **单位是字**（= 512 字节） |
| 31 | `configCHECK_FOR_STACK_OVERFLOW` | `2` | 栈溢出检查开满（F7 会用） |
| 34/35 | 动态/静态分配 | `1` / `0` | 只用动态分配 |
| 36 | `configTOTAL_HEAP_SIZE` | `(16 * 1024)` | heap_4 的池子 = 16KB |
| 41 | `configTASK_NOTIFICATION_ARRAY_ENTRIES` | `1` | 每任务 1 个通知槽（F6 讲"容量一"） |
| 42 | `configUSE_16_BIT_TICKS` | `0` | `TickType_t` 是 32 位 |
| 45 | `configTIMER_TASK_PRIORITY` | `configMAX_PRIORITIES - 1` = `4` | 定时器守护任务跑最高 |
| 53 | `configUSE_TRACE_FACILITY` | `1` | `vTaskList` 等可用（场景 1 用到） |

**两个容易读错的点**：

- `configCPU_CLOCK_HZ` 是 **16MHz**，不是 F407 的标称 168MHz：本工程故意跑内部 HSI，省掉时钟树配置的干扰。**拿 168MHz 去套这个工程的节拍计算会错 10 倍。**
- `configUSE_16_BIT_TICKS = 0` 决定了事件组**可用位数**：32 位 `TickType_t` 扣掉 8 个控制位 = **24 位**（配置第 49-50 行专门注释了这条口径）。

**还有一组容易踩的宏**（配置 67-72 行）：V11 内核默认把 `INCLUDE_*` 系列**全关**。从老版本升级后 `vTaskDelay` 链接不上，多半不是代码坏了，而是 `INCLUDE_vTaskDelay` 默认是 0，用哪个开哪个。

## 五、RAM 两套账：heap 池子 vs 裸机主栈

`size` 的实测三段（quick win 的输出改写成表）：

```text
   text	   data	    bss	    dec	    hex	filename
  43156	   2168	  19208	  64532	   fc14	freertos-lab.elf
```

- `text 43156`：代码 + 只读常量。FreeRTOS 内核的调度器、队列、定时器全在这里。
- `data 2168`：已初始化的可读写数据（要从 Flash 拷到 RAM）。
- `bss 19208`：零初始化数据，**16KB 的 heap 池子就躺在这儿**（`configTOTAL_HEAP_SIZE` = 16384 字节）。

**关键认识：`bss` 里的 heap 池子，不等于"FreeRTOS 额外占用了 19KB"。** 裸机程序也有 `.bss`（全局 buffer、栈）。真正的对照是**两套栈预算**：

| | 裸机工程 | RTOS 工程 |
|---|---|---|
| 主栈 | 链接脚本里的 `_Min_Stack_Size`（启动后 SP 指向它） | 只给**中断和启动阶段**用（MSP） |
| 任务栈 | 不存在 | 每个任务从 **heap 池子**里切一块 |
| 谁在记账 | 链接脚本一处 | `configTOTAL_HEAP_SIZE` + 每个任务的栈深 |

所以 RTOS 化的 RAM 账要**重算**：`heap 池子 = 所有任务栈 + 所有 TCB + 所有队列/信号量/定时器`，池子用尽时 `xTaskCreate` 会**返回失败**（`pdFAIL`），而不是像裸机那样栈溢出。

> 栈深单位陷阱再强调一次：`configMINIMAL_STACK_SIZE = 128` 是**128 字 = 512 字节**。这里填 128 字节的话，栈只有 32 字，随便一个 `printf` 就踩穿了。F7 有完整的审计方法。

## 常见坑

- **选错 port 目录**：Cortex-M4F 用了 `ARM_CM4`（不带 F），浮点寄存器不在切换时保存，任务间浮点值互相踩。判据是 `-mfloat-abi=hard` 必须配 `ARM_CM4F`。
- **两份优先级配反**：`configMAX_SYSCALL_INTERRUPT_PRIORITY` 数值大于 `configKERNEL_INTERRUPT_PRIORITY` 才是对的（0x50 < 255）。配反 → 内核临界区盖不住能调 API 的中断 → 随机死机。
- **`configCPU_CLOCK_HZ` 填 168MHz**：本工程跑 HSI 16MHz（`FreeRTOSConfig.h:16`），填错会让节拍时长差 10 倍。
- **栈深单位当字节**：`configMINIMAL_STACK_SIZE = 128` 是 128 **字** = 512 字节。填成 128 字节 = 32 字，立刻踩穿。
- **`INCLUDE_*` 默认是 0**：V11 里这些 API 默认全关（配置 67-72 行）。`vTaskDelay` 链接不上先查这里，别怀疑代码。
- **忘了取内核源码**：Makefile 默认从 `.trellis/ref/freertos-v11/kernel` 找（该目录被 gitignore，不进仓库），新克隆的仓库必须先跑第六节第 1 步。

**2. `configMAX_SYSCALL_INTERRUPT_PRIORITY = (5 << (8 - 4))` 是多少？为什么这么算？**

<details>
<summary>看答案</summary>

`5 << 4` = **0x50 = 80**。左移 `(8 - configPRIO_BITS)` 是把 4 位逻辑优先级抬到 8 位硬件寄存器的**高 4 位**：NVIC 的 IP 寄存器只有高 4 位有效，与 S4 讲的 `IP 字节 = 逻辑优先级 << 4` 是同一件事。含义：优先级数值 ≥ 80 的中断才允许调用 `...FromISR()` API。

</details>

**3. `nm` 出来 `SVC_Handler` 是 `T` 而不是 `W`，说明了什么？**

<details>
<summary>看答案</summary>

`T` = 该符号在本目标的 `.text` 段里已定义，来自 `port.o`。启动文件里原本的 `IRQ_DEFAULT SVC_Handler` 是 `W`（弱符号），链接时被 `port.c` 的强定义**顶替**了。这证明 `FreeRTOSConfig.h` 的 `#define` 映射确实生效，三个异常已经被内核接管。

</details>

**4. RTOS 化之后，`configTOTAL_HEAP_SIZE` 和裸机的 `_Min_Stack_Size` 是什么关系？**

<details>
<summary>看答案</summary>

**没有关系，这是两套独立预算。** `_Min_Stack_Size` 是链接脚本给**主栈（MSP）**留的空间，RTOS 下只给中断和启动阶段用；`configTOTAL_HEAP_SIZE` 是 heap_4 的池子，所有**任务栈 + TCB + 队列/信号量/定时器**都从这里切。池子用尽时 `xTaskCreate` 返回失败，而不是栈溢出。

</details>

**5. 为什么本工程 `configCPU_CLOCK_HZ` 是 16MHz 而不是 168MHz？**

<details>
<summary>看答案</summary>

因为它跑 **HSI 16MHz、不启 PLL**（`FreeRTOSConfig.h:16` 注释写明）。这样做把"时钟树配置"这个变量从移植实验中剔除，节拍计算只依赖一个确定的常量。**拿 168MHz 去算这个工程的 tick 会差 10 倍。**

</details>
