# F0 为什么需要 RTOS：先失败一次

> 🎯 学 RTOS 最好的方法不是先背概念，而是**亲手写一个注定失败的多任务裸机程序**：看着它怎么死，你就懂了 RTOS 为什么生。

## 本章精髓

1. 超级循环的原罪：所有任务共享一个时间轴，任何任务多花一毫秒，其他任务全部晚点；任务越多，"互相拖累"越无解。
2. 时间片轮询的幻觉：用标志位 + 定时器分片，看似"同时"，实则任一任务阻塞（死等延时/等 IO）就全线瘫痪。
3. RTOS 的本质承诺：**每个任务仿佛独占 CPU**：实现这个幻觉只需要三样东西：每任务一个栈、一个 TCB 记账本、一个会保存/恢复现场的切换机制（F1–F2 拆解）。

- **能理解**：为什么"把 `delay` 改成状态机"只是把问题从**等待**挪到了**优先级**：状态机不解决"紧急任务被排在小任务后面"，连调换代码行顺序都救不回来（第三节实测：一件 2 ms 的活摆第一行与摆最后一行，五局最坏迟到的中位是 1.49 ms vs 1.60 ms，两边的区间互相包住，胜负都判不出来）。
- **能用**：拿到需求先算一笔"最坏执行时间 vs 周期"的账，够用就裸机、不够才上 RTOS，不再凭感觉选型。

## 先跑起来（10 分钟 quick win）

在你的 `00-blink` 工程里，把主循环改成三个任务轮着跑：

```c
for (;;) {
    led_tick();      /* 1Hz 闪烁：数到 500 翻转一次 */
    key_scan();      /* 按键：按下翻转另一颗灯 */
    uart_echo();     /* 串口：收到完整一行才返回 ← 元凶在这里 */
}
```

烧录之前先押个死活：按住键盘不停发字符，LED 还闪得下去吗？押完再按住不放，让板子宣判。

`uart_echo()` 按"**收满一行才返回**"的阻塞写法实现（死等 `RXNE`）。然后按住键盘不放——**LED 立刻卡壳**。

这不是比喻：`uart_echo` 在等你松手，`led_tick` 根本没机会被调用。用秒表或逻辑分析仪量一下"按键期间的 LED 周期抖动"，把毫秒数记进实验记录，这就是本章的论据。

手上没板子也能拿到同一笔账：本章每个数字都出自 `code/rtos/00-why-rtos/`，一条命令跑完。

```console
$ cd code/rtos/00-why-rtos && sh probe.sh
```

`superloop.c` 只有一份，宿主机（mingw gcc 16.1.0）编出来跑 6 秒量时间，交叉链（arm-none-eabi-gcc 15.2.1，`-DBOARD_ARM`）编出来只出反汇编数指令。两边看到的任务代码一字不差，所以宿主机上量到的"谁等谁"结构，就是芯片上的结构。

宿主机不是真板：Windows 会随时抢走十几毫秒，单局的"最坏迟到"能差一个数量级。所以 `probe.sh` 默认**每档连跑 5 局、只报跨局中位数**（`REPS=3 sh probe.sh` 改局数，`REPS=1` 退回单局）。交叉侧的指令条数与反汇编是逐位稳定的，想复现就多跑几次；宿主机侧的时间，只有中位数值得写进结论。

真正的修复不在这一章：F1 会把"三个任务各有自己的栈"这件事造出来，让 LED 在串口忙时照闪不误。

## 一、超级循环解剖：三个人挤一条传送带

先看这张图：一根轴上的三个任务，和三条轨道上的三个世界。

![裸机超级循环 vs RTOS 平行世界动画](/anim/why-rtos.svg)

先把"多任务"翻译成裸机的样子。三个任务，三种完全不同的时间需求：

| 任务 | 周期要求 | 单次最坏执行时间（实测） | 晚了会怎样 |
|---|---|---|---|
| `led_tick` | 500ms（1Hz 闪烁 = 每 500ms 翻一次） | 20 条指令（16 MHz 下 1.3 µs 量级） | 灯闪得慢一点，肉眼几乎看不出 |
| `key_scan` | 每次都查（≤20ms 一次才不丢按键） | 14 条指令 | 按键漏检 |
| `uart_echo` | 有数据就办，无硬周期 | **不定**（实测最长单圈 3.299 s，5 局中位） | 回显变慢、按键整条丢掉 |

前两个数字是 `arm-none-eabi-gcc -O2` 反汇编里数出来的行（`probe.sh` 第 3 步，逐位稳定），第三个是宿主机 6 秒一局、连跑 5 局取中位的读数（`probe.sh` 第 1 步），**同一个 `uart_echo`，指令只有 7 条，时间却是无限的**。

超级循环把它们串成一条线：

```c
for (;;) {
    led_tick();
    key_scan();
    uart_echo();
}
```

**关键在第三列与第一列的对比**：前两个任务的单次开销是微秒级，第三个是"不定"：**只要有一个任务的最坏执行时间不可界定，整条循环的周期就不可界定**。这是超级循环的原罪，与代码写得多漂亮无关。

## 二、阻塞的传染性：一根轴上加不进新东西

`uart_echo` 的阻塞写法（教科书式、也最容易写出来）：

```c
void uart_echo(void)
{
    char c = uart_getc();      /* 死等 RXNE */
    if (c == '\n') {
        uart_puts(line);
        line_len = 0;
    } else {
        line[line_len++] = c;
    }
}
```

`uart_getc()` 内部是 `while (!(USART2->SR & USART_SR_RXNE)) { }`。**在收到下一个字节之前，这个循环不会返回，`led_tick` 与 `key_scan` 都不会被调用。**

- 你按住键盘不放 → 不再有新字节进来 → 卡在 `uart_getc` 里 → LED 停摆。
- 就算你正常打字，两个字符之间的间隙也足以让 LED 的相位漂移。

`-O2` 之后这个死等连函数都不剩，整个 `while` 被内联进任务体尾部（`probe.sh` 第 3 步，Cortex-M4 真寄存器版）：

```asm
000000b4 <uart_echo>:
  b4:  mov.w  r2, #1073758208      @ 0x40004000  USART2 基址
  b8:  ldr.w  r3, [r2, #1024]      @ 0x400       SR
  bc:  lsls   r3, r3, #26          @ RXNE(bit5) 挪到符号位
  be:  bpl.n  b8 <uart_echo+0x4>   ← 字节不来，就永远在这四条里转
  c0:  ldr.w  r0, [r2, #1028]      @ 0x404       DR
  c4:  uxtb   r0, r0
  c6:  b.n    0 <consume>
```

7 条指令，一扇出口，钥匙在对方手里。这 7 条与 `led_tick` 的 20 条挂在同一根轴上，账却完全不对称。

看看代价。宿主机 gcc 16.1.0，6 秒一局、**每档连跑 5 局**，两种模式的**事件脚本一字不改**（600–875 ms 送来 `hello world!`、900 ms 一个换行；4200–5175 ms 送来 40 个 `A`、5498 ms 换行；三次按键分别是 702–717 ms 的 15 ms 短按、1000–4300 ms 的 3.3 s 长按、5499–5514 ms 的短按）。统计量取跨局中位，逐键明细取自末局，日志里 min / 中位 / max 一并给出：

| 观测量 | 阻塞版 `uart_echo` | 改良版 `uart_poll` |
|---|---|---|
| 超级循环圈数 | 55（五局全同） | 30 682 621（中位） |
| 单圈 µs：min / max | 24 998 / **3 298 958** | 0.10 / 3 472 |
| LED 翻转次数（该翻 12 次） | 中位 **5**（4–5） | 中位 12（11–12） |
| 最长的一次翻灯间隔 | **3600.00 ms** | 501.47 ms |
| 15 ms 短按（落在字节流里） | **五局全丢** | 迟到 0.00 ms |
| 3.3 s 长按（这期间一个字节都没有） | 迟到 **3200 ms** | 迟到 0.00 ms |
| 短按（落在回显发送里） | 迟到 2.47 ms | 迟到 2.47 ms |
| 串口收 / 发字节 | 54 / 52 | 54 / 52 |

最后一行两栏完全相同：**阻塞版一个字节都没丢**。它没搞坏数据，它偷的是别人的时间：该翻 12 次的灯中位只翻了 5 次，15 ms 的短按五局局局凭空消失，一次长按晚了 3.2 秒才被看见。

而 3.2 秒既不是随机数、也不是宿主机噪声：五局里最长单圈全是 **3298.96 ms**（min = 中位 = max），最坏迟到钉在同一个数，丢键的局 **5/5**。这一局里长按的迟到是 **3200.00 ms**，短按那 15 ms 干脆整条没被采到。**响应上界 = 一整圈**。改良版那两栏同样自洽：最坏迟到中位 2.47 ms（min = 中位 = max），对照最长单圈中位 3.47 ms，那 3.47 ms 正是 40 个字符回显必须占用的线上时间（115200 8N1 → 86.805 µs/字符 × 40 = 3.472 ms），谁也变不走。

顺带一条诚实注脚：圈数这一栏两档的**稳定性**也完全不同：阻塞版五局都是 55 圈（被事件脚本钉死），改良版五局从 29 174 989 到 31 287 271 圈。宿主机上"一圈多快"会随负载漂，"阻塞那一圈有多长"却纹丝不动，因为它的钥匙在对方手里。

**这就是"共享一根时间轴"的具体后果**：任务之间不是"先后关系"，而是"连坐关系"：任何一个任务的时间不确定，所有人的时间都不确定。

## 三、时间片改良的极限：把大任务切碎

自然的想法是：把 `uart_echo` 改成**非阻塞状态机**，每次只处理一点点：

```c
void uart_poll(void)            /* 每次进来只查一眼，立刻返回 */
{
    if (!(USART2->SR & USART_SR_RXNE)) return;
    char c = (char)(USART2->DR & 0xFF);
    ...
}
```

循环变成三个人都"很快返回"：

```c
for (;;) {
    led_tick();
    key_scan();
    uart_poll();     /* 再也不阻塞 */
}
```

这确实解决了**等待**。但它没解决两件事：

1. **谁先跑**。`key_scan` 和 `led_tick` 之间没有任何优先级概念，只是按书写顺序执行。流行的说法是"你可以靠**调换代码行顺序**来调优先级，把急的活摆到第一行"。这条直觉经不起一次实测：往循环里加一件 2 ms 的活（`host_burn_us(2000)`，顶替一段跑不掉的批量采样），只把它从第一行挪到最后一行，跑同一张事件表、每档连跑 5 局：

   | | 2 ms 的活摆第一行 | 同样的活摆最后一行 |
   |---|---|---|
   | 最长单圈 5 局：min / 中位 / max | 5.47 / **5.49** / 8.13 ms | 5.47 / **5.47** / 5.48 ms |
   | 三次按键的迟到（末局） | 1.85 / 1.27 / 0.37 ms | 0.25 / 1.39 / 0.17 ms |
   | **最坏迟到** 5 局：min / 中位 / max | 0.71 / **1.49** / 1.85 ms | 0.41 / **1.60** / **5.24** ms |
   | LED 迟到翻灯（>550 ms） | 0 次（0 / 5 局） | 0 次（0 / 5 局） |
   | 丢键的局 | 0 / 5 | 0 / 5 |

   中位差 0.11 ms，而摆最后一行的五局区间（0.41–5.24 ms）把摆第一行的（0.71–1.85 ms）整个包住，统计上根本分不出胜负，摆最后一行的最大值 5.24 ms 反而是摆第一行最大值 1.85 ms 的 2.8 倍。**换行序换不来优先级，连"哪种摆法更差"都决定不了**：你只是改了自己在一圈里的站位，而上界由那一圈多长决定（≈5.5 ms），跟站位无关。需求里写的"必须 200 µs 内响应"要的是上界，行序只动得了平均值。
2. **不可预知的抖动**。每次循环的总耗时随分支变化，每个任务的实际启动时刻都在漂移。想量化"最坏情况"就得对**所有分支组合**做最坏分析：任务一多，组合爆炸。上面那 5.47 ms 的最长单圈就是实例：它不是 2 ms 加三个任务的和，而是"2 ms 撞上 3.47 ms 回显"那一个特定组合同时发生（5.47 ≈ 2.00 + 3.47，两个数各自都能对上独立测算）。

还可以再进一步：用 [S5](../../stm32/05-systick.md) 的 SysTick 做"时间片"，给每个任务发标志位：

```c
void SysTick_Handler(void) { tick++; }

for (;;) {
    if (tick % 1 == 0) led_tick();
    if (tick % 2 == 0) key_scan();
    uart_poll();
}
```

**但这仍然救不了阻塞**：如果某个"任务"内部又出现了一次死等，整个时间片调度一起陪葬。而且 `%` 取模、条件判断本身也在消耗时间，改良方案越叠越复杂，可预测性反而更差。

> 结论：裸机侧的所有"改良"都在**同一根时间轴上腾挪**。要真正的并行，需要让每个任务拥有**自己的执行上下文**：这就是 RTOS 要卖给你的东西。

## 四、RTOS 三件传家宝：一个幻觉的三个零件

"每个任务仿佛独占 CPU" 是一个**幻觉**，它由三个零件构成。这不是比喻，本仓库 `code/rtos/01-freertos-lab/` 里就能逐个指出来：

**1. 私栈（平行世界的地基）**：每个任务有自己独立的栈，所以一个任务"卡住"时，它的调用栈、局部变量都留在自己的地盘上，不会污染别人。内核里这个字段是 `pxStack` / `pxEndOfStack`，见 `tasks.c:358` 起 `tskTaskControlBlock` 结构体定义（该结构体注释明确写着"旧命名惯例被保留，以免破坏内核感知调试器"）。

**2. TCB（户口本）**：任务的身份、状态、优先级、栈指针都记在 `tskTaskControlBlock` 里。其中**第一个成员**是：

```c
volatile StackType_t * pxTopOfStack;  /* THIS MUST BE THE FIRST MEMBER OF THE TCB STRUCT. */
```

`tasks.c` 里那句"必须是第一个成员"是**硬约束**：切换现场时汇编要靠固定偏移找到它（F2 展开）。同一结构体里还有 `xStateListItem`（挂在哪个状态链表：就绪 / 阻塞 / 挂起）、`uxPriority`（数字越大优先级越高）、`pxEndOfStack`。

**3. 切换机制（换魂术）**：`PendSV` 异常里保存当前任务的现场、恢复下一个任务的现场。现场从哪来？就是上面那个 `pxTopOfStack`。

**这三件东西的成本是实打实的 RAM**。看本仓库 lab 的真实配置（`code/rtos/01-freertos-lab/FreeRTOSConfig.h`）：

| 配置项 | 真值 | 行号 | 含义 |
|---|---|---|---|
| `configMINIMAL_STACK_SIZE` | `128` | 27 | **单位是字（4 字节）**，即 512 字节——这是"最小"任务的栈 |
| `configMAX_PRIORITIES` | `5` | 23 | 优先级 0..4，数字越大越高 |
| `configTICK_RATE_HZ` | `1000` | 17 | 1ms 一个节拍 |
| `configCPU_CLOCK_HZ` | `16000000` | 16 | 本工程跑 HSI 16MHz，不启 PLL |
| `configTOTAL_HEAP_SIZE` | `16 * 1024` | 36 | heap_4 的池子，任务栈/TCB/队列都从这里切 |

"单位是字不是字节"这条在 `FreeRTOS.h:162` 的错误提示里写得很直白：`configMINIMAL_STACK_SIZE defines the size (in words) of the stack allocated to the idle task`。**单位记错一次，栈就是 4 倍或 1/4**：这是新手上 RTOS 最常见的翻车点，F7 有完整的审计方法。

## 五、裸机够用清单：什么时候**不该**上 RTOS

RTOS 不是升级，是**换一种成本结构**。它买的是"结构清晰 + 响应有保证"，花的是 RAM（每任务一个栈 + TCB）与切换开销。**小系统上 RTOS 往往更差。**

先算一笔时间账。假设最坏执行时间 `WCET` 与周期 `T` 如下，裸机可行性判据是 `Σ WCET ≤ min(T)`：

| 场景 | 任务 A | 任务 B | 任务 C | 裸机够用？ |
|---|---|---|---|---|
| 纯点灯 | `led_tick` 20 条 / 500ms | — | — | ✅ 一个 `for` 循环足够 |
| 点灯 + 按键 | 20 条 / 500ms | `key_scan` 14 条 / 20ms | — | ✅ 实测一圈 <1 µs（直方图中位数落在 `<1 µs` 桶） |
| 点灯 + 按键 + 阻塞串口 | 20 条 / 500ms | 14 条 / 20ms | `uart_echo` 7 条，但**不定**（实测最长单圈 3.299 s，5 局中位） | ❌ 不可界定 |
| 点灯 + 按键 + 非阻塞串口 + 2 ms 采样 | 20 条 / 500ms | 14 条 / 20ms | 采样 2 ms / 一圈 | ⚠️ 上界 = 一圈 ≈ 5.5 ms，够用与否取决于那个 200 µs |
| 三路高速采样 + 通信 | 各 200µs / 1ms | — | — | ❌ 总占用接近周期，必须抢占式 |

**不该上 RTOS 的信号**：

- 任务都能在**一个固定周期**内轻松跑完，且没有"必须在 X 微秒内响应"的硬要求；
- Flash/RAM 已经吃紧（每任务栈按 512 字节起算，几个任务就是几 KB）；
- 只有"一件事"，只是这件事比较长，那需要的是**状态机**，不是日程表。

**该上 RTOS 的信号**：

- 有**硬实时**要求（响应时限与任务数量同时增长）；
- 任务之间**相互独立**、周期各不相同；
- 有"等待"但不想让等待拖垮别人（等信号量、等队列、等事件组）。

> 判据只有一条：**裸机管"顺序"，RTOS 管"期限"。** 需求里出现第二个"必须在……之内"，就该认真考虑 RTOS 了。

**延伸**：超级循环的局限在 SysTick 节拍（[S5](../../stm32/05-systick.md)）下暴露；RTOS 上下文切换依赖 PendSV（[S4](../../stm32/04-nvic-exti.md)）与调用约定（[C6](../../c/06-abi-stack.md)）。

## 实物实验

- 复现 quick win 的失败：三任务超级循环 + `uart_echo` 阻塞写法，按住键盘，观察 LED 停摆；用逻辑分析仪记录"按键期间 LED 周期抖动"的毫秒数，写进实验记录。
- 没板子就 `cd code/rtos/00-why-rtos && sh probe.sh`，四步一条命令跑完：阻塞 vs 非阻塞（第 1 步）、行序当假优先级的对照（第 2 步）、每个任务在 Cortex-M4 上是多少条指令（第 3 步）、死等那三行在 `-O0` / `-O2` 下的两种形状（第 4 步）。本章每一个数字都出自这里；宿主机那两步默认每档跑 5 局（`REPS=1 sh probe.sh` 退回单局，`REPS=8` 更稳），日志末尾直接打 min / 中位 / max。
- 把 `uart_echo` 改成非阻塞状态机（第三节的 `uart_poll`），再测一次抖动，**会发现抖动变小但没消失**（最长单圈从 3.3 s 降到 3.47 ms，回显那一圈的线上时间仍在），这就是"状态机不解决优先级"的实测证据。
- 进阶：`cd code/rtos/01-freertos-lab && mingw32-make DEMO_SCENE=1 -B`，看 F1 用 RTOS 写同一个需求的产物（产物在 `build/scene-1/`）。注意 `FreeRTOSConfig.h:16` 写的是 **16MHz HSI**，本工程不跑 PLL，别拿 Cortex-M4 的标称主频去套。

## 常见坑

- **把 delay 全改成"非阻塞状态机"就以为够了**：状态机解决等待，不解决优先级，紧急任务照样排队（第三节实测：最坏迟到 = 一整圈，2 ms 的活摆第一行与摆最后一行的五局中位是 1.49 ms 与 1.60 ms，两边的区间互相包住）。
- **把"调换代码行顺序"当优先级用**：行序只改平均启动时刻，不改上界；上界由最长单圈决定，而最长单圈往往由一件你没挪位置的活决定（那 3.47 ms 的回显）。
- **以为 RTOS 会让代码变快**：它买的是"结构清晰 + 响应保证"，成本是 RAM（每任务一栈）与切换开销；`configTOTAL_HEAP_SIZE` 就是这笔账（`FreeRTOSConfig.h:36`）。
- **一上来就十来个任务**：任务越少 RTOS 越优雅；能合并的周期性小任务先用软件定时器（F6）。
- **混淆栈深单位**：`configMINIMAL_STACK_SIZE` 的单位是**字**不是字节（`FreeRTOS.h:162` 明确写了 "in words"），128 是 512 字节。
- **拿宿主机单局的数当结论**：同一份代码、同一张事件表，宿主机上一局的"最坏迟到"能比另一局大一个数量级（Windows 随时抢走十几毫秒）。本章只引用跨局中位数；反过来，交叉链的指令条数与反汇编是逐位稳定的，那种数才是结构，跑一次就够。

## 短自测

**1. 超级循环里三任务都不阻塞，能保证响应时间吗？为什么？**

<details>
<summary>看答案</summary>

不能。不阻塞只保证"每个任务最终会被执行"，不保证**什么时候**执行。每个任务的启动时刻等于"前面所有任务本次耗时之和"，而这些耗时随分支变化，你只能保证一个上界，且任务越多这个上界越接近（甚至超过）最小周期。要**期限**保证就需要抢占式调度。

</details>

**2. 为什么"把 `uart_echo` 改成状态机"不能彻底解决问题？**

<details>
<summary>看答案</summary>

状态机消除的是**等待**，不是**优先级**。改完之后每个任务都很快返回，但它们仍然按书写顺序串行执行：`key_scan` 要等 `led_tick`，`led_tick` 要等 `uart_poll`。出现"必须 200µs 内响应按键"这类硬要求时，调换代码行顺序也没用：实测把一件 2 ms 的活从第一行挪到最后一行，五局最坏迟到的中位从 1.49 ms 变成 1.60 ms（区间分别是 0.71–1.85 与 0.41–5.24，后者把前者整个包住，统计上分不出胜负），而上界始终是"一整圈"（中位 5.47 ms）。要**期限**保证就需要抢占式调度。

</details>

**3. RTOS 的三件传家宝各解决什么问题？**

<details>
<summary>看答案</summary>

**私栈**：让每个任务有独立的调用栈与局部变量，一个任务卡住不污染别人（内核字段 `pxStack`/`pxEndOfStack`）；**TCB**：任务的"户口本"，记录状态/优先级/栈顶指针（`tskTaskControlBlock`，第一个成员必须是 `pxTopOfStack`）；**切换机制**：`PendSV` 里保存/恢复现场，让"幻觉"得以在物理上实现。

</details>

**4. `configMINIMAL_STACK_SIZE = 128` 是多少字节？**

<details>
<summary>看答案</summary>

**512 字节**（128 字 × 4 字节/字）。`FreeRTOS.h:162` 的错误提示写明 "defines the size (in words)"，单位是**字**。本条来自本仓库 `code/rtos/01-freertos-lab/FreeRTOSConfig.h:27` 的真实值。

</details>

**5. 什么信号说明"不该上 RTOS"？**

<details>
<summary>看答案</summary>

任务能在**一个固定周期**内轻松跑完、没有"必须在 X 微秒内响应"的硬要求、Flash/RAM 吃紧、或者"其实只有一件事只是比较长"（那需要状态机而非日程表）。判据：**裸机管顺序，RTOS 管期限。**

</details>

**6. 为什么"最长单圈 3.299 s"可以直接写进结论，"最坏迟到 2 ms 还是 5 ms"却要多跑几局取中位？**

<details>
<summary>看答案</summary>

因为两者的**来源**不同。3.299 s 是阻塞那一圈的时间，长度由事件脚本决定（40 个字符在 4200–5175 ms 间陆续到达，下一个字节 5498 ms 才来），五局的 min / 中位 / max 全等于同一个数，它是**结构**。而"最坏迟到"在改良版里取决于宿主此刻被 Windows 抢走了多少时间，同一档连跑五局能从 0.41 ms 到 5.24 ms，它是**负载**，只有统计量可信。同一件事在芯片上：交叉链反汇编出的 20 / 14 / 7 条指令逐位稳定，跑一次就够；真板上的迟到要跑一批看分布。

</details>
