# A3 工具流：让模型读手册、跑构建、看串口

> 🎯 前两章的模型是「手无寸铁」的：你粘手册它背手册，你粘错误它猜错误，你粘日志它读切片，每个来回你都是它与终端之间的人肉管道。这一章给它装上三件工具：读文件的手册、跑命令的终端、看日志的眼睛；协议底座是 MCP，权限闸门握在你手里。装上工具的模型还是不是假设机？是。变的不是可信等级，是闭环的位置：机器侧的内环它自己转，你守住手册与上板的外环。

## 本章精髓

1. **工具流省的不是复制粘贴，是信息的完整与新鲜**。你粘的是切片、是上一刻、是孤本；它自己取的是全量、是当下、自带行号与工程语境。同一条编译错误，切片喂法它陪你对着症状猜，全量喂法它自己顺着第一条错误挖到根因。差的不是步骤数，是闭环的位置，以及你在闭环里的角色。
2. **MCP 是插座标准，不是又一个工具**。开放协议（版本 2026-07-28，消息格式 JSON-RPC 2.0），Hosts/Clients/Servers 三方，host 为每个 server 建一个 client；server 向 client 暴露 Resources/Prompts/Tools 三类原语：手册文本是 Resource，三段式工单模板是 Prompt，跑构建是 Tool。协议 2025-12 起归 Linux Foundation 下设中立机构治理，学它不押注任何一家厂商。
3. **接入即授权，闸门要建在硬处**。MCP 规范把「工具代表任意代码执行」写进安全原则；Cursor 官方明说 Auto-review is not a security boundary；CLAUDE.md 被官方定性为 context, not enforced configuration。软约束管态度，硬门禁管放行：允许列表、hooks、构建门、对账三问，一层都别省。

- **能理解**：为什么「它自己跑构建」比「你把错误粘给它」信息量高一个量级；Host/Client/Server 三角色各坐在哪；三类原语与嵌入式素材的对应关系；三档运行模式各自把风险放在哪。
- **能用**：给手边的 agent 工位接上读文件与跑命令两类能力，跑通读手册、跑构建、看串口三个场景；给每个接入的工具过一张四问权限清单；把超长日志切成模型吃得下的证据片。

## 先跑起来（同一条错误，两种喂法，15 分钟）

准备工作两件：[B0](../build/00-toolchain.md) 的工具链装好，本书前面任选一个能构建通过的 STM32 裸寄存器工程（S3 的点灯工程即可）；再有一个能跑命令的 agent 工位（A0 工具地图三格任选一格）。

开跑之前先押个轮数：同一处构建错误，把 5 行粘给它，和让它自己捞全量输出，各自几轮修到绿？一边押一个数，两张表填完对答案。

实验 A（搬运工模式）：把工程里改错一行，比如 `RCC->AHB1ENR` 误写成 `RCC->APB1ENR`（A2 的总线归属雷）。自己跑一遍构建，把终端输出的最后 5 行复制下来，粘进一个不能跑命令的普通聊天窗，问：怎么修？

实验 B（工具流模式）：把同一处错误留着，换到 agent 工位，只发一句：

> 构建这个工程，把编译修到通过。只许动 main.c，改完自己重新构建验证后再交。

两轮都结束，填这张对照表：

| 对照项 | 实验 A | 实验 B |
|---|---|---|
| 它问你要信息的次数 | | |
| 修到编译通过用的轮数 | | |
| 它看到的错误输出（切片/全量） | | |
| 有没有顺手改别的东西 | | |

判读两条。其一，看第一轮判断差多远：搬运工模式它只能凭你粘的 5 行猜，而构建错误的根因通常在输出最前面的第一条，后面几十行全是连锁反应；工具流模式它自己捞全量输出，第一刀就砍在根因上。其二，数实验 B 里它跑了几次构建：这个「跑、读、改、再跑」的循环就是官方说的 auto-correct，你不用当管道，它自己转到绿。

如果实验 B 里它转了五轮还没绿、还开始乱改，别急着救场，先记下现场：这正是第六节权限闸门的预习材料，「只许动 main.c」这条约束有没有被遵守，是你评审的第一项。乱改的典型症状是开始动与错误无关的文件：那不是它在努力，是它在表演努力，评审时按越界改动记账。

实验做完把错误改回去，这个工程后面还要用。

实验报告按这个格式存档（进版本控制或实验笔记）：

| 字段 | 内容 |
|---|---|
| 日期与工位 | 哪天做的、用的哪个 agent 工具与版本 |
| 错误原文 | 改坏了哪一行，构建输出的第一条错误 |
| 实验 A 表现 | 问了你几次、第几轮方向才对 |
| 实验 B 表现 | 自己跑了几轮构建、有没有越界改动 |
| 结论 | 这次观察到的差距形态 |

这份报告与 [A0](00-pair-not-ghost.md) 的一致性实验档案是同一类资产：下次评估新工具、新模型时翻出来对照，你的判断就有了自己的数据底座，不用信任何评测文章。

## 一、把错误粘给它，与它自己跑，差在哪

先给两种协作方式起名字。**搬运工模式**：模型不动手，你当它与终端之间的管道，报错靠你复制，文件靠你粘贴，日志靠你截图转文字。**工具流模式**：模型自己有手，读文件、跑命令、看输出，你只下工单与终审。

[A0](00-pair-not-ghost.md) 的能/不能清单没有变：它依然不知道你的原理图，依然不能替你上板。变的是信息到达它手里的路径。搬运工模式里，这条路有三重损耗，每一重你都在日常里见过：

| 损耗 | 现场 | 后果 |
|---|---|---|
| 切片损耗 | 构建吐了 80 行错误，你复制了最后 10 行 | 第一条错误才是根因，后面全是连锁；它陪你对着症状开药 |
| 时效损耗 | 你粘的是五分钟前的输出，中间自己又改了两行 | 它基于过期现场推理，修一个可能已经不存在的问题 |
| 语境损耗 | 错误文本到了，出错的文件、行号、编译命令、工程结构没到 | 它只能猜环境，猜错方向你还得再粘一轮 |

工具流模式把三重损耗一次消掉：它自己跑构建，拿到全量输出，第一条错误在最前面；它自己读文件，行号与上下文自带；它改完自己再跑一遍验证，不用等你当下一次管道。

把切片损耗演一遍给你看。一次真实的构建，输出 80 行：第 3 行是 `main.c:42: 'RCC_AHB1ENR' undeclared`，后面 77 行全是这个未声明宏引发的连锁报错。你复制最后 10 行粘过去，模型看到的是一堆莫名其妙的类型错误，于是开始陪你猜：是不是头文件顺序错了，是不是编译选项少了。它猜得有理有据，全是症状的关联推理。而直接把全量输出给它（或者让它自己跑），它第一眼看到第 3 行：宏名打错了，补个头文件或改对名字，一刀收工。同一条错误，两种喂法，一个是会诊，一个是误诊。你当管道的每一分钟，都在为切片损耗付利息。

这不是本书的推演，是工具官方写好的工作机制。VS Code 的 agents 文档给这个机制起了名字（规范定义，访问日期 2026-10-27）：

> An agent uses a language model to reason about your request and tools to act on your development environment…This repeated reasoning, action, and validation is the **agent loop**.

推理、行动、验证，循环往复。2025-02-24 的 agent mode 预览公告把这个循环描述得更具体（能力描述）："It responds to compile and lint errors, monitors terminal and test output, and auto-corrects in a loop until the task is completed." 响应编译与 lint 错误、监视终端与测试输出、自动修正直到任务完成。Claude Code 官方仓库 README 的定位句同构（能力描述）："edits files, runs commands"。三份互不隶属的来源说的是同一件事：机器侧的内环，机器自己转。

回忆 [A0](00-pair-not-ghost.md) 的两环结构：内环是机器侧验证（编译、测试、lint），外环是你的终审（手册、原理图、上板）。搬运工模式里，内环的传动轴是你，每一圈都要亲手搬一次；工具流模式把内环整个还给机器，你的人肉管道退役，回到审计员的位置。这就是「差在哪」的完整答案：差的不是谁打字快，是闭环的位置，以及你在闭环里的角色。

两种模式摆一张总表：

| 维度 | 搬运工模式 | 工具流模式 |
|---|---|---|
| 信息到达 | 你复制的切片，上一刻的孤本 | 它自己取的全量，当下的现场 |
| 内环传动 | 人肉管道，一圈一搬 | 机器自闭环，auto-correct 转到绿 |
| 你的角色 | 管道工兼审计员 | 纯审计员 |
| 外环终审 | 手册、原理图、上板 | 手册、原理图、上板（不变） |
| 新增风险 | 无新能力，无新风险 | 接入即授权，闸门要建（第六节） |

盯住最后一行：工具流不是免费的午餐，它用「授权风险」换「信息完整」。这笔交易值不值，取决于第六节的三层防线你建没建。

顺带说清本章的排位逻辑：工具流排在 A1 与 A2 之后，是因为工单与对账是它的前置技能。没有三段式，你不知道给它下什么工单；没有对账三问，它自己跑出来的绿你会当成终审。先会验收，再发工具，顺序不能反。

不变的那一半也要看见。agent loop 里的「验证」仍然是机器侧验证：编译绿、测试绿、lint 绿，三个绿都不认识 RM0090，不认识共阳接法。它把 `RCC->AHB1ENR` 误写成 `RCC->APB1ENR`，编译照样全绿，灯照样不亮。内环越顺，这个盲区越隐蔽：人很容易把「它自己跑通了」误读成「它对了」。终审不撤，对账三问照跑（[A2](02-manual-reconciliation.md)），工具流时代反而更要盯紧这一条。

## 二、MCP 解剖：三个角色、三类原语、一条拓扑

要让模型读手册、跑构建，得先有一条把外部能力接进模型的标准插座。这条插座就是 MCP。最短定义用 Claude Code 官方文档的说法（能力描述，访问日期 2026-10-27）：

> The Model Context Protocol (MCP) is an open standard for connecting AI tools to external data sources.

规范侧的硬事实（MCP 官方规范，协议版本 2026-07-28，规范用语遵循 BCP 14 / RFC 2119）：消息格式 JSON-RPC 2.0，方法与参数都是结构化 JSON，抓包能逐字读；架构分三方；server 暴露三类原语。逐层拆。

消费侧接触 MCP 的入口通常是一份配置文件：在工位的设置里声明要接哪些 server、各自用什么方式启动（本地命令还是远程地址）。界面与文件名随工具与版本漂移，各家写法不同，查各自官方文档的当前版本；不变的是三件要决定的事：接哪个 server、给它什么权限、它出不出网。这份文件读到底是一张授权表：每添一行，就多一个能摸到你文件的角色；填表的手续在第六节，四问清单就是从这三件事长出来的。

**三个角色**。Hosts 是发起连接的 LLM 应用：你的 VS Code、Cursor、Claude Code 工位都是 host。Servers 是提供上下文与能力的服务：读文件、查 Git、抓网页各是一个 server。Clients 是 host 内部的连接器，host 为每个 server 建一个 client。盯住「一 server 一 client」这条拓扑（官方架构页）：接三个 server，host 里就是三条各自独立的排线，一条连手册柜、一条连版本史、一条连外网文档。排线的好处是各拔各的：哪条出事拔哪条，其余照常干活。这就是授权的颗粒度：能力按 server 分批接入、分批授权，出问题时按 server 定位与摘除。

拓扑还有一层工程含义。本地 STDIO server 通常只服务一个 client，跑在你自己机器上，权限跟着你的用户走；远程 Streamable HTTP server 通常服务多个 client，你的代码与日志要出机器、进别人的服务。消费侧的默认姿势是本地优先，第六节展开。规范把协议切成两层：data layer（消息与能力协商）与 transport layer（STDIO 与 Streamable HTTP 两种搬运方式）。消费侧只需抓住一条：同一套原语，本地管道与远程 HTTP 都能跑。

**三类原语**。server 向 client 暴露 Resources、Prompts、Tools 三样东西，用嵌入式的手各翻译一遍：

| 原语 | 规范里的角色 | 嵌入式翻译 |
|---|---|---|
| Resources | 数据，server 提供给模型的上下文 | RM0090 章节文本、原理图导出、仓库文件、串口日志 |
| Prompts | 提示模板，可复用的提示词 | [A1](01-prompt-patterns.md) 的三段式工单固化成模板，全组共用 |
| Tools | 可执行能力，模型可以调用的动作 | 跑一次 arm-none-eabi-gcc 构建、读一段串口日志 |

client 侧还有一个 Elicitation 原语：server 可以主动向用户反问补齐信息，与 [A1](01-prompt-patterns.md) 里「不确定就提问」那条保险丝同一个意图。一个时效提醒：旧教程常提的 Sampling 与 Logging 两个 client 原语，自协议版本 2026-07-28 起已被官方标记为 deprecated（架构页明示），学新不学旧。

三类原语与后面三节场景实录是一一对应的：场景一「读手册」消费的是 Resources，把手册文本当数据喂进上下文；场景二「跑构建」消费的是 Tools，把构建命令包成模型可调用的动作；场景三「看串口」两者都吃，日志文件是 Resource，管道直喂是 host 自带的壳能力。至于 Prompts，你的三段式工单模板固化进去，全组下工单就走同一张骨架。原语只有三类，组合是无限的：消费侧的功夫全在「拿什么素材配什么原语」这一件事上。

**生态与治理**。官方在册 reference servers 仅 7 个：Everything、Fetch、Filesystem、Git、Memory、Sequential Thinking、Time（官方 servers 仓库 README，访问日期 2026-10-27）。官方明示其定位是教学示例，"not as production-ready solutions"；早期的 GitHub、GitLab、Google Drive、Postgres、SQLite、Slack 等参考实现已归档进 servers-archived；更多服务器走官方 MCP Registry。治理侧：2025-12，Anthropic 把 MCP 捐赠给 Linux Foundation 下设的 Agentic AI Foundation（2025-12-09 成立），与 Block 的 goose、OpenAI 的 AGENTS.md 同为创始项目。一个协议有了中立治理与官方注册中心，就从某家的私有排线变成行业的标准插座，这是它值得进你工具箱的理由。

本章立场是消费侧：怎么选 server、怎么授权、怎么用在嵌入式流程里；自建 server 是另一门课，本书不展开。时效口径与全书一致：本节每个事实都对着附录 E 的一张来源卡（访问日期 2026-10-27），网上旧文引的旧版协议号（如 2025-06-18）已过时，以 2026-07-28 为准。界面与清单会变，「三角色、三原语、一 server 一 client」的方法论不变。

为什么押协议而不是押某个工具？官方架构页自己给了类比：LSP（语言服务器协议）当年把「编辑器接语言智能」这件事标准化，换来的是任何编辑器都能接任何语言。MCP 想做的是同一件事在 AI 工具侧的翻版：工具与数据源写一遍 server，任何 host 都能用。协议层沉淀、产品层换代，你的学习投资应该放在沉淀的那层。规范本身也在快速演进：2025-11-25 的规范版本引入了异步操作、无状态化、server 身份与官方 extensions 等机制，到 2026-07-28 版本又有调整；这恰好是「学协议骨架、不背界面细节」这条口径的官方证明。

## 三、场景实录一：读手册，别靠背

[A1](01-prompt-patterns.md) 里你学过给手册章节号当锚点：§2.3 表 1 查总线归属，§7.3 查使能位，§8.4 查位定义。那是「靠锚点」级：模型对 RM0090 的训练记忆相当广，锚点能帮它站稳，但记忆终究是记忆，它能把 MODER 的偏移说对，也可能在下一轮一本正经地编一个不存在的位名。工具流把这个场景再升一级：不靠记忆，靠文件。

三级对照：

| 级别 | 做法 | 幻觉风险 |
|---|---|---|
| L0 靠记忆 | 什么都不给，直接问 | 编页码、编位名，语气与答对时一样自信（[A1](01-prompt-patterns.md) 实锤） |
| L1 给锚点 | 提示词里写手册章节号 | 站稳大半，内容仍靠它的记忆转述 |
| L2 给文件 | 手册文本进仓库，Filesystem server 授权只读 | 它引的每行都有仓库原文可对 |

实录一遍 L2 的姿势。把 RM0090 相关章节的文本导出（比如 GPIO 寄存器章、RCC 章），放进工程仓库的 datasheets/ 目录；这份文本你自己核对过，从此是「手册的仓库快照」，与代码同仓演进。给工位配 Filesystem server，授权范围只读这个目录（授权怎么审，第六节）。工单从 [A1](01-prompt-patterns.md) 的「位定义查 §8.4」升级成：

> 【上下文】……位定义读 datasheets/ 下 RM0090 的 GPIO 章文本，MODER/OTYPER/OSPEEDR/BSRR 各寄存器的偏移与位域以该文件为准，引用时给出原文行。

输出的变化肉眼可见：它给的每个位定义后面跟着仓库文件里的原文行。你的对账动作不变，还是三问（[A2](02-manual-reconciliation.md)），但抽查成本骤降：它写「MODER 偏移 0x00」，你打开 datasheets/ 搜一下就知道它读没读对，不用翻整本 PDF。

两条边界先说死。其一，它读到的原文经它转述仍可能走样：读串行、截断、把相邻寄存器的位域张冠李戴，这类错工具流不免疫；所以抽查不撤，只是从「怀疑它的记忆」降级为「核对它的引用」。其二，手册快照是你的资产：官网改版、PDF 换版，你的 datasheets/ 目录不动，全组对的是同一份文本。网页版手册与厂商文档页也可以经 Fetch server 抓，同一口径：抓来的内容进证据链时带来源与日期，与 [A0](00-pair-not-ghost.md) 的来源卡纪律一致。

快照从哪来、放哪去，定三条规矩就够。来源：手册原文只能从厂商官方渠道拿（ST 官网的 RM0090 PDF），文本导出后你自己核对一遍关键表再入库，导出工具的错字与模型的幻觉是同一物种，都不能免检。范围：datasheets/ 只放团队核实过的章节，按芯片与外设分文件，别整本糊成一个巨型文本，检索精度与上下文预算都吃不消。演进：手册换版时更新快照并在 commit 里写明版本差异，模型引用的「原文行」必须能对回你手里的那份，而不是对回官网的最新版。

为什么是文本快照而不是直接喂 PDF？三个现实原因。其一，PDF 的位定义表排版复杂，两栏、跨页、合并单元格，解析成文本后错行错列是常态，你核对过的纯文本比现场解析的 PDF 可信。其二，上下文预算：参考手册体量庞大，整本进上下文既不经济也不必要，你关心的一直是当前外设那几章。其三，可评审：文本进了版本库，diff 看得见，PDF 换版你只能靠记忆发现。哪天工具的 PDF 解析可靠到你能抽查通过，再换不迟：方法不变，载体可换。

L0 与 L2 的回答摆在一起对照，差别一眼可见：

| 对照项 | L0 靠记忆 | L2 给文件 |
|---|---|---|
| 位定义的出处 | 「根据 RM0090……」（记忆转述） | 指着仓库里的原文行 |
| 你的对账动作 | 翻整本 PDF 逐位重查 | 打开 datasheets/ 抽查引用行 |
| 幻觉被抓的时机 | 上板之后（最坏的时机） | 对账台上（最好的时机） |
| 团队复用 | 每人各信各的记忆 | 全组对同一份快照 |

读手册这个场景是三个场景里收益最稳的一个：零写入、零执行，风险最低，而幻觉高发区恰好就在手册事实上。工具流的第一课从这里开始：先把「它的记忆」换成「你的快照」，再谈跑命令这种带电操作。

## 四、场景实录二：跑构建，内环还给机器

[B0](../build/00-toolchain.md) 教你装 arm-none-eabi-gcc 时，构建是你亲手跑的：敲命令、读红字、改、再敲。这个循环正是 agent loop 的天然靶子，2025-02-24 的官方公告把这套动作写进了产品定义（第一节引过原文）。实录工单长这样：

> 【上下文】工程：S3 点灯工程，霸道者 F407，板卡事实照旧：PF6 红灯共阳接 3.3V，低电平点亮；GPIOF 基地址 0x40021400，时钟使能位 RCC_AHB1ENR bit5。
>
> 【约束】只许动 main.c；禁用 HAL 与标准库；时钟使能第一句；不许用压警告的方式消警告。
>
> 【验收】arm-none-eabi-gcc 交叉编译通过、零警告；随代码附对账表；你自己重新构建验证后再交。

发出去，观察，不要插手。它跑构建、读错误、改代码、再跑构建，转到零警告交卷。这个过程你只盯三件事，盯的时候手里拿一张观察记录表：

| 轮次 | 它跑了什么命令 | 它改了什么 | 结果（错误数变化） |
|---|---|---|---|
| 1 | | | |
| 2 | | | |
| 3 | | | |

这张表就是 agent 会话的对账单。它交卷时你不只看最终的绿，还看这张表：每一步是不是都在收敛，有没有一轮改完错误数反而变多（那是在拆东墙），有没有同一个文件被来回改（那是在绕圈）。

**它修的是因还是症状**。报 undefined reference，修因是补上定义或改对名字，修症状是把调用删了；报警告，修因是改代码，修症状是加编译选项把警告压掉。「不许用压警告的方式消警告」写进约束段，封的就是后一条路。判断因与症状，用的还是你在前面章节攒下的判据：工具流不生产判据，只消耗判据。

修症状有三个肉眼可辨的信号，评审 diff 时对照着看：其一，删代码多于加代码，功能随着错误一起消失了；其二，改动出现在构建配置而不是源码里，警告被 flag 压掉、检查被选项绕过；其三，它解释不清为什么这样修，注释从「因为手册说」退化成「这样可以过」。三个信号中任何一个出现，这一轮就不能算收敛，退回让它修因，修不了就换你上。

**它跑了几次构建**。一次过，说明任务太简单或运气好；三到五次收敛是常态；十次以上还在转，多半在绕圈，叫停，看它卡在哪个错误上：多半是缺上下文，按 [A1](01-prompt-patterns.md) 的迭代纪律补锚点，比让它硬转便宜。Cursor 官方文档明示一个任务内工具调用次数无上限（能力描述，访问日期 2026-10-27），所以「让它自己转到天荒地老」不是策略，是账单的代名词。

**它有没有顺手越界**。约束写了只许动 main.c，它有没有动 Makefile、有没有顺手「优化」别的文件。Cursor 官方文档给过一个配套机制：Checkpoints 是会话期间的本地代码快照，只用于撤销 agent 的改动，永久版本控制请用 Git（能力描述，访问日期 2026-10-27）。agent 的产物必须进你自己的版本控制、逐 diff 评审，这条纪律与工具无关。

验收的换算关系随之更新。[A1](01-prompt-patterns.md) 的三层验收是可编译、上板现象、对账动作；工具流把「可编译」这一层整个包给机器，你的终审从三层收敛到两层：对账与上板。省力是真，陷阱也是真：内环越自动化，「编译绿」的迷惑性越强。它自己跑通的代码，位照样可能错：AHB1 写成 APB1，编译器不报警，它也不报警，因为它和那台编译器一样，不认识你的板子。绿灯只放行到对账台，不放行到烧录器（[A2](02-manual-reconciliation.md)）。

它交卷之后，你的动作序列固定四步：

1. **看 diff 不看总结**：它的「修好了」是语气，git diff 是证据；逐 hunk 过，顺手改动当场揪出；
2. **看对账表抽查**：它附的逐寄存器章节号表，抽一行对回手册，对不上整份退回；
3. **自己复跑一遍构建**：它的「零警告」在你的机器上复现才算数，环境差异是常客；
4. **上板取证**：烧录、按复位、看灯，终审动作一个不少。

四步与 [A0](00-pair-not-ghost.md) 的审计员五步环同构，只是把「下工单」到「收草稿」之间的活整个外包给了机器。外包的是手，不是眼睛。

## 五、场景实录三：看串口，日志变证据

嵌入式与纯软件的工具流，差在最后这一公里：你的「测试输出」在串口上。本书 E08 放音工程（[P12 音频链路](../esp32/12-audio-path.md)）是个现成例子：ESP32-S3 经 I2S 推 ES8311 让喇叭「滴」一声，16kHz/16bit，MCLK = 256 × fs = 4.096MHz，固件启动时串口打出一行 `MCLK=4096000`（main.c:126）。喇叭没响的时候，这行日志在不在、值对不对，是排查的第一站。

日志进模型有两种合规喂法。其一，串口输出抓到文件（uart.log），Filesystem server 授权只读，模型自己读。其二，管道直喂：Claude Code 官方文档明示它遵循 Unix 哲学、可管道化，原话例子就是 `tail -200 app.log | claude -p "…"`（能力描述，访问日期 2026-10-27）。把 app.log 换成你的串口日志，这条路就是为嵌入式准备的。

抓日志本身也有姿势，按排查阶段选：常抓求全（调试期全程落盘，出事后慢慢切），触发抓求准（只在故障复现时开抓，日志短而准），双份抓求对照（正常跑一份、故障跑一份，喂给它做 diff，它找差异比你肉眼快一个量级）。三种姿势的产出都是文件，都走同一个切片纪律。

让它读日志，下工单时把证据三元组写进验收（细则在 [A2](02-manual-reconciliation.md)）：

> 读 uart.log，回答：喇叭为什么没响？回答格式：实测现象（日志里有什么、缺什么）+ 出处（固件哪一行该打这行日志）+ 假设（最可能的原因，按可能性排序）。不许改代码，只出分析报告。

一个合格输出长这样：日志里 I2S 初始化行在、`MCLK=4096000` 在，但功放使能行缺失；查 main.c 第 81 行注释，PA_EN 走 PCA9557 的 bit1（I2C 地址 0x19），不是 ESP32 的 GPIO；假设：功放没被使能，喇叭物理上没通电。注意这条结论链的每一环都有日志行或代码行作锚：实测、出处、板卡事实，证据三元组齐活。

把三元组在本节的落点摆成一张表，回 [A2](02-manual-reconciliation.md) 第四节对照：

| 三元组 | A2 点灯案例 | 本节 E08 案例 |
|---|---|---|
| 实测现象 | 灯不亮、引脚读回高电平 | 日志缺功放使能行、喇叭无声 |
| 手册出处 | RM0090 §7.3、§8.4 | main.c:81 注释、I2C 地址 0x19 |
| 板卡事实 | PF6 共阳接 3.3V | PA_EN 走 PCA9557 bit1 而非 GPIO |

同一个格式，换一个外设照样成立：这就是把回喂纪律写成验收条款的意义，格式对了，它的分析报告才有可审性。

纪律两条，都是 [A0](00-pair-not-ghost.md) 不能清单的延伸。其一，它读的是日志，不是现象本身：日志是固件自报的二手现象，固件说「I2S 初始化完成」不等于示波器上真有 BCK 波形；日志与示波器冲突时，信示波器。其二，它能读你抓回来的日志，不能替你夹探头：串口线你插，日志你抓，终审的物理动作一个没少。工具流改变的是「读」的分工，不改变「测」的分工。

切片怎么下刀，拿 E08 的 uart.log 演一遍。喇叭没响，日志三千行，三刀切出证据片：

1. **尾部窗口**：`tail -200 uart.log`，最后 200 行通常覆盖出事前后的现场；
2. **锚点检索**：`grep -n "MCLK\|I2S\|PA_EN\|ERR" uart.log`，把初始化链路与报错行连同行号一起捞出来；
3. **时间窗**：知道故障在第 40 秒前后发生，就按日志时间戳切那一小段，前后各留 20 行余量。

切完的三片拼起来喂给它，附一句「这是三段切片，分别来自日志尾部、锚点检索与故障时间窗」。它拿到的信息密度比三千行全量高得多，你省下的上下文预算，留给它的分析报告用。切片的原则只有一条：有名有姓。每一片从哪来、为什么切它，写在切片开头；无名切片与断章取义是同义词。

## 六、权限与安全边界：软约束不是硬门禁

工具接得越多，闸门越要建在硬处。这一节摆三份官方口径，它们说的是同一件事：别把安全押在模型的自觉上。

**口径一：MCP 规范的安全原则**。协议版本 2026-07-28 的规范原文三句（规范定义）：

> Users must explicitly consent to and understand all data access and operations.

> Hosts must obtain explicit user consent before invoking any tool.

> Tools represent arbitrary code execution and must be treated with appropriate caution.

翻译过来：数据访问与工具调用，用户必须明示同意且知情；工具等于任意代码执行，按这个危险等级对待。「接入即授权」不是修辞：你每接一个 server，都是一份实打实的能力让渡。

「明示同意」在嵌入式工位上要翻译成一份逐次点头的清单：读文件可以批量放行，写文件要看路径，跑构建命令可以入白名单，推仓库与发网络请求必须逐次确认。凡是让比特离开这台机器的动作（推送、上传、发请求），都不配进「不再询问」的名单；这条线画在哪，取决于这次泄露的后果你赔不赔得起。

**口径二：Cursor Run Modes 三档**。官方文档（访问日期 2026-10-27；版本线索取自其页内 Changelog：v3.6 于 2026-05-29 把 Auto-review 定为推荐默认，v3.23 于 2026-10-01 新增 Read access Workspace 模式）：

| 模式 | 行为 |
|---|---|
| Auto-review | allowlist 内的命令直跑；其余尽量进沙箱；再剩下的交后端 LLM 分类器判读 |
| Allowlist | 只跑白名单内的命令，其余逐条问你 |
| Run Everything | 全部直跑，不问 |

沙箱是操作系统级的实现：macOS Seatbelt、Linux Landlock+seccomp。Auto-review 的分类器能借助 ReadFile/Grep/Glob/ListDir 这类只读工具判读命令内容。Cloud Agents 不走 Run Modes（官方明示）。最关键的一句官方原话，值得贴在工位上：

> The classifier can make mistakes…Auto-review is not a security boundary.

分类器会犯错，Auto-review 不是安全边界。厂商自己都不敢让模型给模型当门卫，你更不该。

**口径三：CLAUDE.md 是软约束**。Claude Code 官方 memory 文档写得明白：CLAUDE.md 每次会话启动时被读取，但（能力描述，访问日期 2026-10-27）：

> Claude treats them as context, not enforced configuration. To block an action…use a PreToolUse hook.

上下文，不是强制配置。你在 CLAUDE.md 里写「禁用 HAL」，它大概率遵守，也可能在某一轮忘了；想硬拦一个动作，官方指的出路是 hooks 这类机制。这与本书的立场同构：三段式提示词是软约束，管态度与质量；构建门、对账三问、diff 评审是硬门禁，管放行。[A1](01-prompt-patterns.md) 教你写好软约束，[A2](02-manual-reconciliation.md) 给你硬门禁的对账动作，两者缺一不可，且不能互相替代。

三份口径摆在一起，交集清晰得近乎苛刻：规范说工具调用前须用户明示同意，Cursor 说自己的自动分类器不是安全边界，Anthropic 说自家的记忆文件不是强制配置。三家厂商，三份各自独立的文档，同一句潜台词：自动化的每一层都会错，最后一道闸门必须是不依赖模型自觉的东西。这不是本书的偏执，是供给侧的自白。

三层防线摆一张表：

| 层 | 例子 | 性质 | 失手后果 |
|---|---|---|---|
| 软约束 | 三段式、CLAUDE.md、rules | 模型每轮读到，靠它遵守 | 质量漂移，含雷量回升 |
| 工具闸门 | Run Modes、allowlist、沙箱 | 拦截执行，但分类器会错 | 危险命令可能漏放 |
| 硬门禁 | hooks、构建门、对账三问、diff 评审 | 确定性检查，不依赖模型自觉 | 不绿不放行，雷留在对账台上 |

落到操作：每个接入的工具先过四问清单，答完再授权。把这一步当成入职面试：四道题就是背景审查，授权就是发工牌；答不上题的候选人，演示再精彩也不发。

1. **读什么**：路径范围收到最小，datasheets/ 只读，别把整块硬盘放出去；
2. **写什么**：默认零写入，构建类能力只给构建目录；
3. **执行什么**：命令白名单到具体命令（make、arm-none-eabi-gcc），不给任意 shell；
4. **出不出网**：本地 STDIO 优先；远程 server 意味着你的代码与日志进别人的服务，涉敏工程直接否。

四问之外加一条凭据纪律：生产环境的凭据（OTA 服务器、量产烧录、云控制台）永不进 agent 的运行环境。它能跑构建，不等于它该握着产线的钥匙。常见坑第一条就是这条的事故形态。

把四问清单用在两个典型 server 上，答案长这样：

| 四问 | Filesystem server（读手册） | 构建能力（跑命令） |
|---|---|---|
| 读什么 | datasheets/ 与 docs/，其余不可见 | 工程目录只读，构建脚本内容可审计 |
| 写什么 | 零写入 | 只写构建输出目录（build/） |
| 执行什么 | 不执行任何命令 | 白名单：make 与 arm-none-eabi-gcc 系列 |
| 出不出网 | 不出 | 不出；拉依赖走你自己的包管理，不走它 |

两张答案卡填完，授权范围就定死了；填不出来的格子，等于候选人交了张空白简历，不录。

授权的顺序也有讲究，按风险从低到高爬坡：先本地后远程（STDIO 不出机器，HTTP 出机器），先只读后写入（读手册、读日志先于改文件、跑命令），先单 server 后多 server（一条连接跑顺了再接下一条，出问题好定位）。每爬一级，把这一级的行为观察一个任务周期再放行下一级。权限一旦放出去就很难完整收回，爬坡容易下坡难。

最后把第六节收拢成一句立场：工具流把模型的手接进了你的工程，手的每一根手指都要经过你的闸门。软约束让它知道规矩，工具闸门让它难越界，硬门禁让越界变不成事故。三层都在，工具流才是生产力；只剩软约束，工具流就是把风险自动化。

## 常见坑

- **把 Auto-review 当安全边界**：官方原话 "Auto-review is not a security boundary"，分类器会犯错。它的定位是省你的确认点击，不是保你的安全。真正管放行的只有硬门禁：allowlist、沙箱、hooks、你的 diff 评审。
- **给模型生产环境凭据**：OTA 升级服务器 token、量产烧录座、云控制台账号，进了 agent 环境就等于进了它的行动半径。一句「帮我部署一下」配一把真钥匙，事故报告都不知道从哪写起。开发与生产的凭据物理隔离，agent 只碰开发侧。
- **整段日志塞进上下文**：串口跑了半小时，几千行日志一把糊给它，关键行被淹没，它开始一本正经地编「日志里有」的行。切片三招：tail 窗口取最后 200 行；按时间戳或锚点行（如 `MCLK=`）筛出关键段；分段喂，每段带一句「这是第几段、共几段」。给的是切片，但要给得有名有姓。
- **拿 7 个 reference servers 上生产**：官方 README 明示其定位是教学示例，"not as production-ready solutions"。学拓扑、跑实验尽管用；进产线、进团队流程之前，按第六节四问清单重新审一遍，或换生产级实现。
- **工具接上了，对账撤了**：内环全绿（编译过、它自己验证过）是最容易放松终审的时刻。它不认识你的板子这件事，与它能跑多少工具无关。绿灯只放行到对账台：三问照跑，上板照烧（[A2](02-manual-reconciliation.md)）。
- **抄别人的 MCP 配置不审能力清单**：网上抄一段配置，server 一连，工具一多，看着挺热闹。接入即授权：每个 server 先问它暴露了哪些 Tools、读到什么路径、出不出网，四问过不完不授权。别人的配置堵的是别人的风险。
- **把 agent 的总结当交付**：它说「修好了，全部测试通过」，diff 里却混着三处顺手改动、一处警告被 flag 压掉。交付物以 diff、构建门与对账表为准，不以它的总结为准；总结是语气，diff 是证据。

## 短自测

五题全答得出，本章才算闭环；答不出的回到对应节复读。

1. MCP 的 Hosts/Clients/Servers 各自是什么？「一 server 一 client」的拓扑决定了什么？
<details><summary>看答案</summary>Hosts 是发起连接的 LLM 应用（你的 VS Code、Cursor、Claude Code 工位）；Servers 是提供上下文与能力的服务（读文件、查 Git、抓网页各一个）；Clients 是 host 内部的连接器，host 为每个 server 建一个 client。这条拓扑决定授权的颗粒度：能力按 server 分批接入与授权，出问题按 server 定位与摘除；本地 STDIO server 通常只服务一个 client、权限随你的用户，远程 Streamable HTTP server 通常服务多个 client、你的数据要出机器。</details>

2. Resources/Prompts/Tools 三类原语，各自对应嵌入式工具流里的什么素材？
<details><summary>看答案</summary>Resources 是数据：RM0090 章节文本、原理图导出、仓库文件、串口日志；Prompts 是提示模板：A1 的三段式工单固化后全组复用；Tools 是可执行能力：跑一次 arm-none-eabi-gcc 构建、读一段串口日志。client 侧的 Elicitation 对应「不确定就提问」那条保险丝。另记一条时效：Sampling 与 Logging 两个 client 原语自协议版本 2026-07-28 起已 deprecated，旧教程的说法不要学。</details>

3. 「你粘错误」与「它自己跑构建」差在哪三重损耗？为什么内环还给机器后，你反而更不能下班？
<details><summary>看答案</summary>切片损耗（你粘最后 10 行，根因常在第一条）、时效损耗（你粘的是上一刻的现场）、语境损耗（文件、行号、编译命令、工程结构没跟过去）。内环还给机器后你从管道回到审计员：内环绿只证明语法与环境层面的正确，总线归属、共阳极性这类「你的板子」的事实，编译器与 agent 都不认识；对账与上板两个终审动作反而成了你的主战场。</details>

4. Cursor 官方为什么说 "Auto-review is not a security boundary"？三层防线各管什么？
<details><summary>看答案</summary>Auto-review 把白名单外的命令交后端 LLM 分类器判读，官方明示分类器会犯错，所以它不是安全边界，定位是省确认点击。三层防线：软约束（三段式、CLAUDE.md，管态度与质量；官方定性 context, not enforced configuration）、工具闸门（Run Modes、allowlist、沙箱，拦截执行但会漏）、硬门禁（hooks、构建门、对账三问、diff 评审，确定性检查，不绿不放行）。</details>

5. 串口日志回喂的切片三招是什么？为什么说模型读日志不改变「测」的分工？
<details><summary>看答案</summary>切片三招：tail 窗口取尾部（官方例 tail -200）、按锚点行或时间戳筛关键段、分段喂并标注段号。日志是固件自报的二手现象：固件说 I2S 初始化完成，不等于示波器上有 BCK 波形，日志与示波器冲突时信示波器。插串口线、抓日志、夹探头这些物理动作仍是你的活，工具流只改变「读」的分工，不改变「测」的分工。</details>
