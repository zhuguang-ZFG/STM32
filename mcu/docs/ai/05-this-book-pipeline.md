# A5 这本书是怎么和 AI 一起写成的：生产线的自证

> 🎯 前四章教你把大模型当结对工程师。这一章把被告叫上证人席：你手里这本书，从起草到印前，就是按那套方法论由 AI 和人结对生产的——而且它给自己装了十几道机器门。自证不是炫技，是把「模型给假设、人拿终审权」落成可复现的命令。你在这一章读到的每个论断，都能在仓库里跑一条命令复现。

## 本章精髓

1. **软约束挡不住流水线事故，硬门禁才挡得住**。AGENTS.md 里的写作约定是 context，真正能拦住缺陷的是门：印前 13 门、契约测试、口癖门、题图守卫、数字声明对账：每一道门背后都有一次真实事故，本章逐个解剖。
2. **AI 写的文字要过口癖门，AI 参与的构建要过证据门**。口癖有预算（破折号散文面 ≤2/章），事实有指纹（事实 token 多重集）：`——` 超了是风格问题，「27000 个 tick」被润色成「2.7 万个」是事实事故，两种问题各有一道机器门。
3. **自证的意义是让方法论变成公共财产**。A0 讲定位、A1 讲提示词、A2 讲对账、A3 讲工具流、A4 讲幻觉防御，这些不是道理，是这本书生产线上的工作记录：每一章的写作过程本身就用了那一章的方法。

- **能理解**：为什么「相信 AI」的反面不是「不信 AI」而是「给 AI 的输出装门禁」；一道机器门如何从一次事故里长出来；为什么软约束（风格指南、记忆文件）必须有硬门兜底。
- **能用**：给自己的项目搭一条最小生产线：一个可复现的构建 + 一条数字声明对账 + 一个事实指纹脚本。

## 一、生产线全景：八道工序，十几道门

这本书的生产线不是一条「写完就发」的管道，是八道工序、每道工序至少一台机器门：

| 工序 | 工具 | 守它的门 |
|---|---|---|
| 正文源文 | `docs/` 91 章 markdown（成稿时 94 章） | 磁盘↔manifest 集合相等（`test_build.py`） |
| 装订清单 | `manifest.json`（11 部 / 罗盘 / 75 项来源） | 罗盘四字段非空、来源 ID 已注册 |
| 离线 HTML | `mcu-book/build_html.py` | 构建期断言：章序/罗盘数/附录集/零断链/组件残留即失败 |
| 题花与插图 | 100 枚题花 + 109 张机制动画 | `art_guard`（纯矢量、≤6000B、笔压分级）+ `anim-lint`（色板映射、连续动画） |
| 印前重排 | `mcu-book/build_print.py`（paged.js + Chromium） | 寡行守卫 v3.3（断点前移 + 边界抬升） |
| 终审 | `mcu-book/check_pdf.py` | **13 道门**：字数、字体、页眉页码、目录页码、U+2011、灰点矢量扫描…… |
| 回归测试 | `mcu-book/tests/` | pytest 72 项（契约、守卫、门禁自身） |
| 站点一致性 | `scripts/docs-check.mjs` | 27 条手写数字声明 ↔ manifest 真相逐条对账 |

注意这张表的结构：**左列是资产，右列是对资产的断言**。没有右列，左列就是一堆迟早过期的文件。这本书能宣称「与在线站点同源」，靠的不是承诺，是 `docs-check.mjs` 每跑一次就把 README、入口页、维护说明里的手写数字抓出来跟 manifest 对一遍账。

## 二、三个真实事故：门是怎么长出来的

门不是设计出来的，是事故撞出来的。三个例子，全部有仓库现场可查。

### 事故一：滤镜题图被印前光栅化

章首题花的手绘感最初靠 SVG 滤镜（feTurbulence 抖动）表达。直接内联进 HTML 没问题，但走印前路径时，Chromium 把带滤镜的题图**整块光栅化**，全书平白多出 94 张位图，印刷分辨率与文字可搜索性净损。更糟的是另一条流水线会话把滤镜版题图批量写回过目录，对抗发生。

长出的门：题花一律纯矢量（零 filter/id/url/href），`mcu-book/tools/art_guard.py` 全目录把守（viewBox 320×88、≤6000B、笔压至少两档、纯 LF），`build_html.py` 装配期再加一道硬门：带 feTurbulence 的题图直接构建失败。回归测试 `tests/test_print_vectors.py` 钉死「印前产物不得出现题图位图」。

**教训**（A4 决策树的叶子一）：「图画得对不对」的正确性定义在印前产物里，不在屏幕预览里，所以验证动作是矢量扫描产物，不是看图。

### 事故二：断点处的幽灵连字符 U+2011

印前重排用 paged.js 的分页引擎。寡行守卫要把「页首只剩一行」的段落断点前移一行，实现上要在溢出 Range 上设边界。有一类边界落在文本节点偏移 0，paged.js 的 hyphenateAtBreak 取 `prevLetter` 得到 `undefined`，`String(undefined)` 是字符串 `"undefined"`，首字母 `u` 恰好命中单词字符正则，于是页尾被悄悄追加一个连字符 U+2011。系统字体回退渲染它，字体门当场红。

更深的事故还在后面：修掉连字符后，元素形式的边界 `(code, 0)` 会在上一行末尾留下一个**空 `<code>` 元素**：inline-code 的背景色块凭空出现在行尾，文字检索完全看不见（空元素没有文本）。三处现场（p492/p577/p716）用像素级采样才抓到：行尾约 2.5×11pt 的灰色小片。

长出的门：寡行守卫 v3.3 把边界「抬升」过内联元素（`build_print.py:306` 的 walk-up），外加全书矢量扫描：`get_drawings()` 按填充色 `#f2f2f2`、宽 `<6pt`、高 `>7pt` 全书搜空内联灰点。这道扫描现在是印前电池的常驻成员。

**教训**：幽灵缺陷的共同形态是「肉眼看不见、文本检索看不见」。对这类缺陷，验证动作必须落在渲染产物或矢量结构上，而不是源文。

### 事故三：手写数字与真相漂移

新增第十一部时，构建器里钉着一个常量 `EXPECTED_CHAPTERS = 88`。接线的第一天它就在五处断言里把「加一章」变成「改五个数」。同一天还发现：README、入口页、维护说明里的手写数字（章数/部数/附录数/来源数/动画数）全部滞后于真相，`docs-check` 一口气报了 24 处不符。

长出的门与修法：常量删除，改为 `chapter_count(manifest)` 从清单推导（`build_html.py:49`）；测试断言同步改为推导式；数字声明交给 `docs-check.mjs:340` 的 27 条 CLAIMS 对账：连「历史上 v1.0.0 是 88 章」这样的句子都要改写成不命中正则的措辞，因为门的语义是「任何命中的数字都必须等于当前真相」。

**教训**：手写数字是债。能推导的推导，不能推导的（比如历史版本号）就改写成「当时的」口径，并用门的正则形状约束自己。

### 一个附赠事故：对账章引错手册

A2 是全书的「引证纪律」章，初稿里写着「查 §7.3 存储器映射」。评审通道抓出来：存储器映射是 RM0090 §2.3 表 1，§7.3 是 RCC 寄存器定义。错处当场分家：基地址区段引 §2.3，使能位引 §7.3，正文、对账表、自测答案、动画注释、manifest 罗盘边界八处同步改正。

这条值得单列，因为它就是 A2 自己的论点：模型（这次是给书起草章节的模型）给的引证是假设，判据在手册。对账章都没豁免，你的代码当然也不豁免。

## 三、AI 在生产线上的四个角色

这本书的第十一部是这样生产出来的（全部过程在仓库 `.trellis/tasks/10-27-ai-dev-deepen/` 里留痕）：

**角色一：研究采集**。研究代理只读官方一手文档（厂商文档/规范仓库/官方博客），产出 15 条带来源、快照与访问日期的引用条目，营销话术逐条隔离。对应你在 A0 学到的「来源卡纪律」：采集时就把「可引」和「好听」分开。

**角色二：批次起草**。章节由起草代理按罗盘（问题/交付/边界）+ 试点章样板成批撰写，每章落盘即过 `prose_guard --single` 口癖门与链接白名单。运行实录里最值钱的一条纪律是 **file-first**：子代理 15 分钟运行时上限，两个代理都曾因调研耗尽上限而零产出；恢复指令只有一句：先落完整骨架，再打磨。这条纪律你在任何长任务里都该用。

**角色三：评审通道**。独立的评审代理对每一轮改动给出意见，本轮一共采纳 7 条（引证分离、无效 SVG 动画属性、旧计数漂移、站点门禁、隔页覆盖测试等）、驳回 3 条过时或误报。评审意见不是命令，是要逐条验真的输入；其中「试点章引错手册」那一条，直接改写了 A2 的八处引证。

**角色四：对账与终审**。所有数字/版本/行号引用在成稿时逐条核过当期仓库；每条论断给复现命令；终审权在人，这是 VS Code agents 文档的红线句在本书生产线上的落实。

四个角色合起来，就是 A0 那张「能/不能清单」的工业化形态：能起草、能采集、能评审、能对账；不能替你做终审、不能替你上板、不能替你为错误负责。

## 五、边界：哪些环节 AI 不许碰

生产线再自动化，有几道环节 AI 永远不许单独碰：

1. **手册事实的终审**。模型可以读手册、抄位表，但「这个位是什么」的最终判定必须落在手册原文与你的复核上。A2 的对账三问没有代理。
2. **上板实测**。凡标「待上板实测」的论断，只有仪器说了才算数。模型可以帮你写测试代码，不能替你看见示波器。
3. **出版裁决**。门禁全绿是出版的必要条件，不是充分条件。发不发布，人说了算。
4. **门的阈值放宽**。阈值只能变严不能变松，这是防「为了过门而松门」的元规则。本轮所有阈值的变动历史都在仓库里，每一条都是收紧。

这四条合起来，就是 A0 里那句红线的完整版：模型对产物负责的部分是「生成与建议」，人对产物负责的部分是「判定与发布」。

## 常见坑

- **把软约束当门禁用**：CLAUDE.md/AGENTS.md 是 context，不是门禁：写得再严，模型也只是「通常照做」。防线要落在可执行检查上（脚本 + 退出码）。
- **门禁只建不审**：门会漂。数字声明手写一次就过时一次，要么推导（chapter_count），要么对账（docs-check），不许靠记忆维护。
- **评审意见照单全收**：评审代理也会过时（它的意见基于更早的仓库状态）。每条意见先验真再采纳，本轮 10 条里 3 条被驳回。
- **子代理长任务不设 file-first**：调研到运行时上限、零落盘是真实发生过的失败形态。骨架先行，加深靠追加。
- **给 AI 的职责越界**：让模型「顺便决定发不发版」是边界事故。终审与发布永远在人。

## 短自测

1. 这本书「可信」的理由是什么？为什么说这个理由与作者无关？
<details><summary>看答案</summary>理由是每条论断都有一道可复现的机器门守着：印前 13 门、契约测试、口癖门、题图守卫、数字声明对账，全部给出命令与退出码。与作者无关的含义：可信度不来自「这是谁写的/谁审核的」这种声明，而来自「不信你可以自己跑」的可复现性。作者声明可以被编造，退出码不能。</details>

2. 事故二里幽灵连字符 U+2011 与灰色小片为什么文本检索抓不到？各自的正确探测手段是什么？
<details><summary>看答案</summary>U+2011 是渲染产物里的字符：它由分页引擎在断点处临时追加，源文里根本不存在，搜源文永远搜不到；探测手段是检索印前产物（PDF 文本层）或字体门的回退报告。灰色小片是空 code 元素（inline-code）的背景色块：空元素没有文本，文本层同样看不见；探测手段是渲染产物的矢量扫描（get_drawings 按填充色与尺寸搜）。共同教训：幽灵缺陷的探测必须落在产物上，不是源文上。</details>

3. 手写数字为什么是债？本书怎么处置它？
<details><summary>看答案</summary>手写数字与真相之间没有任何强制同步机制，真相变一次它就过时一次，这就是债。处置分两类：能推导的改推导：章数从 manifest 求和（chapter_count），进度块由 docs:gen 扫描生成；不能推导的（历史版本的真实数字）改写成「当时的」口径，让数字声明门的正则不再命中它。门的语义是任何命中的数字必须等于当前真相。</details>

4. 第十一部生产过程中的 file-first 纪律是什么？它治什么病？
<details><summary>看答案</summary>file-first：子代理先落完整骨架（全部必备结构段落齐、正文可到七成），再迭代打磨，落盘优先于完美。它治的病是「调研耗尽运行时上限、零文件落盘」：本轮两个起草代理都曾因此撞 15 分钟上限被取消，恢复指令就是这句纪律。推广到任何长任务：先有一个可构建的整体，再加深局部。</details>

5. AI 在本书生产线上有哪四个角色？哪一个环节它永远不许单独碰？
<details><summary>看答案</summary>四角色：研究采集（官方文档带来源卡）、批次起草（罗盘+口癖门+链接白名单）、评审通道（意见逐条验真后采纳）、对账终审辅助（数字/行号核当期仓库）。永远不许单独碰的环节有四个：手册事实终审、上板实测、出版裁决、门的阈值放宽：前三个是终审权问题，第四个是防「为过门而松门」的元规则。</details>
