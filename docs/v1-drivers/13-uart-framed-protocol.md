# UART 与可恢复帧协议

> UART 的硬件只保证一件事：线上的电平按约定节拍一位一位地走，它不知道一条命令在哪里结束。这一章先把 0x41 的十位骨架和 BRR 的分频账算清，把 TXE/TC 与接收标志的清除顺序钉住；后半段把字节流切成可恢复的帧：COBS 定界、CRC-16/CCITT-FALSE 验身、逐字节状态机在丢字节后重新对齐。F407 与 F103 各算一套账，HAL 与手写落位对一遍；GD32 与 ESP32 只划边界。

## 本章罗盘

- **问题**：0x41 在线上为什么是 1,0,0,0,0,0,1,0，115200 下一位多宽？72MHz 与 84MHz 的 BRR 为什么是 `0x271` 与 729，`baud = PCLK / BRR` 里的 BRR 到底是寄存器整数值还是两个字段？TXE 与 TC 差在哪，RS-485 为什么必须等 TC？IDLE 与 ORE 为什么要“读 SR 再读 DR”，FE 置位时坏字节为什么还进了 DR？HAL 的 MspInit 与 SetConfig 两层与手写 `usart1_init()` 怎么一一对上？UART 为什么不能告诉你命令的边界，长度前缀、转义、COBS 在丢一个字节后各付什么代价？一帧为什么是 8+N 字节、74 字节上限怎么推出来？CRC-16/CCITT-FALSE 的四个参数与检查值 0x29B1 怎么验？EMPTY/COLLECT/DISCARD 三态在丢字节后怎么重新对齐，确认帧入队失败为什么不能执行命令？e02 的探头接哪里、记录什么，来源留下了哪些读数？
- **交付**：能从真实 PCLK 算出两套 BRR 并说明字段拆法；能在逻辑分析仪上认出一帧并量出位宽；能写出 TXE/TC 与 RXNE/IDLE/ORE 的判据与清除序列；能把 HAL 的 MspInit、SetConfig、Transmit 三层与手写落位对上；能手算一帧的 CRC 与 COBS 编码，说出解码的四个拒绝条件；能画出三态状态机与八项计数，解释丢字节后第一帧为什么可能被牺牲；能按 e02 接线、设采样率、解码并留下记录。
- **边界**：四平台章。F407 的 84MHz、PA9/PA10 复用、HAL 行号来自 S7《S7 USART：让芯片开口说话》及 DS8626、RM0090；F103 的 72MHz、`0x271`、没有 OVER8 来自根书第 06 章及 RM0008、DS5319；可恢复帧协议来自 C8《C8 串口协议：从字节流到可恢复的消息》与 `mcu/code/common/reliability`；实验来自 E02。四个来源都没有留下本章的上板读数：S7 的八行误差表由宿主脚本按公式打印，e02 的 `hardware_status` 是 pending、记录表为空，C8 的实验记录写“待实测”。S7 有一句说 16MHz 下改 OVER8=1 能把 921600 的误差降到 -0.794%，按 RM0090 的 3 位小数位复算对不上，本章标为待复核、不复述结论。GD32 只写寄存器改名与编号边界，并指出 G3 的偏移表与 RM0090 的 USART 布局冲突；ESP32 只写 UART 驱动边界。DMA 引擎留给[第 14 章](./14-dma.md)，仪器与证据方法留给[第 40 章](../v6-labs-projects/40-lab-method-instruments.md)。
- **依据锚点**：S7（`mcu/docs/stm32/07-usart.md`）、根书第 06 章《06 串口 UART》（`docs/06-串口UART.md`）、C8（`mcu/docs/c/08-framed-protocol.md`）、E02（`mcu/docs/lab/e02-logic-uart.md`）；[第 8 章](./08-architecture-memory-clock.md)的 APB 时钟与 USART1 基址、[第 10 章](./10-interrupts-nvic-exti.md)的 NVIC 使能、[第 12 章](./12-timers-pwm.md)的时基对照、[第 2 章](../v0-foundations/02-c-volatile-ub.md)的 volatile 合同、[第 3 章](../v0-foundations/03-struct-abi-registers.md)的寄存器结构体与 ABI、[第 4 章](../v0-foundations/04-function-pointer-state-machine.md)的状态机写法。RM0090、RM0008、DS8626、DS5319 与 HAL 源码行号均转引自上述来源。

## 先做出来

不接板子也能完成最小胜利：把两套波特率账和一张帧的宽度算出来。默认 16 倍过采样（OVER8=0）时只有一条公式：

```text
baud = PCLK / BRR
BRR = 16 × USARTDIV = (DIV_Mantissa << 4) | DIV_Fraction
```

表里两行输入写在第一列，目标都是 115200：

| 平台 | PCLK（输入） | USARTDIV = PCLK/(16×115200) | BRR 寄存器 | 实际波特率 | 误差 |
| --- | --- | --- | --- | --- | --- |
| F103 USART1 | 72MHz（APB2） | 39.0625 | `0x271`（625） | 72e6/625 = 115200 | 0 |
| F407 USART1 | 84MHz（APB2） | 45.5729 | 729（`0x2D9`） | 84e6/729 = 115226 | +0.023% |

一帧 8N1 是 10 位：1 位起始、8 位数据、1 位停止。115200 下一位 1/115200 = 8.68µs，一帧约 86.8µs。0x41 = `0100 0001`，从最低位开始发，线上顺序是 **1,0,0,0,0,0,1,0**；0x55 = `0101 0101`，线上是 1,0,1,0,1,0,1,0。两帧的骨架一样，只有数据段不同。

押一题再往下读：把 F103 的 BRR 从 625 改成 624，波特率变大还是变小，偏多少？答案是变大：波特率与 BRR 成反比，72e6/624 = 115384.6，误差 +0.16%。改成 626 则是 115016，误差 -0.16%。一个 BRR 步进在 625 附近就是 0.16% 的量化台阶；四舍五入最多只差半格，这只是后面“误差预算”要扣的第一项。

协议那一半也能在宿主机上先验一件事：CRC-16/CCITT-FALSE 对 ASCII `123456789` 必须算出 `0x29B1`。五行的 Python 就能复算，任何对不上的实现都不该接进协议：

```python
def crc16_ccitt_false(data):
    crc = 0xFFFF
    for byte in data:
        crc ^= byte << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF
    return crc

print(hex(crc16_ccitt_false(b"123456789")))   # 0x29b1
```

有板的人烧 `mcu/code/stm32/03-uart-dma`，USB-TTL 接 PA9/PA10、115200 8N1，发任意字符串应原样回显。来源没有记录这次上板的读数，本章不把预期回显写成已经跑过的结果；探头怎么接、记录什么，见“测量与证据”的 e02。

## 机制

### 一帧的骨架：空闲高，起始低，八位 LSB 先行，停止高

线上的空闲电平是高。一帧从起始位开始：线被拉低一位的时间，接收端看到这个下降沿才开始按约定节拍数格子。接着是 8 个数据位，低位先发，最后是停止位把线拉回高电平，给下一帧留出下降沿。

| 段 | 线上电平 | 位数 | 说明 |
| --- | --- | --- | --- |
| 空闲 | 高 | — | 帧与帧之间的默认状态 |
| 起始位 | 低 | 1 | 下降沿给接收端起拍 |
| 数据位 | 每位按位值 | 8（可配 7 或 9） | LSB 先发 |
| 校验位 | 可选 | 0 或 1 | 奇校验或偶校验 |
| 停止位 | 高 | 0.5 / 1 / 1.5 / 2 | 8N1 用 1 位 |
| 一帧合计 | — | 10（8N1） | 115200 下约 86.8µs |

接收端不是每个位只采一次。F103 的接收器用 16 倍波特率的时钟采样，起始位在第 3、5、7 个采样点确认以滤掉毛刺，数据位与停止位取中间的第 8、9、10 点做多数表决；停止位的三点表决为低就置 FE。这条采样规则来自 RM0008 27.3.3，转引自根书第 06 章，本章没有用仪器复核每个采样点的位置。F103 的 CR1 没有 OVER8 位，过采样固定 16 倍；F407 的 CR1 bit15 是 OVER8，复位值 0，本章的账都按 16 倍算。

![UART 一帧的解剖：0x41 与 0x55 并排，空闲高、起始位拉低、8 位 LSB 先发、停止位拉高；数据不同而骨架相同](/anim/uart-frame.svg)

### 波特率：BRR 的整数值就是分母

把 BRR 拆成两个字段看，`DIV_Mantissa[15:4]` 是整数部分，`DIV_Fraction[3:0]` 是小数部分，手册写的是 `USARTDIV = Mantissa + Fraction/16`、`baud = PCLK/(16 × USARTDIV)`。把 16 乘进去：`16 × USARTDIV = 16 × Mantissa + Fraction`，右边正好是寄存器里那 16 位。所以固件直接写一个整数（625 = `0x271`，Mantissa 39、Fraction 1），不需要先算小数再拼字段；`baud = PCLK / BRR` 里的 BRR 就是这个整数值。字段定义见 RM0008 27.3.4（BRR 寄存器描述 27.6.3）与 RM0090 30.3.4，仓库的寄存器速查表也按同一拆法登记；本章按这个定义复算了下面每一行。

![BRR 的来历：PCLK 与 baud 相除后拆成整数 Mantissa 与小数 Fraction 两个字段](/figures/stm32-07-usart-brr.svg)

S7 给过一张八行误差表，说明同一组公式在不同 PCLK 下的结果：

| PCLK | 目标波特率 | BRR | 实际波特率 | 误差 |
| --- | --- | --- | --- | --- |
| 1MHz | 115200 | 9 | 111111 | -3.549% |
| 8MHz | 115200 | 69 | 115942 | +0.644% |
| 16MHz | 9600 | 1667 | 9598 | -0.020% |
| 16MHz | 115200 | 139 | 115108 | -0.080% |
| 16MHz | 460800 | 35 | 457143 | -0.794% |
| 16MHz | 921600 | 17 | 941176 | +2.124% |
| 42MHz | 115200 | 365 | 115068 | -0.114% |
| 84MHz | 115200 | 729 | 115226 | +0.023% |

这张表的来路要说清：S7 说它由 `probe.sh` 第 1 步在本机打印，输入是固件里的 `BAUD_FROM_PCLK` 与 `PCLK_OF_BRR` 两个宏，不是示波器或逻辑分析仪量出来的。本章按 `BRR = round(PCLK/baud)` 复算了八行，又把 1 到 65535 的每个 BRR 都试了一遍，八行的四舍五入值与最优值完全一致；这只能说明算术与整数下限，不能说明某块板上的 TX 引脚真的跑出了这个波特率。

误差沿整帧累积。接收端在每个位的中点采样，8N1 最危险的时刻是最后一个数据位的中点，也就是起拍后 8.5 个位时间。要让采样点不滑出这一位，需要 `|误差| × 8.5 < 0.5`，总容差约 5.882%，再由收发两端对半分，每端 2.941%。这条推导解释了“±2% 到 3% 的经验值”从哪来，但不含晶振温漂、走线延迟与采样沿抖动；根书第 06 章按另一套口径（0.5 位 = 5% 的帧尾硬边界）再扣掉三点表决窗口半宽与起始沿识别各 1/16 位，给出约 3.75% 的工程预算，本章把它当保守值。

拿这套预算看 1MHz 配 115200：BRR 只能取 9，实际 111111，误差 -3.549%，一项就吃掉 5.882% 的六成；余下 2.333% 由两端分，每端 1.166%，刚够 HSI 的 ±1%，没有余量留给第二项误差。S7 把这个数写成“实测误差”，但同一节说明八行是宿主脚本打印的；本章按算术结果使用，不称它为板上测量。16MHz 配 921600 同样卡在量化上：BRR=17 得 941176，+2.124%，超过每端 2.941% 的一半，余下不到 0.82% 留给两端时钟源。

F407 多一个 OVER8 位（CR1 bit15），置 1 后过采样从 16 倍降到 8 倍，小数部分收窄为 3 位。S7 正文说 16MHz 下改 OVER8=1 可以“等价于把时钟当 32MHz 算，BRR=35，误差回到 -0.794%”，并按它注里的 `baud = 2 × f_PCLK / BRR` 代出这个数。按 RM0090 30.3.4 的字段定义复算，OVER8=1 时 BRR=35 解出 Mantissa=2、Fraction=3、USARTDIV=2.375，实际约 842105 波特，误差约 -8.6%；`2 × f_PCLK / BRR` 把 BRR=35 当成 USARTDIV=2.1875（16 倍口径）来除，只在 Fraction=0 时才与字段定义重合。两个结果对不上，本章不给结论，把它列进读数来路表标为待复核；要落定这件事，得在 F4 上置 OVER8 后读回 BRR 并用仪器量线上位宽。

### 发送：TXE 说“可写”，TC 说“发完”

`USART_SR` 里两个容易混的标志只差一位：TXE 是 bit7，TC 是 bit6。TXE 置位表示数据寄存器 DR 空了，可以塞下一个字节，此时上一个字节可能还在移位寄存器里一位一位往外蹦；TC 置位才表示包括停止位在内的整个字节已经发完。位号按 RM0008 27.6.1 / RM0090 30.6.1，S7 与仓库速查表的登记一致。

| 标志 | 位 | 含义 | 什么时候必须看它 |
| --- | --- | --- | --- |
| TXE | 7 | DR 空，可写下一字节 | 每塞一个字节之前 |
| TC | 6 | 移位寄存器空，停止位已发完 | 切 RS-485 方向、断电、进低功耗之前 |

发送的写法只有一句：塞数据看 TXE，全部塞完再等 TC。

```c
/* 塞数据只看 TXE，全部塞完再等 TC */
while ((USART1->SR & (1U << 7)) == 0) { }   /* TXE */
USART1->DR = byte;
/* ... 循环 ... */
while ((USART1->SR & (1U << 6)) == 0) { }   /* TC，最后必须等这个 */
```

漏掉最后的 TC 等待，在 RS-485 上会把方向切得太早，最后一位被拦腰截断，对方收到半个字节，校验直接挂。中断发送把这两个标志拆成两个使能位：TXEIE（CR1 bit7）每字节进一次中断，TCIE（CR1 bit6）只在收尾时用；接收侧的 RXNEIE 是 bit5。DMA 发送则把“每字节搬一次”交给控制器，手册里的开关是 CR3 的 DMAT（bit7），接收方向是 DMAR（bit6）；开关置位只说明请求接出去了，帧边界仍归协议层。

![TXE 与 TC：写 DR 后 TXE 立刻置位，移位寄存器还在发；停止位发完 TC 才置位，RS-485 切方向必须等它](/anim/usart-txe-tc.svg)

### 接收：RXNE 是字节，IDLE 只是“线空了一个帧时间”

接收有两个层次。字节层是 RXNE（SR bit5）：置位表示收到一个字节，读 DR 取走。帧层是 IDLE（SR bit4）：总线保持高电平满一个帧时间，IDLE 置位。IDLE 只说明线空了，不说明对方协议里的一包数据已经结束；把 86.8µs 的停顿当成命令边界，两条命令之间稍一犹豫就会误判。

IDLE 的清除有一个硬性序列：先读 SR，再读 DR。只读 DR 清不掉；IDLE 是只读位，写 SR 也不管用。标志一直挂着，中断会反复进。ORE、FE、NE、PE 这四个错误位共用同一个清除序列，因为它们都挂在 SR 上，读 SR 再读 DR 才完成一次完整的“状态+数据”握手。FE 置位时坏字节仍然进了 DR，这是它最容易骗人的地方：程序读到一个字节，以为收成功了，其实停止位采样是低电平。

| 标志 | 位 | 含义 | 清除方式 |
| --- | --- | --- | --- |
| PE | 0 | 校验错误 | 读 SR，再读 DR |
| FE | 1 | 帧错误：停止位采到 0 | 读 SR，再读 DR；坏字节仍在 DR |
| NE | 2 | 噪声错误：采样窗口电平不干净 | 读 SR，再读 DR |
| ORE | 3 | 溢出：上一字节没取走，新字节又到了 | 读 SR，再读 DR；只读 DR 不够 |
| IDLE | 4 | 线路空闲满一个帧时间 | 读 SR，再读 DR |
| RXNE | 5 | 收到一个字节，DR 可读 | 读 DR |
| TC | 6 | 发送完成 | 读 SR 再写 DR，或写 0 清 |
| TXE | 7 | 发送数据寄存器空 | 写 DR 后自动清 |

中断接收的边界是“每字节一次”：RXNEIE 打开后，115200 下每秒约 11520 次中断，每次只做取字节与入队这类有界动作。DMA 接收的边界是“搬够 N 个字节或半满”，DMA 不理解帧；循环模式下回调里的 `Size` 是 DMA 当前写到的位置，不是这次新收的字节数，要自己保存上次位置再相减并处理绕回。要按一整包通知，得靠 IDLE 之类的线路事件，而它仍然只是通知，不是协议帧尾。

### HAL 两层：MspInit 管板级，SetConfig 管寄存器

手写初始化是一口气写完的：开 USART1 与 GPIOA 时钟、把 PA9/PA10 配成复用、清 CR1/CR2/CR3、写 BRR、最后置 UE/TE/RE 与 IDLEIE。来源工程 `03-uart-dma/main.c` 的顺序就是这样，F407 的 PCLK2=84MHz：

```c
/* F407 USART1：PA9=TX、PA10=RX，AF7；PCLK2=84MHz */
USART1->CR1 = 0;                       /* 先关外设再改参数 */
USART1->CR2 = 0;                       /* STOP=00，1 位停止位 */
USART1->CR3 = 0;
USART1->BRR = 729;                     /* 84MHz / 115200 = 729.17 → 729 */
USART1->CR1 = (1U << 13) | (1U << 3) | (1U << 2) | (1U << 4);
/* UE=1，TE=1，RE=1，IDLEIE=1 */
```

HAL 把同一组落位拆成两层：`HAL_UART_Init()`（`hal_uart.c` @1f6451c 的 L357）先调用 `HAL_UART_MspInit()`，时钟与引脚归这个板级回调；随后关掉外设，再由 `UART_SetConfig()`（L3731）一次落 CR1/CR2/CR3，OVER8 位在同一批写入（L3752-3756），BRR 在函数尾部按过采样选 `UART_BRR_SAMPLING16/8`（L3787/L3791），最后 `__HAL_UART_ENABLE()`（L417）。MspInit 只在句柄状态是 RESET 时被调用，和手写代码“上电配一次”的时机等价。

| 手写落位（`03-uart-dma/main.c`） | HAL 对应（`stm32f4xx_hal_uart.c` @ 1f6451c） | 对照结论 |
| --- | --- | --- |
| 开 USART1/GPIOA 时钟，PA9/PA10 配 AF7 | `HAL_UART_MspInit()`：板级引脚与时钟，只在句柄 RESET 时调用 | 板级两件事归 MspInit |
| 清 CR1/CR2/CR3，再写 BRR | `HAL_UART_Init()`（L357）先关 UE，再 `UART_SetConfig()`（L3731）一次落三个控制寄存器 | 顺序不同，落位相同 |
| `BRR = round(PCLK/baud)` | `UART_SetConfig()` 尾部按 OVER8 选 16 倍或 8 倍宏（L3787/L3791） | 同一个公式，HAL 只换宏名 |
| 发送：TXE 塞、收尾等 TC | `HAL_UART_Transmit()`：每字节前等 TXE（L1172），结束再等 TC（L1191），全程 `HAL_GetTick` 计时超时 | 死等被超时兜底 |
| 接收中断：读 SR 与 CR 使能位再分支 | `HAL_UART_IRQHandler()`（L2355）按“SR 标志 & 对应 CR 使能位”的组合分发（L2599） | 结构同构，不是见标志就处理 |

对应的 HAL 序列（根书第 06 章，F103 的 72MHz 参数）：

```c
UART_HandleTypeDef huart1 = {0};
huart1.Instance = USART1;
huart1.Init.BaudRate = 115200;
```

### 字节流没有边界：三种定界法在丢字节后的代价

UART 硬件只管一个字节。驱动层给的“收到数据”事件、IDLE 中断、一次 `read()` 返回的长度，都只说明此刻手里有这些字节；主机一次写出的命令可能分三次到，三条命令也可能一次全到。边界必须由协议写进字节流本身。

| 定界法 | 做法 | 丢一个字节之后 |
| --- | --- | --- |
| 长度前缀 | 帧头写“后面还有 N 字节” | 长度字段本身错位，之后每一帧都按错的长度切，一路错下去 |
| 转义（SLIP/HDLC） | 保留帧标志字节，数据里出现它就转义成两字节 | 等到下一个帧标志就重新对齐，最坏情况数据长度翻倍 |
| COBS | 把数据里的所有 0 换掉，0x00 只当帧尾 | 等到下一个 0 就重新对齐，开销固定，每 254 字节最多多 1 字节 |

本协议选 COBS，理由是可重新同步且最坏开销能提前算进预算：raw 最长 72 字节，小于 254，COBS 开销恒为 1 字节，缓冲区大小可以在编译期写死，再用 `_Static_assert` 锁住。

### 帧布局与容量：8+N、72、73、74

raw 帧共 8+N 字节，多字节字段都是小端：

| 偏移 | 字段 | 长度 | 含义 |
| --- | --- | --- | --- |
| 0 | version | 1 | 固定为 1；见到别的值报 VERSION |
| 1 | type | 1 | 最高位 0=请求、1=响应；设备收到响应型帧直接忽略 |
| 2 | sequence | 2 | 主机递增，设备原样带回，主机靠它配对响应 |
| 4 | length | 2 | 负载长度 0 到 64 |
| 6 | payload | N | 负载 |
| 6+N | crc | 2 | CRC-16/CCITT-FALSE，覆盖偏移 0 到 5+N 的全部字节 |

解码要求 COBS 还原出的字节数恰好等于 length+8，多一个少一个都报 LENGTH。容量一路推下来：raw 最大 6+64+2=72，COBS 后 73，加帧尾 0x00 共 74。这三个数在 `protocol.h` 里是 `PROTOCOL_RAW_MAX / ENCODED_MAX / WIRE_MAX`，`protocol.c` 开头的两条 `_Static_assert` 把它们和布局绑在一起；本章按源码逐项核对过，属于静态事实。响应的状态字节也占负载容量，INFO/STATUS 的 payload[0] 就是状态码，不能把它当成 64 字节之外的“额外一字节”。

多字节字段一律显式移位读写，不把结构体直接 `memcpy` 上线。填充与端序由编译器和 ABI 决定（[第 3 章](../v0-foundations/03-struct-abi-registers.md)），直接发结构体内存，等于让编译器替你定了一份没写在任何地方的协议。

![raw 帧布局：version、type、sequence、length、payload、CRC-16 共 8+N 字节，COBS 编码后以 0x00 收尾](/figures/c-08-framed-protocol.svg)

### CRC-16/CCITT-FALSE：先把名字叫全

“CRC-16”是一族算法，要确定是哪一个，得给全多项式、初值、输入输出是否反转、结果是否再异或这几个参数。本协议用的是：

| 参数 | 值 |
| --- | --- |
| 多项式 | 0x1021 |
| 初值 | 0xFFFF |
| 输入/输出反转 | 都不反转 |
| 结果异或 | 0x0000 |
| 检查值（ASCII `123456789`） | 0x29B1 |

检查值是验收标准：哪个实现对 `123456789` 算出 0x29B1，才和本协议一致。本章用上面那段独立 Python 实现复算过这个值，和 C8 的登记一致；这不是上板证据，是参数自洽的检查。`protocol.c` 用逐位实现，没有查表，72 字节以内一帧只需要几百次循环：

```c
uint16_t protocol_crc(const uint8_t *data, size_t n)
{
    uint16_t crc = 0xffffU;
    for (size_t i = 0; i < n; i++) {
        crc ^= (uint16_t)((uint16_t)data[i] << 8);          /* 新字节对齐到高 8 位 */
        for (unsigned bit = 0; bit < 8; bit++)
            crc = (uint16_t)((crc & 0x8000U) ? ((uint32_t)crc << 1) ^ 0x1021U : (uint32_t)crc << 1);
    }
    return crc;
}
```

CRC 的边界要说清：它能检出随机损坏，比如单比特错与突发错，但防不住有意篡改，改了数据的人顺手重算一遍 CRC 就行；要防篡改得用带密钥的 MAC。它覆盖的是 COBS 之前的 raw 字节，所以接收端先 COBS 解码、再验 CRC。

### COBS 手算一帧：10 个字节怎么来的

以主机发出的第一条请求为例：INFO（type=0x01），seq=7，无负载。

第 1 步拼 raw：`01 01 07 00 00 00`，依次是 version、type、seq 低字节、seq 高字节、length 低字节、length 高字节。第 2 步算 CRC：对这 6 字节算出 0xB0CC，小端追加，raw 变成 8 字节 `01 01 07 00 00 00 CC B0`。第 3 步按 0 切段，每段前面放“段长+1”的码字：

| 段 | 内容 | 码字 = 段长+1 |
| --- | --- | --- |
| 1 | `01 01 07` | 04 |
| 2 | 空（第 1 个 0 与第 2 个 0 之间） | 01 |
| 3 | 空（第 2 个 0 与第 3 个 0 之间） | 01 |
| 4 | `CC B0`（帧末） | 03 |

第 4 步拼起来再加帧尾：`04 01 01 07 01 01 03 CC B0 00`。10 字节 = 8 raw + 1 COBS 开销 + 1 帧尾，和上一节的公式一致。本章用独立实现复算过这条 10 字节序列，逐字节相同；C8 还给了一条用仓库脚本 `scripts/device-console.py` 复核的命令，那需要 mcu 树的环境，本章没有执行。

解码倒过来走：读码字 c，原样拷贝后面 c-1 字节；c 不等于 255 且后面还有数据时，补一个 0。`protocol_cobs_decode` 有四个拒绝条件，任何一个成立就返回 0：码字为 0；声称的段长超过剩余字节；段内出现 0；输出已满。段内出现 0 说明这一段被截断或拼接过，长度对不上说明有字节丢了，两种情况都不能“尽量解出一点”。

### 逐字节状态机：三个状态，八项计数

`protocol_rx_feed` 每次吃一个字节，状态只有三个：EMPTY、COLLECT、DISCARD。

| 当前状态 | 收到 | 动作 | 计数 |
| --- | --- | --- | --- |
| EMPTY | 0x00 | 什么都不做 | — |
| EMPTY / COLLECT | 非零，缓冲未满 | 存入缓冲，记下 `last_ms`，进 COLLECT | — |
| COLLECT | 非零，缓冲已满 73 字节 | 清空，进 DISCARD | oversize |
| COLLECT | 0x00 | 调 `protocol_decode`，回 EMPTY | ok / cobs / version / length / crc 之一 |
| COLLECT | 距 `last_ms` 满 100ms 后的非零字节 | 先超时：清空，进 DISCARD，本字节被吞 | timeout |
| DISCARD | 非零 | 吞掉 | — |
| DISCARD | 0x00 | 回 EMPTY | — |
| 任意 | 传输层报丢失 | 清空，进 DISCARD | transport_loss |

几处值得逐行看的细节：

- **EMPTY 收 0 不计数是有意的。** 主机重试前会多发一个 0x00 做同步；它落在 EMPTY 态只是个空操作，不会污染错误统计。
- **超时用无符号减法判断**：`(uint32_t)(now - last_ms) >= timeout_ms`，毫秒计数回绕时差值仍然正确。`tests.c` 从 `UINT32_MAX - 50` 起跑，分别验证间隔 99、100、101ms：99 能收到完整帧，100 和 101 计一次 timeout；下一帧仍能收到，因为超时帧自己的帧尾 0 把 DISCARD 结束了。这是源码里的断言，本章没有编译运行。
- **超时按适配层看到字节的时间算。** F407 的一次 DMA 中断可能一口气交出几十个字节，它们共用同一个 `now`；100ms 量的是“解析器多久没收到新字节”，不是线上每个字节的物理到达时间。
- **计数器是饱和加法**：加到 `UINT32_MAX` 就停住，不会回绕成 0，把“错过很多次”伪装成“从没错过”。

传输层确认丢了字节时，会调 `protocol_rx_loss`，解析器进 DISCARD 等下一个 0。如果丢掉的恰好是上一帧的帧尾 0，解析器遇到的“下一个 0”其实是下一帧的帧尾，下一帧会被整个当成残段吞掉。所以主机侧的规矩是：info/status 有限重试，每次重试前先单独发一个 0x00；那个 0 落在 DISCARD 态就提前结束丢弃，落在 EMPTY 态就是空操作。

发送侧是另一套计数。`protocol_tx_t` 只有 4 个槽，每槽 74 字节，入队时就编码好：队列满了丢新帧并让 `dropped` 加一，已经排着的帧不受影响；一帧发了 100ms 还没发完就放弃剩下的部分，计一次丢，并置 `sync`，下一帧之前先单独发一个 0x00，把对端可能残留的半帧结束掉；`sync` 初值就是 true，所以第一帧之前也会先单独发一个 0x00。服务层最关键的一行是“确认先于执行”：`protocol_tx_enqueue(&tx, &response) && invoke` 两个条件同时成立才执行故障注入。反过来写，命令先执行了、确认帧因为队列满被丢掉，主机会超时重试，同一条不可重试的命令就执行了两次。

![C8 帧协议：字节流逐字节进入 EMPTY/COLLECT/DISCARD 状态机，坏帧与重新同步一图看完](/anim/c08-frame-parse.svg)

### 与第 14 章 DMA 的分工

本章的解析器只认字节，不关心字节从哪来：轮询读 DR、RXNE 中断、DMA 环形缓冲都可以喂它。DMA 自己的账在[第 14 章](./14-dma.md)：F407 的 DMA2 有 8 条流、每条流 8 个通道，USART1_RX 在工程里配的是 DMA2 Stream5 Channel4；F103 的 USART1_RX 走 DMA1 Channel5、USART1_TX 走 DMA1 Channel4（RM0008 的 DMA1 请求映射）。来源工程 `03-uart-dma/main.c` 自己注明没有取得 RM0090 Table 43 的正文，Stream5/Channel4 是常用映射，需要上板自检才能坐实，本章把它标为待复核。

两边分工只有一句：DMA 负责“把字节搬到内存并告诉你搬了多少”，协议层负责“这些字节属于哪一帧、对不对”。DMA 的 HT/TC 中断只说明缓冲区写到了哪里，不能当帧边界；把 DMA 的 `Size` 当帧长，等于让搬运进度冒充协议长度。总线冲突、流与通道的选择、循环模式与 NDTR 回绕留给第 14 章，本章只用到它的字节流。

### e02：逻辑分析仪抓 UART 帧（来源实验设计，记录待做）

![E02 接线与预期波形：USB-TTL 与板子共地收发，逻辑分析仪 CH0 旁听 PA9，字母 A（0x41）按低位先行展开为 1,0,0,0,0,0,1,0](/images/labs/e02-uart-capture.svg)

步骤按 e02 的顺序：

1. 进入 `mcu/code/stm32/03-uart-dma`，`make` 后 `make flash`；装 PulseView，采样率按 e02 的步骤选 24MHz，e02 同时注明按 16 倍波特率留余量时 115200 至少要 2MHz。24MHz 是这类分析仪的标称上限、不必每次顶满，这是本章的建议，不是 e02 的步骤原文。
2. 触发方式设 CH0 下降沿：起始位就是下降沿。
3. 开始采集；USB-TTL 串口助手设 115200 8N1，发送单个 `A`，固件在 PA9 回显。复位时固件还会输出 `uart-dma ready`，它不含大写 `A`，别抓错帧。
4. 添加 UART 解码器：115200、8 数据位、无校验、1 停止位。
5. 找到 `A` 的帧，放大逐位数电平，对照 ASCII 0x41 = `0100 0001`，线上是低位先行。
6. e02 的目标里还提到抓字符 `5`：再发一个 `5`（0x35），对照 0x41 看数据段不同、起始与停止的节奏一样。

## 失败分支

| 现象 | 原因 | 区分证据 | 下一动作 |
| --- | --- | --- | --- |
| 完全没有输出 | USART1 时钟门没开（F1 是 `RCC_APB2ENR` bit14），或 UE/TE 没置 | 读 `RCC_APB2ENR` 与 CR1 的 UE/TE；时钟没开时 BRR 写不进、SR 读回复位值 | 先开时钟，再置 UE/TE |
| TX 有波形，电脑收不到 | TX/RX 没交叉，或没共地 | 把 PA9 与 PA10 短接做自环（先断开外部发送端），能收到自己发的字节就说明 MCU 侧正常 | 交叉接线、共地，再查 USB-TTL |
| 满屏乱码 | BRR 与真实 PCLK 不匹配；时钟源回落到 HSI 8MHz 仍按 72MHz 算 | 读 BRR 与 `RCC_CFGR` 的 SWS；8e6/625 只有 12800 波特，慢 9 倍 | 先确认时钟源，再重算 BRR |
| 波特率正好差一倍 | 把 APB1 的 USART2（36MHz）当成 APB2 的 USART1（72MHz） | 看外设基址：F103 的 USART1 在 `0x4001_38xx`、F407 的在 `0x4001_1000`，USART2 在 `0x4000_44xx` | 按总线归属取 PCLK |
| FE 置位，收到坏字节 | 停止位采到 0，通常是波特率偏差或线路干扰 | 读 SR 的 FE；坏字节仍进了 DR | 读 SR 再读 DR 清 FE，再查波特率与接线 |
| 接收停死，新字节被丢 | ORE：上一字节没取走，新字节又到了 | 读 SR 的 ORE；只读 DR 清不掉 | 读 SR 再读 DR，提高取数优先级 |
| IDLE 中断反复进 | 没有按“读 SR 再读 DR”清 IDLE | 读 SR 的 IDLE；ISR 里是否只读了 DR | 改成读 SR 再读 DR |
| RS-485 最后一个字节被截 | 等 TXE 就切方向，没等 TC | 读 SR 的 TC；截断总是发生在最后一字节 | 切向前等 TC |
| 把 IDLE 当成协议帧尾 | IDLE 只说明线空了一个帧时间 | 两条命令之间停顿超过 86.8µs 就误判 | 用协议定界，IDLE 只当通知 |
| DMA 环形缓冲的 `Size` 当成新增字节数 | `Size` 是 DMA 当前写到的位置 | 连续两次 `Size` 相同时仍收到数据 | 保存上次位置，读到当前写位置，处理绕回 |
| 协议口混进 printf 文本 | 文本没有 0x00 结尾，和下一帧拼接 | 偶发 CRC 错，越打印越错 | 协议口只走二进制帧，调试走 SWD 或独立串口 |
| 偶发 CRC 错 | 半帧残留、丢字节或线路干扰 | 看 COBS/CRC/oversize/timeout 哪个计数在涨 | 先补一个 0x00 重新对齐，再查丢字节源 |
| 丢字节后第一帧被吞 | 丢的正是上一帧的帧尾 0 | `transport_loss` 计数增加，紧接着的下一帧没有 ok | 主机重试前先发一个 0x00 |
| 主机超时重试，同一条命令被执行两次 | 确认帧入队失败，代码仍执行了命令 | 看 STATUS 里的 TX 丢帧数是否在涨；服务层顺序 | 先入队确认，成功才执行 |
| 超时误判 | 100ms 从解析器看到字节算，不是线上到达时间 | 一次 DMA 交出几十字节共用同一个 `now` | 按适配层时间戳算，不按字节物理到达算 |
| COBS 解码返回 0 | 码字为 0、段长超过剩余、段内出现 0、输出已满 | 看接收错误里的 cobs 项 | 丢弃整段，等下一个 0 |

## 跨平台边界

F407 一侧：USART1 在 APB2，168MHz 主频、APB2=/2 时 PCLK2=84MHz，115200 用 BRR=729；PA9=TX、PA10=RX，AF7。寄存器偏移按 RM0090 的 USART 布局：SR `0x00`、DR `0x04`、BRR `0x08`、CR1 `0x0C`、CR2 `0x10`、CR3 `0x14`。CR1 的 bit15 是 OVER8，复位值 0；本章的公式只在 OVER8=0 时成立。USART2/3 与 UART4/5 挂在 APB1，USART1/6 挂在 APB2（USART6 基址 `0x4001_1400`）；F103 只有 USART1 在 APB2、USART2/3 在 APB1；本章的 F103C8 没有 UART4/5（高密度 F103xC/D/E 才有）。换串口先换总线再换 PCLK。HAL 行号与 MspInit 行为绑定 F4 HAL 的 1f6451c 版本，换库先核对。

F103 一侧：USART1 同样在 APB2，72MHz 主频时 PCLK2=72MHz，115200 用 `0x271`；PA9 是 LQFP48 第 30 脚、PA10 第 31 脚，要换到 PB6/PB7 得先开 AFIO 时钟再配重映射。F103 的 CR1 没有 OVER8 位，只有 16 倍过采样，别把 F4 的 8 倍写法搬过去。USART1 的时钟门是 `RCC_APB2ENR` bit14；USART2/3 在 `RCC_APB1ENR` 的 bit17/18，PCLK1=36MHz 时同样 115200 要 `0x138`，误差 +0.16%。接收 DMA 用 DMA1 Channel5，发送用 DMA1 Channel4；SPL 的 `USART_Init()` 与 HAL 落位相同，但一手源码仍缺。

GD32 只划边界。G3《USART 增强点》记录了两条可用的差异：GD32F4xx 的串口从 0 起编号，寄存器名从 CR1/CR2/CR3、BRR、SR、DR 换成 CTL0/CTL1/CTL2、BAUD、STAT、DATA，动作位加 EN 后缀（UEN/REN/TEN），状态位用 B 替代 X（RBNE/TBE）。G3 还给过一张偏移表，把 CR1 写成 `0x00`、SR 写成 `0x14`，这和 RM0090 与仓库速查表的 USART 布局（SR `0x00`、DR `0x04`、BRR `0x08`、CR1 `0x0C`）对不上；本章不复述那张表，偏移一项标为待复核，完整对照与 ARM/RISC-V 两条线见[第 29 章](../v4-platforms/29-gd32-arm-riscv.md)。在 GD32 上照抄 STM32 的 CR1 名字编不过，这是确定的；按偏移迁移之前先对一遍手册。

ESP32 只划边界。ESP32-S3 没有 STM32 的 USART 寄存器，串口走 ESP-IDF 的 UART 驱动，环形缓冲、事件队列与超时语义都由驱动定义；本章的 BRR、TXE/TC、IDLE 名字一个都不要带过去。C8 在 S3 上用的是 UART1、GPIO10=TX、GPIO11=RX、驱动 RX 环形区 1024 字节、每轮最多取 512 字节、事件最多等 5ms，这些是那一份工程的具体配置，不是系列通用常数。外设与驱动框架见[第 31 章](../v4-platforms/31-esp32-drivers-audio.md)，架构与启动见[第 30 章](../v4-platforms/30-esp32s3-architecture-boot.md)。

其它分工：DMA 引擎在[第 14 章](./14-dma.md)；仪器与证据方法在[第 40 章](../v6-labs-projects/40-lab-method-instruments.md)；双板记录器项目用的是同一份 codec，见[第 41 章](../v6-labs-projects/41-dual-board-logger-project.md)。CAN 与 USB 的现场总线对照在[第 35 章](../v4-platforms/35-can-usb-fieldbus.md)。

## 离开检查

1. 0x41 在串口线上的位序是什么？115200 8N1 下一位多宽、一帧多宽？
2. 72MHz 与 84MHz 的 BRR 各是多少？`0x271` 的 Mantissa 与 Fraction 怎么拆？
3. 5.882% 的总容差怎么来的？1MHz 配 115200 为什么不行？
4. TXE 与 TC 的区别是什么？RS-485 切方向为什么必须等 TC？
5. IDLE 与 ORE 为什么都要“读 SR 再读 DR”？IDLE 为什么不是协议帧边界？
6. HAL 的 MspInit 与 SetConfig 两层，与手写的 `usart1_init()` 怎么对上？
7. 一帧为什么是 8+N 字节、74 字节上限怎么推？CRC-16/CCITT-FALSE 的四个参数与检查值是什么？
8. 丢一个字节后解析器怎么重新对齐？第一帧为什么可能被牺牲？确认帧入队失败为什么不能执行命令？

<details>
<summary>对照答案</summary>

1. 0x41 = `0100 0001`，LSB 先发，线上是 1,0,0,0,0,0,1,0。115200 下一位 1/115200 = 8.68µs，8N1 一帧 10 位，约 86.8µs。
2. F103 是 625（`0x271`），F407 是 729（`0x2D9`）。`0x271` 拆成 Mantissa 39（`0x27`）与 Fraction 1，USARTDIV = 39 + 1/16 = 39.0625，16 × 39.0625 = 625。
3. 接收端在最坏位置（最后一个数据位的中点，起拍后 8.5 位）采样，要求 `|误差| × 8.5 < 0.5`，得总容差 0.5/8.5 ≈ 5.882%，收发两端对半分是每端 2.941%。1MHz 配 115200 只能取 BRR=9，实际 111111，误差 -3.549%，占掉总预算的六成，余下每端 1.166%，刚够 HSI 的 ±1%，没有余量。
4. TXE 说 DR 空了、可以塞下一个字节，移位寄存器可能还在发；TC 说包括停止位在内的整个字节已经发完。RS-485 提前切方向会把最后一位截断。HAL 的 `HAL_UART_Transmit()` 每字节等 TXE，结束再等 TC，死等由 `HAL_GetTick` 超时兜底。
5. 这两个标志都在 SR 上，硬件规定的清除序列是先读 SR 再读 DR；只读 DR 清不掉 ORE；IDLE 是只读位，写 SR 也不管用，只能走同一条读 SR 再读 DR 的序列。IDLE 只说明线路空闲满一个帧时间（8N1 约 86.8µs），两条命令之间停顿超过它就置位，和对方协议里的一包是否结束没有关系。
6. `HAL_UART_Init()` 先调 `HAL_UART_MspInit()` 开时钟、配引脚，对应手写的板级两件事；再关 UE，调 `UART_SetConfig()` 一次落 CR1/CR2/CR3 并按过采样算 BRR，对应手写的清寄存器、写 BRR；最后 `__HAL_UART_ENABLE()` 置 UE。手写的最后一次写 CR1 把 UE/TE/RE/IDLEIE 一起置上，在 HAL 里 TE/RE 由 `Init.Mode` 落位、IDLEIE 由中断使能单独开。MspInit 只在句柄状态 RESET 时调用。
7. 帧 = 1 字节 version + 1 字节 type + 2 字节 sequence + 2 字节 length + N 字节 payload + 2 字节 CRC = 8+N。N 最大 64，raw 最大 72；raw 小于 254，COBS 开销恒为 1，编码后 73；加帧尾 0x00 共 74。CRC-16/CCITT-FALSE 的参数是多项式 0x1021、初值 0xFFFF、输入输出都不反转、结果异或 0x0000，检查值 0x29B1。
8. 解析器在 COLLECT 态遇到帧尾 0 时解码；解码失败只计一次并回 EMPTY，下一段从头收集。如果传输层报告丢了字节，解析器进 DISCARD 等下一个 0；丢掉的若正是上一帧的帧尾，下一个 0 其实是下一帧的帧尾，下一帧会被整个吞掉。所以主机重试前先单独发一个 0x00。确认帧入队失败时执行命令，会让主机超时重试同一条不可重试的命令，造成执行两次；所以必须先入队确认，成功才执行。

</details>
