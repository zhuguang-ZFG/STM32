# baibaiAIGC 评估：不用于改写，清单并入 slop_lint

评估对象：[poleHansen/baibaiAIGC](https://github.com/poleHansen/baibaiAIGC)（AGPL-3.0，克隆到 `.temp/baibaiAIGC`，未改动上游）。用户提议用它给本书去 AI 味。

## 结论

**不把它的改写管线用于本书正文**；其 `references/checklist.md` 中可机械判定的元话语规则并入 `tools/slop_lint.py`（「聊天腔元话语」组），七维评分表留作人工评审参照。

## 为什么不改写

1. **目标相反**。两轮提示词的自我定位是"降低被 AI 检测工具识别的概率"（baibaiaigc2.md 原文），核心手法是第一轮的"增加冗余与解释性"（管理 → 开展……的管理工作）与第二轮的"句法结构冗余化"（开创性研究 → 所开展的具有开创意义的研究成果）。本书的文风契约正好相反：短句、直接、证据口径内嵌；按它的规则改写会把书变差。
2. **破坏受保护契约**。它的"括号内容整合/删除"规则会碰到本书高频的括号证据：`（原理示意，非实拍）` 徽章、`（FreeRTOSConfig.h:27）` 行号、`（来源说法(未复核)）` 口径标记。切块改写不认识这些契约，`book/checks.py` 与 `book/contracts.py` 会红。
3. **事实漂移风险**。正文钉满了行号、寄存器值、实测口径；工具自己也在 README 里声明不适合"随意改动事实或专业内容"的场景。
4. **管线不匹配**。输入是 .docx/.txt、按 850 字切块、调外部 OpenAI 兼容接口；本书是 markdown，代码块、表格、链接、quiz 组件都会被切块改写弄坏。

## 采纳了什么

`references/checklist.md` 十条里有三条是机械可判定的，其中"元话语"（`修改后`、`可以改成`、`如果你愿意` 等聊天腔）与"解释隐喻""连接词"两条在本书实测为 0 或均为正当技术用法（"被改写后"是内存覆写的术语用法；"也就是说"是正当逻辑连接词，不并入）。已并入 slop_lint 的规则组：**聊天腔元话语**（`如果你愿意`、`可以改成`、`帮你改好`、`建议你可以这样`、`这里是改写后的`、`候选版本/候选标题`）——全仓 0 命中，纯防护栏。

## 没采纳什么

- "连续三个句子长度相同""三段式列举""段落单行结尾"：节奏类判据。`slop_lint.py` 文档注释里已有明确设计决策——节奏、rule-of-three 留给人读，不机械化。
- 两轮改写提示词与其评分表中的"纯净输出/语义保真"维度：那是对改写输出的验收，本书没有改写输出可验收。
- 七维评分表（直接性/节奏/信任度/真实性/精炼度/语义保真/纯净输出，70 分制）：留作人工抽查某一章的参照，不进 CI。

## 复核方式

`slop_lint.py --list` 应出现"聊天腔元话语"组；全仓跑一遍应保持既有命中数（书稿正文 0 命中）。
