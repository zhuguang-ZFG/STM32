# R7 移植 RT-Thread 到霸天虎：Nano 手动移植 → 标准版

> 🎯 F8 我们手动接管了 FreeRTOS 的三个异常；这一章走两条路：先用 **Nano**（3KB 的迷你内核）手动移植感受"最小成本"，再用**标准版 BSP** 体验"设备框架+finsh"的完整生态——两条路都走通，RT-Thread 的版图在你心里就完整了。

## 本章精髓

1. Nano 手动移植四件套：内核源码（src/ + libcpu/arm/cortex-m4）+ `rtconfig.h`（裁剪配置）+ board.c（实现 `rt_hw_board_init`：时钟/SysTick/堆）+ 三异常接管（与 F8 同款：PendSV/SysTick/HardFault），内核无关板卡，板卡全在 board.c。
2. SysTick 的双重身份：`rt_hw_board_init` 里配好 1ms tick，ISR 里调 `rt_tick_increase()`，与 FreeRTOS 的 xPortSysTickHandler 异曲同工。
3. 标准版的价值在"带 BSP"：RT-Thread 仓库自带大量 STM32 BSP（同系 F407 BSP 可就近借鉴），复制最近似 BSP 改引脚/时钟/外设，比从零写快十倍；finsh 与设备框架随 `rtconfig.h` 开关即来。

- **能理解**：为什么 board.c 是 Nano 移植唯一的"板卡知识"集中地；为什么标准版抄 BSP 比从零写快十倍；为什么 RT-Thread 不像 FreeRTOS 用 SVC 启动第一个任务。
- **能用**：Nano 路线跑通双线程异频闪灯；标准版路线选最近似 BSP 改三步，出 `list_device` 看到 pin/uart1 在册。

## 一、Nano 四件套：源码/rtconfig.h/board.c/异常接管

RT-Thread Nano 是约 3KB 的迷你内核，只保留调度/IPC/内存，不带设备框架/finsh/软件包。手动移植到霸天虎 F407，四件套：

| 件 | 内容 | 来源 |
|---|---|---|
| 内核源码 | src/（线程/IPC/内存/调度）+ libcpu/arm/cortex-m4（上下文切换/异常） | RT-Thread 仓库 |
| rtconfig.h | 裁剪配置（开哪些 IPC/调度选项、TICK_HZ、堆大小） | 官方模板改 |
| board.c | rt_hw_board_init（时钟/SysTick/堆）+ 三异常接管 | 自己写 |
| 链接脚本 | FLASH/RAM 布局；堆边界符号（与 board.c 配合） | 回 [B3](../../build/03-linker-script.md) |

Nano 的哲学：**内核无关板卡，板卡全在 board.c**。内核源码（src + libcpu）跨所有 Cortex-M4 通用，F407/F411/GD32F4 全用同一份；板卡的差异（时钟频率、HSE 晶振、引脚、堆位置）全部集中到 board.c 一个文件。这与 F8 的 FreeRTOS 移植同理，port 层通用，差异在 FreeRTOSConfig.h + board。

四件套到手后的工程结构：

```text
rtthread-nano-port/
├── src/                    # 内核：thread.c/ipc.c/scheduler.c/...
├── libcpu/arm/cortex-m4/   # 上下文切换：cpuport.c/context_rvds.S
├── include/                # rtthread.h/rtdef.h/...
├── board/
│   ├── board.c             # ★ 板卡知识全在这
│   ├── board.h
│   └── linker.ld           # 链接脚本
├── rtconfig.h              # 裁剪配置
└── applications/main.c     # 双线程闪灯
```

`src/` 与 `libcpu/` 直接从仓库拷，不动一行；`rtconfig.h` 从官方模板改（关掉用不到的 IPC、定 `RT_TICK_PER_SECOND` 与堆大小）；board.c 是唯一的"原创"，这也是为什么说 Nano 移植"最小成本"：要写的代码集中在一个文件。

## 二、board.c 逐行：rt_hw_board_init

board.c 是 Nano 移植的"板卡知识全集"，核心函数 `rt_hw_board_init`：

```c
// board.c（节选）
void rt_hw_board_init(void)
{
    /* 1) 硬件初始化：时钟/中断优先级分组 */
    HAL_Init();
    SystemClock_Config();              // 时钟树（回 S2），HSE 以板卡规格书为准

    /* 2) 系统滴答：SysTick 配 1ms tick */
    SysTick_Config(SystemCoreClock / RT_TICK_PER_SECOND);  // 通常 1000

    /* 3) 堆：把链接脚本划出的区间交给内核 */
    rt_system_heap_init((void *)HEAP_BEGIN, (void *)HEAP_END);

    /* 4) 组件初始化钩子（标准版走 rt_components_init，Nano 可留空） */
#ifdef RT_USING_COMPONENTS_INIT
    rt_components_board_init();
#endif
}
```

三件事的分工：
- **时钟**：调 `SystemClock_Config`（S2 那套 PLL 公式），HSE 晶振频率以板卡规格书为准（霸天虎回 [S2](../../stm32/02-rcc-clock.md) 核对 HSE）。
- **SysTick**：配 1ms tick：`SystemCoreClock / RT_TICK_PER_SECOND`，`RT_TICK_PER_SECOND` 在 rtconfig.h（通常 1000）。
- **堆**：把链接脚本里划出的堆区间交给内核：`rt_system_heap_init(HEAP_BEGIN, HEAP_END)`，`HEAP_BEGIN/END` 是链接脚本符号（回 [B3](../../build/03-linker-script.md)）。

堆边界符号对不上是骨架坑列表第二名：链接脚本的 `end`/`_estack` 与 rt_hw 堆参数对不上，首次 malloc 即崩，这是 B3 链接脚本符号的复训点。内核堆的"池子"就是链接脚本里 `.bss` 之后到栈底之间那块，与 F8 的 `configTOTAL_HEAP_SIZE` 是两种风格：FreeRTOS 用宏定池子大小（一个定长数组），RT-Thread 用链接脚本符号定池子边界（用 leftover 空间）。

## 三、三异常接管：与 F8 同款

Nano 的内核上下文切换也挂在 Cortex-M 的三个异常上：PendSV/SysTick/HardFault（与 [F8](../freertos/08-port-f407.md) 同款，但 RT-Thread 不用 SVC 启动第一个任务，区别在后面）：

| 异常 | RT-Thread 函数 | 干什么 | F8 对照 |
|---|---|---|---|
| PendSV（14） | rt_hw_pendsv（libcpu） | 上下文切换：保存当前线程、恢复下一个 | xPortPendSVHandler |
| SysTick（15） | rt_hw_systick（board.c） | tick 递增：调 rt_tick_increase() | xPortSysTickHandler |
| HardFault（3） | rt_hw_hard_fault（board.c） | 故障取证：打印 PC/LR/栈帧 | 自写（S16） |

**SysTick 的双重身份**：`rt_hw_board_init` 里配好 1ms tick，SysTick ISR 里调 `rt_tick_increase()`：递增全局 tick 计数、检查延时到期的线程、必要时挂起 PendSV 请求切换。这与 FreeRTOS 的 `xPortSysTickHandler` 异曲同工（回 [F8 第二节](../freertos/08-port-f407.md)）：同一颗 SysTick，同一个 1ms 节拍，不同内核的"报时员"。

SysTick ISR 的最小实现：

```c
// board.c
void SysTick_Handler(void)
{
    rt_interrupt_enter();          // 进中断钩子（嵌套计数 +1）
    rt_tick_increase();            // ★ tick + 1，检查延时，可能挂 PendSV
    rt_interrupt_leave();          // 离中断钩子（计数归零可能触发切换）
}
```

`rt_interrupt_enter/leave` 是 RT-Thread 的中断嵌套计数：`leave` 时若计数归零且有挂起的 PendSV，就真正触发切换。这是 RT-Thread 与 FreeRTOS 在中断处理层的细微差别：FreeRTOS 的 `xPortSysTickHandler` 直接在 ISR 里 portYIELD，RT-Thread 用 enter/leave 钩子统一管理临界区与切换时机。

**HardFault 处理差异**：F8 那套是 FreeRTOS 自带（V11 默认关，靠 configASSERT）；RT-Thread 的 Nano 移植要自己写 `rt_hw_hard_fault`，打印出错时的 PC/LR/SP，回 [S16 HardFault 取证](../../stm32/16-debug-hardfault.md) 的栈帧挖 PC 方法。这是 Nano "不带 BSP" 的代价，标准版 BSP 已写好。

**为什么 RT-Thread 不用 SVC**：FreeRTOS 用 SVC 异常手工"启动第一个任务"（恢复它的现场，从此不返回）；RT-Thread 不用 SVC：`rt_thread_startup` 只把线程挂进就绪表，真正的第一次切换在 `rt_system_scheduler_start` 里：它挑出最高优先级线程，调 `rt_hw_context_switch_to`，后者把 `from` 记为 0、置位 PendSV，开中断后 PendSV 立刻进来恢复目标线程现场（`libcpu/arm/cortex-m4/context_gcc.S`）。这是两个内核启动模型的差别：一个靠异常跳进第一个任务，一个靠普通调度路径自然滑进去。

## 四、标准版移植：就近抄 BSP

标准版的价值在"带 BSP"：RT-Thread 仓库 `bsp/` 自带大量 STM32 BSP：stm32f407-atk-explorer、stm32f407-st-discovery、stm32f407-zeo... 同系 F407 BSP 可就近借鉴。流程：

**第 1 步：选最近似 BSP**，优先选同芯片同封装同外设的，差异最小。霸天虎 F407 找同系 F407 BSP 作母本（如 `stm32f407-zeo`）。

**第 2 步：改板三步**，母本 BSP 复制后改三处：

| 改什么 | 在哪改 | 参照 |
|---|---|---|
| 时钟源 | board/board.c 的 SystemClock_Config + linker.ld 的 FLASH/RAM | [S2](../../stm32/02-rcc-clock.md) 核对 HSE 晶振 |
| 引脚 | board/CubeMX_Config 重新配 LED/USART 引脚 | [S3](../../stm32/03-gpio.md)；霸天虎 LED=PF6/7/8 共阳（回 S3/S0） |
| 内存 | linker.ld 的 FLASH/RAM 起址与大小 | 芯片 datasheet |

这就是骨架坑列表第四条"BSP 时钟源不改"的翻车现场：母本 BSP 用 25MHz 晶振，而霸天虎不同频。不改 HSE，PLL 算出来的 SYSCLK 全错；串口波特率依赖 APB 时钟，跟着全错，打印全是乱码。**改板第一步永远是核对 HSE**（回 S2）。

**第 3 步：menuconfig 裁剪 + scons**，`menuconfig` 关掉母本有但霸天虎没有的外设、开需要的（finsh/uart）；`scons -j8` 编；`scons --target=mdk5` 导出 IDE 工程。finsh 与设备框架随 rtconfig.h 开关即来，不需要手写一行 finsh 代码，勾 `RT_USING_FINSH` 自动进构建（回 [R5](05-finsh.md)）。

"比从零写快十倍"的原因：母本 BSP 的 board.c/libraries/Kconfig 已经按 F407 调好，时钟树、HAL 驱动包装、设备框架注册全是现成的，你只改引脚/晶振/内存这三个板卡差异点。从零写 board.c 要调时钟树（S2）、写 HAL 包装（R4）、注册设备，三天活；抄 BSP 改三步，半小时。

## 五、finsh 接入：R4 + R5 闭环

标准版移植的最后闭环是 finsh 接入，串口设备注册给 finsh 的全过程（回 [R4 设备框架](04-device.md) + [R5 finsh](05-finsh.md)）：

```text
USART1 硬件 ──HAL 驱动包装──> rt_serial_device ──注册──> 设备容器 "uart1"
                                                          ↓
                                                    finsh 组件
                                                          ↓
                                                    msh /> 提示符
```

三步：
1. **HAL 包装**：libraries/HAL_Drivers 把 STM32 HAL 的 USART 包装成 `rt_serial_device`（R4 的 rt_device 接口：open/read/write/control）。
2. **设备注册**：`rt_hw_serial_register` 把 uart1 注册进设备容器，`list_device` 能看到它。
3. **finsh 绑定**：rtconfig.h 开 `RT_USING_FINSH`，finsh 启动时查 `rt_console_set_device` 找注册的串口，绑定成控制台，`msh />` 提示符出来。

`menuconfig` 里勾 `RT_USING_FINSH` + `RT_USING_SERIAL`，scons 自动把 finsh 源码和 uart 驱动编进固件，配置驱动开发，不用手写一行 finsh 代码。这就是 R0 说的"组件层当水电"：finsh 是水电，menuconfig 是开关，R6 的"点单系统"在 R5 的 finsh 上落地。

## 六、验收清单：tick/切换/finsh/list_device

移植完按这个清单逐项验：

| 验收项 | 怎么验 | 通过判据 |
|---|---|---|
| tick 走起来 | finsh 敲 `list_thread`，看 tick 计数在涨 | 数字在动 = SysTick 接管成功 |
| 线程切换 | 起两个线程异频闪灯（PF6/7/8），看是否交替闪 | 两灯不同步 = 调度器在切换 |
| finsh 响应 | 串口回车出 `msh />`，敲 `help` | 命令清单出 = finsh+uart 闭环 |
| 设备注册 | 敲 `list_device` | 看到 pin/uart1 在册 = 设备框架工作 |
| 堆可用 | 起线程 + malloc 一块 | 不崩 = 堆边界符号对 |

骨架坑列表的"首次 malloc 即崩"就卡在堆边界符号：`list_thread` 能跑但一 malloc 就 HardFault，根因是链接脚本的 HEAP_BEGIN/END 与 `rt_system_heap_init` 参数对不上（回 [B3](../../build/03-linker-script.md)）。Nano 路线没有 finsh，验收用双线程异频闪灯 + 串口裸打印 tick 计数即可。

## 实物实验

- Nano 版双线程 + finsh 版本二选一跑通；
- 标准版 BSP 改造后 `list_device` 看到 pin/uart 设备注册在册，生态落地的实锤。

## 常见坑

- **rtconfig.h 与源码版本不配**：配置项名随版本漂移，从官方模板改，不抄旧文。
- **board.c 堆边界符号错**：链接脚本符号（如 `end`/`_estack`）与 rt_hw 堆参数对不上，首次 malloc 即崩（B3 复训）。
- **SysTick 冲突**：裸机延时与内核 tick 抢 SysTick，同 F8 教训，统一交给内核。
- **BSP 时钟源不改**：母本 BSP 用 25MHz 晶振而霸天虎不同频，串口波特率全错的经典翻车（回 S2 核对 HSE）。
- **libcpu 选错架构**：拿了 cortex-m3 的 libcpu 给 F407（cortex-m4），上下文切换没存浮点寄存器，浮点任务间互踩。判据是 `-mcpu=cortex-m4` 必须配 libcpu/arm/cortex-m4（同 F8 的 ARM_CM4F 教训）。

## 短自测

**1. Nano 四件套是哪四件？为什么说"内核无关板卡，板卡全在 board.c"？**

<details><summary>看答案</summary>

四件套是内核源码（src/ + libcpu/arm/cortex-m4）、rtconfig.h（裁剪配置）、board.c（rt_hw_board_init + 三异常接管）、链接脚本。说"内核无关板卡"是因为 src/ 与 libcpu/ 跨所有 Cortex-M4 通用，F407/F411/GD32F4 全用同一份；板卡的差异（时钟频率、HSE 晶振、引脚、堆位置）全部集中到 board.c 一个文件，内核代码不动一行，只改 board.c 就能换板。

</details>

**2. SysTick 在 RT-Thread 里的双重身份是什么？与 FreeRTOS 的 xPortSysTickHandler 如何对照？**

<details><summary>看答案</summary>

双重身份：`rt_hw_board_init` 把 SysTick 配成 1ms tick（硬件定时器）；SysTick ISR 里调 `rt_tick_increase`（内核报时员），递增全局 tick、检查延时到期线程、必要时挂起 PendSV 请求切换。与 FreeRTOS 的 xPortSysTickHandler 异曲同工：同一颗 SysTick、同一个 1ms 节拍、都靠 PendSV 切换。细微差别是 RT-Thread 用 rt_interrupt_enter/leave 钩子统一管理切换时机，FreeRTOS 在 ISR 里直接 portYIELD。

</details>

**3. 为什么 RT-Thread 不像 FreeRTOS 那样用 SVC 启动第一个任务？**

<details><summary>看答案</summary>

FreeRTOS 用 SVC 异常手工恢复第一个任务的现场，从此不返回，靠 SVC"起死回生"。RT-Thread 不用 SVC。`rt_thread_startup` 只把线程挂进就绪表；第一次切换发生在 `rt_system_scheduler_start` 里，由 `rt_hw_context_switch_to` 置位 PendSV，开中断后自然进 PendSV 恢复第一个线程。这是两个内核启动模型的差别：一个靠异常跳进第一个任务，一个靠普通调度路径自然滑进去。

</details>

**4. 标准版移植"改板三步"是哪三步？为什么抄 BSP 比从零写快十倍？**

<details><summary>看答案</summary>

改板三步：时钟源（board.c 的 SystemClock_Config + linker.ld）、引脚（CubeMX_Config 重配 LED/USART）、内存（linker.ld 的 FLASH/RAM 起址大小）。抄 BSP 快是因为母本 BSP 的 board.c/libraries/Kconfig 已按 F407 调好，时钟树、HAL 驱动包装、设备框架注册全现成，只改引脚/晶振/内存三个板卡差异点。从零写要调时钟树（S2）、写 HAL 包装（R4）、注册设备，三天活；抄 BSP 改三步，半小时。

</details>

**5. list_device 看到 pin/uart1 在册，说明哪条链路全部打通了？**

<details><summary>看答案</summary>

这说明从硬件到 finsh 的整条链路打通了：USART1 硬件经 HAL 驱动包装成 `rt_serial_device`，注册进设备容器（`list_device` 能看到 uart1），再由 finsh 组件绑定串口成控制台。这是 R4 设备框架 + R5 finsh + R6 menuconfig 的三闭环，勾 RT_USING_SERIAL 与 RT_USING_FINSH 后 scons 自动把驱动和 finsh 编进固件，不用手写一行接合代码。

</details>
