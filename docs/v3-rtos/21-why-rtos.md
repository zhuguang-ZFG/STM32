# 为什么需要 RTOS

按住键盘不放，三任务超级循环里的 LED 会停。原因不是循环"慢"，而是 `uart_echo` 在死等 `RXNE`：等字节的整段时间里，`led_tick` 与 `key_scan` 根本没有被调用。一个任务的等待把整圈拉长，响应上界等于最长单圈；只要有一个任务的最坏执行时间不可界定，整圈就不可界定。

RTOS 卖的不是"更快"，是给每个任务一条自己的时间轴：私有栈、TCB、PendSV 切换，代价是每任务一份 RAM。要不要买，先算账。两个来源都没有留下本章的上板读数：`docs/15` 的四个实验未附板上测量值，`00-why-rtos` 的 probe 有脚本无日志。3.299 s 与 5.47 ms 是宿主事件表读数，本章标「来源说法(未复核)」，不写成 F103/F407 板上实测；115200 8N1 的 86.805 µs/字符 ×40 = 3.472 ms 是「文档推导」。

> 版本口径：根书第 15 章引 FreeRTOS V11.3.2；lab 与本章的源码行号与宏语义按 V11.1.0 对账，V11.3.2 与 V11.1.0 两版行号不混排。

## 本章罗盘

- **问题**：为什么三任务超级循环在按住键盘时会停掉 LED？为什么把 2 ms 的活从第一行挪到最后一行，五局最坏迟到的中位只从 1.49 ms 变成 1.60 ms？RTOS 的三件套各买什么、花多少 RAM？FreeRTOS 任务优先级和 NVIC 中断优先级为什么方向相反，FromISR 的边界到底是逻辑 5 还是 80？SysTick 归谁、HAL 的 1 ms 为什么要搬到 TIM4？`vTaskDelay(1)` 为什么不是精确 1 ms？栈深 128 到底是字节还是字，heap 池子多大才会让 `xTaskCreate` 失败？裸机够不够用，为什么 `ΣWCET ≤ min(T)` 比平均 CPU 利用率更可靠？
- **交付**：能在纸上算出一次阻塞等待如何把响应上界推到最长单圈；能把任务优先级与 NVIC 优先级放进同一张表，并算出 `5 << (8-4) = 0x50`；能按工程算出任务栈、TCB 与 heap 的 RAM 账；能用 `ΣWCET ≤ min(T)` 判断裸机是否够用，不够时说出 RTOS 买的是哪三件东西。
- **边界**：双平台章。F103 是 Cortex-M3、72 MHz、无 FPU、`ARM_CM3`；F407 是 Cortex-M4F、标称 168 MHz，lab 场景 1 跑 HSI 16 MHz、`ARM_CM4F`。F103 根书例程的任务栈 128/192/256 字、heap 10240 B；F407 lab 是 256/256/320 字、heap 16 KiB，两个工程的数字不可互换。3.299 s、5.47 ms、1.49/1.60 ms 来自宿主事件表，不是板上读数；根书的四个上板实验与 F0 的四步 probe 在本仓库都没有日志或产物。第 22 章才展开 TCB、就绪表与调度器，第 23 章才展开 PendSV 与移植，本章只到"要不要上、先算什么"。
- **依据锚点**：根书第 15 章《FreeRTOS 入门》（`docs/15-FreeRTOS入门.md`）、F0《为什么需要 RTOS：先失败一次》（`mcu/docs/rtos/freertos/00-why-rtos.md`）；TCB 首成员与栈字单位见 `01-task-tcb.md`，延时语义见 `03-scheduler.md`，lab 配置见 `mcu/code/rtos/01-freertos-lab/FreeRTOSConfig.h`；中断优先级与 IP 字节见 [v1 第 10 章](../v1-drivers/10-interrupts-nvic-exti.md)，SysTick 与 HAL 时基见 [v1 第 11 章](../v1-drivers/11-systick-timebase-rtc.md)，测量方法见 [v2 第 20 章](../v2-reliability/20-debug-performance.md)。

## 先做出来

先不接板，把四笔账算在纸上。它们决定你上板后看到的是"任务真的晚了"，还是"账本来就不够"。

1. **响应上界账**：115200 8N1 一个字符是 10 位（1 起始 + 8 数据 + 1 停止），一位 1/115200 = 8.6805 µs，一个字符 86.805 µs；40 个字符是 3.472 ms。只要循环里有一个"收一个字符才返回"的调用（逐字节死等），每次调用至少等一个字符（86.805 µs）；下一个字节迟迟不来时，等待可以更长。源文宿主事件表记录的最长单圈是 3.299 s，这个数标「来源说法(未复核)」，但"响应上界 = 最长单圈"的结构不依赖这个具体读数。

   | 量 | 值 | 来路 |
   | --- | --- | --- |
   | 1 个字符（8N1，10 位） | 86.805 µs | 文档推导 |
   | 40 个字符 | 3.472 ms | 文档推导 |
   | 阻塞版最长单圈（宿主事件表） | 3.299 s | 来源说法(未复核) |

   3.299 s 里的大部分不是传输，而是在长按静默段等 4200 ms 才到的下一个字节（901–4200 ms 没有字节）；3.472 ms 只是 40 个字符在线上必须占用的时间。两笔账不能混。

2. **优先级账**：任务优先级数值大者先，NVIC 中断优先级数值小者急。例程里 KEY 是 2，LED 和 UART 是 1，空闲任务是 0；中断侧 0 最急，5 是 FromISR 的起点，15 最缓。两边比较时要用同一种表示：逻辑 5 对逻辑 5，原始 `0x50` 对原始 `0x50`。

   | 对象 | 数值方向 | 例 |
   | --- | --- | --- |
   | FreeRTOS 任务 | 数值大者先 | KEY=2 > LED/UART=1 > idle=0 |
   | NVIC 中断 | 数值小者急 | 0 最急；5 是 FromISR 起点；15 最缓 |
   | 寄存器 IP 字节 | 高 4 位有效 | 逻辑 5 → `5 << (8-4) = 0x50` |

   `0x50` 的十进制是 80，但 80 不是 NVIC 逻辑优先级；把它当逻辑值，会写出一个无法配置的阈值。

3. **RAM 账**：每任务一个私有栈，栈深单位是字不是字节；再加 TCB、队列、信号量与定时器，这些都从 heap 池子里切。把两个工程的数字并排放，是为了看清它们不能互换。

   | 工程 | 任务栈（字） | 折算（B） | heap |
   | --- | --- | --- | --- |
   | F103 根书例程 | 128 / 192 / 256 | 512 / 768 / 1024 | 10240 B |
   | F407 lab 场景 1 | 256 / 256 / 320 | 1024 / 1024 / 1280 | 16 KiB = 16384 B |

   F407 lab 的 `configMINIMAL_STACK_SIZE = 128` 字 = 512 B，是最小任务（空闲任务）的栈下限，不是上面三个业务任务的栈。

4. **WCET 账**：裸机可行性的判据是 `ΣWCET ≤ min(T)`。三个任务 A/B/C 的 WCET 分别是 0.2/0.5/0.3 ms，周期 1/2/5 ms，和是 1.0 ms，正好压在最短周期 1 ms 上；平均 CPU 利用率只有 51%，看起来还有一半余量。把 A 的 WCET 改成 0.4 ms，和变成 1.2 ms，超过 1 ms，平均利用率仍只有 71%，但三个任务同时就绪时一定有人错过期限。平均利用率不能替代最坏响应。

   | 任务 | WCET | 周期 | 平均占用 |
   | --- | --- | --- | --- |
   | A | 0.2 ms | 1 ms | 20% |
   | B | 0.5 ms | 2 ms | 25% |
   | C | 0.3 ms | 5 ms | 6% |
   | 合计 | 1.0 ms | min(T)=1 ms | 51% |

   这组数是教学算术（文档推导），不是测量；它只用来说明"平均值好看"与"最坏时刻够不够"是两件事。

四笔账都对上，才有资格谈"要不要上 RTOS"；对不上，先改代码或减任务，OS 不会替你把 WCET 变小。

## 机制

### 一、超级循环的失败是阻塞传染，不是"慢"

三个任务串成一条线：

```c
for (;;) {
    led_tick();
    key_scan();
    uart_echo();
}
```

`uart_echo` 的写法是"收一个字符才返回"，逐字节死等；真正的实现只有一行 `consume(board_uart_getc())`，下面把它展开成便于对照的形状（教科书里"按行读"的 `uart_gets()` 是另一种写法，不是本章 `uart_echo` 的实现）：

```c
void uart_echo(void)
{
    char c = uart_getc();      /* 死等 RXNE */
    if (c == '\n') {
        uart_puts(line);
        line_len = 0;
    } else {
        line[line_len++] = c;
    }
}
```

`uart_getc()` 内部是：

```c
while (!(USART2->SR & USART_SR_RXNE)) { }
```

收到下一个字节之前，这个循环不会返回，`led_tick` 与 `key_scan` 都不会被调用。你按住键盘不放，没有新字节进来，程序就卡在 `uart_getc` 里，LED 停摆；就算正常打字，两个字符之间的间隙也足以让 LED 的相位漂移。

这就是**阻塞传染**：三个任务共享一根时间轴，每个任务的启动时刻等于前面所有任务本次耗时之和。前两个任务的单次开销是微秒级，第三个是"不定"；一个任务的最坏执行时间不可界定，整条循环的周期就不可界定。问题不在 CPU 慢，而在一个等待把所有人的时间都锁住了。

![超级循环的一根轴与 RTOS 的平行世界](/anim/why-rtos.svg)

图中左侧三个任务共享一根时间轴，`uart_echo` 死等 `RXNE` 时扫描指针停住，LED 与按键一起停摆；右侧三个任务各有私有栈与 TCB，PendSV 在调度点换现场（不只发生在节拍上）。动画是原理示意，不是实测波形。

源文的宿主事件表把同一张事件脚本跑了两版：阻塞版 `uart_echo` 与轮询版 `uart_poll`。读数如下，全部标「来源说法(未复核)」：

| 观测量 | 阻塞版 `uart_echo` | 轮询版 `uart_poll` |
| --- | --- | --- |
| 最长单圈 | 3.299 s | 3.472 ms |
| LED 翻转（应翻 12 次） | 中位 5 | 中位 12 |
| 15 ms 短按（落在字节流里） | 五局全丢 | 迟到 0.00 ms |
| 3.3 s 长按（期间没有字节） | 迟到 3200 ms | 迟到 0.00 ms |
| 串口收 / 发字节 | 54 / 52 | 54 / 52 |

最后一行两栏相同：阻塞版一个字节都没丢。它没搞坏数据，它偷的是别人的时间：该翻 12 次的灯中位只翻了 5 次，15 ms 的短按五局全丢，一次长按晚了 3.2 秒才被看见。

3.299 s 与 3.472 ms 不是同一件事的两个测量。3.299 s 是阻塞版在长按静默段等 4200 ms 才到的下一个字节（901–4200 ms 没有字节），3.472 ms 是轮询版处理 40 个字符必须占用的线上时间；前者是等待，后者是传输。把这两个数分开，才知道"消掉阻塞"消掉的是哪一段。

轮询版把等待消掉了，最长单圈降到 3.472 ms；但它仍然是一根轴，只是那根轴短了很多。下面这笔账说明，短轴不等于优先级。

### 二、调换代码行序不是优先级

把 `uart_echo` 改成非阻塞状态机，确实解决了"等待"：

```c
void uart_poll(void)            /* 每次进来只查一眼，立刻返回 */
{
    if (!(USART2->SR & USART_SR_RXNE)) return;
    char c = (char)(USART2->DR & 0xFF);
    /* ... */
}
```

循环变成三个人都"很快返回"：

```c
for (;;) {
    led_tick();
    key_scan();
    uart_poll();
}
```

但它没解决"谁先跑"。三个任务之间没有任何优先级概念，只是按书写顺序执行。流行的说法是"靠调换代码行顺序来调优先级，把急的活摆到第一行"。这条直觉经不起一次对照：往循环里加一件 2 ms 的活（顶替一段跑不掉的批量采样），只把它从第一行挪到最后一行，跑同一张事件表、每档连跑 5 局。

| 观测量（5 局） | 2 ms 的活摆第一行 | 同样的活摆最后一行 |
| --- | --- | --- |
| 最长单圈 min / 中位 / max | 5.47 / 5.49 / 8.13 ms | 5.47 / 5.47 / 5.48 ms |
| 最坏迟到 min / 中位 / max | 0.71 / 1.49 / 1.85 ms | 0.41 / 1.60 / 5.24 ms |
| 丢键的局 | 0 / 5 | 0 / 5 |

中位差 0.11 ms，而摆最后一行的五局区间（0.41–5.24 ms）把摆第一行的（0.71–1.85 ms）整个包住；摆最后一行的最大值 5.24 ms 反而是摆第一行最大值 1.85 ms 的约 2.8 倍。换行序换不来优先级，连"哪种摆法更差"都决定不了：你只是改了自己在一圈里的站位，而上界由那一圈多长决定，跟站位无关。

这一组数全部标「来源说法(未复核)」。上界约 5.5 ms 的算术来自 2.00 ms 采样 + 3.47 ms 回显（文档推导），它说的是"最长单圈由哪两件事撞在一起决定"，不是板上测量。需求里写"必须 200 µs 内响应"，要的是上界；行序只动得了平均值。

再进一步，用 SysTick 做"时间片"、给每个任务发标志位：

```c
void SysTick_Handler(void) { tick++; }

for (;;) {
    if (tick % 2 == 0) key_scan();
    uart_poll();
}
```

分片仍然在同一根轴上腾挪：取模与条件判断本身也耗时间，某个"任务"内部再出现一次死等，整个时间片调度一起陪葬。改良方案越叠越复杂，可预测性反而更差。要让高优先级任务在就绪时立刻接手，需要的是抢占式调度和独立的执行上下文，不是更多的标志位。

### 三、RTOS 三件套：私栈、TCB 与 PendSV

"每个任务仿佛独占 CPU"是一个幻觉，由三个零件构成：

1. **私有栈**：每个任务有自己的栈，任务卡住时，它的调用栈与局部变量留在自己的地盘上，不污染别人。内核里对应 `pxStack` 与 `pxEndOfStack`。
2. **TCB（任务控制块）**：任务的身份、状态、优先级、栈顶指针都记在 `tskTaskControlBlock` 里。`pxTopOfStack` 必须是结构体的第一个成员，因为切换现场时汇编要靠固定偏移找到它；`uxPriority` 是任务优先级，数值越大越高；`xStateListItem` 把任务挂在就绪、阻塞或挂起链表上。
3. **PendSV 切换**：PendSV 异常里保存当前任务的现场、恢复下一个任务的现场。现场从哪来？就是 TCB 里的 `pxTopOfStack`。第 23 章会展开软硬栈帧与汇编；本章只记住"换指针就是换魂"。

![FreeRTOS 任务状态：Running、Ready、Blocked、Suspended](/figures/sample-15-task-states.svg)

图中 Running 只有一个；Ready 等 CPU；Blocked 等时间或事件；Suspended 要显式恢复。事件唤醒可以在两个 tick 之间发生，不必等到下一个节拍。状态图是原理示意。

阻塞的作用不是"让 CPU 能切换"，而是不占 CPU 地等待，并让低优先级任务有机会运行；一个一直 Ready 的高优先级任务会把低优先级任务饿死。RTOS 解决的是"什么时候轮到谁"，不是"让每件事都变快"。

这三件东西的成本是实打实的 RAM：每任务一个栈、一个 TCB，队列、信号量与定时器再从 heap 池子里切。先算账再上 OS，别等 `xTaskCreate` 返回失败才回头数字节。

### 四、栈按字不按字节，heap 是池子

`xTaskCreate` 的栈深单位是 `StackType_t`，Cortex-M 上是 4 B 的字，不是字节。同一个数字按字节理解，栈就只剩四分之一。

| 工程 | 任务栈（字） | 折算（B） | 说明 |
| --- | --- | --- | --- |
| F103 根书例程 | LED 128 / KEY 192 / UART 256 | 512 / 768 / 1024 | 三任务合计 2304 B |
| F407 lab 场景 1 | low 256 / high 256 / rpt 320 | 1024 / 1024 / 1280 | 三任务合计 3328 B |
| F407 lab 空闲任务下限 | `configMINIMAL_STACK_SIZE = 128` | 512 | 这是最小任务/空闲任务的栈下限 |

F103 例程的 128 字是 LED 任务；F407 lab 的 128 字是 `configMINIMAL_STACK_SIZE` 的空闲任务下限。同一个数字，两个角色，不能互换。

栈够不够，看水位：`uxTaskGetStackHighWaterMark()` 返回任务运行以来剩余的最小空闲字数，接近 0 就该加大。溢出检查用 `configCHECK_FOR_STACK_OVERFLOW = 2`：创建任务时用 `0xA5` 填充栈，溢出时检查栈尾模式并调用 `vApplicationStackOverflowHook`。调用 `printf` 后出现 HardFault，先看水位与钩子，不能只凭打印动作断定是栈溢出。

heap 是池子。`configTOTAL_HEAP_SIZE` 要覆盖所有动态创建的任务栈、TCB、队列、信号量、定时器；池尽时 `xTaskCreate` 失败。F103 根书例程的池子是 10240 B，F407 lab 是 16 KiB = 16384 B；引用时标工程，别把两个数混着用。

堆不足的返回值不是 `pdFAIL`（0），而是负的错误码 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`（-1）。`xTaskCreate` 成功返回 `pdPASS`（1），失败返回 -1；判断写成 `!= pdPASS`，不要写成 `== 0`。

F407 lab 的配置可以直接对账：

| 配置项 | 值 | 行号 | 含义 |
| --- | --- | --- | --- |
| `configCPU_CLOCK_HZ` | 16000000 | 16 | 本工程跑 HSI 16 MHz，不启 PLL |
| `configTICK_RATE_HZ` | 1000 | 17 | 1 ms 一个节拍 |
| `configMAX_PRIORITIES` | 5 | 23 | 优先级 0..4，数字越大越高 |
| `configMINIMAL_STACK_SIZE` | 128 | 27 | 单位是字，512 B |
| `configTOTAL_HEAP_SIZE` | 16 * 1024 | 36 | heap_4 的池子，16384 B |

这张表是 F407 lab 的真值，不是 F103 根书例程的真值。两个工程的优先级级数、栈与 heap 都不同，跨工程引用时先把表头写清楚。

### 五、两套优先级方向：任务看大，中断看小

FreeRTOS 任务优先级数值越大越先跑；NVIC 中断优先级数值越小越急。两套规则方向相反，混着记必错一个。

| 对象 | 规则 | 例 |
| --- | --- | --- |
| FreeRTOS 任务 | 数值大者先 | KEY=2 > LED/UART=1 > idle=0 |
| NVIC 中断 | 数值小者急 | 0 最急；5 是 FromISR 起点；15 最缓 |
| 任务同优先级 | 时间片轮转 | `configUSE_TIME_SLICING` 默认开 |
| 任务与中断 | 两套编号，不可直接比大小 | 任务 2 与中断 5 没有可比性 |

![两套优先级规则：任务号大者先，中断号小者急](/images/ch15-two-priority-rules.png)

图中左列任务号大者先（KEY 2 > LED/UART 1 > idle 0），右列中断号小者急（0 最急，15 最缓）；中间是 `5 << (8-4) = 0x50` 与 1 ms 时基分工。图是原理示意，不是调度波形。

调用 `...FromISR` 的中断，NVIC 逻辑优先级必须大于等于 5。这个 5 来自 `configMAX_SYSCALL_INTERRUPT_PRIORITY = 0x50`：芯片只用高 4 位，`5 << (8-4) = 0x50`。逻辑优先级 0–4 比阈值更急，不受 BASEPRI 临界区屏蔽，可以打断内核正在更新的数据，因此不能调用 FreeRTOS API；5–15 会被屏蔽，可以调用 `...FromISR`。例程把 EXTI0 设成 5。

启用有效的 `configASSERT` 时，带优先级校验的 API 路径能帮助发现这类错误；没有启用断言或没有走校验路径时，错误配置可能直接损坏内核数据。比较时两边要用同一表示：逻辑 5 与逻辑 5，原始 `0x50` 与原始 `0x50`，不要拿 5 和 `0x50` 直接比大小。

来源勘误：`08-port-f407.md:160,296` 把 8 位 IP 原始值 `0x50`（十进制 80）当成了 NVIC 逻辑值，于是给出一个以 80 为逻辑阈值的结论。NVIC 逻辑优先级只有 0–15，80 不是一个可配置的逻辑优先级。本章按逻辑 ≥5 / 原始 ≥0x50 写。中断分组、IP 字节与 EXTI 六步见 [v1 第 10 章](../v1-drivers/10-interrupts-nvic-exti.md)，本章不重讲。

### 六、时基所有权：SysTick 给内核，HAL 改 TIM4

FreeRTOS 的内核节拍通常由 SysTick 提供；本例 `configTICK_RATE_HZ = 1000`，每 tick 1 ms。HAL 的默认时基也用 SysTick。两个都当主人，`HAL_Delay` 会卡住：HAL 的计数没有被它期待的处理函数推进，或者处理函数被内核接管。

做法是把 CubeMX 的 SYS → Timebase Source 改成 TIM4，让两套计数各有入口。若坚持共用 SysTick，必须把处理函数、频率与调度器启动前后的行为一起整合，不能只替换其中一个处理函数。

1 ms 是节拍粒度，不是所有任务响应的下限。事件唤醒可以发生在两个 tick 之间，`portYIELD_FROM_ISR` 可以在 ISR 退出时请求切换；所以"1 kHz 节拍"不等于"响应精度 1 ms"。提高 tick 频率能缩小计时粒度，也增加中断开销，不能单凭频率保证实时性。

F103 根书例程是 SysTick 内核 + TIM4 HAL；F407 lab 场景 1 只使用 SysTick，没有 HAL 时基，所以这条冲突在 lab 里不出现。SysTick 的 `LOAD` 算术与寄存器细节见 [v1 第 11 章](../v1-drivers/11-systick-timebase-rtc.md)，本章不重列。

### 七、延时语义：vTaskDelay 与 vTaskDelayUntil

`vTaskDelay(n)` 从调用时刻再等 n 个 tick。1 kHz 下 `vTaskDelay(1)` 的墙上等待是 (0,1] ms，不是精确 1 ms：调用可能发生在 tick 边界后的任意位置，刚过 tick 调用要等近 1 ms，临近下一个 tick 调用只等几个 µs。

任务先干 3 ms 活再 `vTaskDelay(10)`，周期约 13 ms；工作时间加进了周期。固定周期用 `vTaskDelayUntil`，以上次计划唤醒点为锚：

```c
TickType_t last = xTaskGetTickCount();
for (;;) {
    do_work();
    vTaskDelayUntil(&last, pdMS_TO_TICKS(10));
}
```

它按上次计划唤醒时刻递推下一次；实际开始执行仍可能有抖动或超期。若 `do_work()` 超过一个周期，下一次计划时刻已经过去，函数会立即返回，周期仍然追不回来；该做的是减小 WCET 或加长周期。软件定时器的回调跑在定时器服务任务里，里面不能 `vTaskDelay`，也不能等一个可能被占用的互斥量；需要等待的活交给普通任务。

### 八、WCET 判据：裸机够用不够用，看最坏账

RTOS 不是升级，是换一种成本结构：买的是结构清晰与响应保证，花的是 RAM 与切换开销。小系统上 RTOS 往往更差。

裸机可行性判据是 `ΣWCET ≤ min(T)`：所有任务的最坏执行时间之和必须塞进最短周期，否则所有任务同时就绪时，至少有一个任务错过期限。这是必要条件，不是充分条件；优先级分配、阻塞关系与中断还会改变最坏响应。

| 场景 | 任务与周期 | 判据 | 结论 |
| --- | --- | --- | --- |
| 纯点灯 | `led_tick` 20 条 / 500 ms | 远小于周期 | 裸机足够 |
| 点灯 + 按键 | 加 `key_scan` 14 条 / 20 ms | 一圈 <1 µs（源称） | 裸机足够 |
| 点灯 + 按键 + 阻塞串口 | `uart_echo` 7 条但不定 | 最长单圈 3.299 s（源称） | 不可界定 |
| 点灯 + 按键 + 非阻塞串口 + 2 ms 采样 | 2 ms / 圈 | 上界约 5.5 ms | 取决于那个 200 µs 需求 |
| 三路高速采样 + 通信 | 各 200 µs / 1 ms | 3×200 µs / 1 ms ≈ 60%，加通信后接近周期 | 需要抢占式调度 |

表中的 3.299 s、5.5 ms、指令条数都是「来源说法(未复核)」；3×200 µs / 1 ms = 60% 与判据本身是算术。判据之外还要看任务之间是否独立、周期是否各不相同、有没有"等待但不想拖垮别人"的需求。

不该上 RTOS 的信号：任务都能在一个固定周期内轻松跑完，没有"必须在 X 微秒内响应"的硬要求；Flash/RAM 已经吃紧；其实只有一件事，只是这件事比较长——那需要的是状态机，不是日程表。

该上 RTOS 的信号：有硬实时要求；任务相互独立、周期各不相同；有等待但不想让等待拖垮别人。判据只有一条：**裸机管顺序，RTOS 管期限**。需求里出现第二个"必须在……之内"，就该认真算 RTOS 的账。

## 失败分支

| 现象 | 原因 | 区分证据 | 下一动作 |
| --- | --- | --- | --- |
| 按住键 LED 停，松手又恢复 | `uart_echo` 死等 `RXNE`，阻塞传染 | PC 停在 `uart_getc` 的 `while`；逻辑分析仪上按键期间没有 LED 边沿 | 改成非阻塞状态机，或把串口搬进独立任务 |
| 调换行序后响应仍然晚 | 上界由最长单圈决定，行序只改平均值 | 多局最坏迟到的区间重叠；平均启动时刻变了，上界没变 | 减小 WCET，或改用抢占式调度 |
| 任务越加，周期越长 | 所有任务共享一根时间轴 | 单圈耗时的分布随任务数上升；某个任务的最坏值不可界定 | 合并小任务，或上 RTOS |
| `HAL_Delay` 卡住、调度器起不来 | HAL 与内核抢 SysTick | 检查 Timebase Source 是否还是 SysTick；`HAL_GetTick()` 是否不涨 | 把 HAL 时基改到 TIM4；共用时整合处理函数与计数 |
| 中断里调 FromISR 停在 `configASSERT` | 该中断的 NVIC 逻辑优先级小于 5 | 读 NVIC IP 字节与优先级分组，算出逻辑值；确认 `configPRIO_BITS` | 把中断优先级设成 5 或更缓；不要在 0–4 里调 API |
| 中断里调 API 数据偶发损坏 | 中断优先级 0–4 不被 BASEPRI 屏蔽 | 关中断/临界区行为与损坏是否相关；断言是否启用 | 限制 API 调用；把中断降到 5–15 |
| `xTaskCreate` 返回失败 | heap 池子不够 | 返回值是负的错误码；剩余 heap 接近 0 | 加大 `configTOTAL_HEAP_SIZE`，或减小栈/对象 |
| 打印后 HardFault | 栈按字/字节混淆，或局部大数组占栈 | `uxTaskGetStackHighWaterMark()` 接近 0；溢出钩子命中；0xA5 模式被破坏 | 按字算栈，加大栈，把大数组移出栈 |
| 周期越来越长 | `vTaskDelay` 是相对延时，工作时间累进 | 记录每次唤醒时刻，周期≈工作时间+延时 | 固定周期改用 `vTaskDelayUntil` |
| `vTaskDelay(1)` 不是 1 ms | 1 kHz 下是 (0,1] tick 的区间 | GPIO 翻转测实际间隔，随调用相位变化 | 不要拿它当精确计时；精确计时用硬件定时器 |
| 高优先级任务饿死低优先级 | 高优先级任务一直 Ready、不阻塞 | 低优先级任务长期不进 Running；高优先级任务没有阻塞点 | 加阻塞/延时，或降低其优先级 |
| 高优先级任务等低优先级持有的锁 | 优先级反转 | 中优先级任务抢占了持锁的低优先级任务 | 用带优先级继承的互斥量，不用二值信号量 |
| 两个任务的串口输出叠在一起 | 共享外设没有覆盖完整事务 | 交错发生在整段发送中间，不是单字节 | 用互斥量保护完整发送过程，或改成唯一所有者任务 |

## 跨平台边界

F103 与 F407 都能跑 FreeRTOS，但两套账不能互搬。

| 维度 | F103（根书例程） | F407（lab 场景 1） |
| --- | --- | --- |
| 内核 | Cortex-M3，72 MHz，无 FPU | Cortex-M4F，标称 168 MHz，lab 跑 HSI 16 MHz |
| FreeRTOS port | `ARM_CM3` | `ARM_CM4F`（硬浮点 ABI） |
| 工程 | `examples/freertos-task`（HAL） | `mcu/code/rtos/01-freertos-lab`（无 HAL 时基） |
| 时基 | SysTick 内核 1 kHz + TIM4 HAL | 仅 SysTick 内核 1 kHz |
| 任务栈 | 128/192/256 字 = 512/768/1024 B | 256/256/320 字 = 1024/1024/1280 B；最小栈 128 字=512 B |
| heap | 10240 B | 16 KiB = 16384 B |
| 任务优先级级数 | 例程用 0–2；级数按工程配置 | `configMAX_PRIORITIES=5`（0–4） |
| NVIC 优先级位 | 4 位，分组 4 | 4 位（`configPRIO_BITS=4`） |
| FromISR 阈值 | 逻辑 5 / 原始 0x50；EXTI0=5 | 逻辑 5 / 原始 0x50 |
| RAM | 20 KB SRAM | 192 KB（128 KB SRAM + 64 KB CCM） |
| FPU 上下文 | 无 FPU | 单精度 FPU；切换要保存浮点上下文（第 23 章） |

F103 选错 port 的代价很直接：`ARM_CM4F` 在 M3 上可能编译通过，但调度器一启动就 HardFault，因为 M3 不认浮点指令。F407 lab 跑 HSI 16 MHz，不是 168 MHz；用 168 MHz 去换算 DWT cycles 或延时，会差 10.5 倍。168 MHz 是标称值，不是本 lab 的时钟。

F103 根书例程有 HAL 时基冲突，F407 lab 没有 HAL 时基；把 F103 的 TIM4 步骤原样搬到 lab，会多出一个不需要的时基。反过来，把 lab 的"只配 SysTick"搬到带 HAL 的工程，`HAL_Delay` 可能卡住。

3.299 s、5.47 ms、1.49/1.60 ms 是宿主事件表读数，不是 F103/F407 板上实测；换到真板要跑一批看分布。指令条数 20/14/7 来自交叉链反汇编，是结构数，不是板级时间。

第 22 章展开 TCB、就绪表与调度器，第 23 章展开 PendSV、软硬栈帧与 `ARM_CM3`/`ARM_CM4F` 移植；本章只到"要不要上、先算什么"。

1. 因为失败不是"每一圈都慢一点"，而是某个任务死等时，后面所有任务根本不被调用；一个等待把整圈拉长，响应上界等于最长单圈。只要有一个任务的最坏执行时间不可界定，整圈就不可界定。
2. 卡在 `uart_getc()` 的 `while (!(USART2->SR & USART_SR_RXNE))` 里。证据一：调试器读 PC 或看栈回溯，停在 `uart_getc` 的等待循环；证据二：逻辑分析仪看按键期间 LED 没有边沿，而松手后恢复。两个证据合起来才能排除"LED 任务自己写错"。
3. 3.299 s 是宿主事件表里阻塞版的最长单圈，5.47 ms 是行序对照里有 2 ms 采样时改良版的最长单圈；两者都来自宿主机上的 `probe.sh` 事件表，仓库没有日志与产物。它们是「来源说法(未复核)」，不是 F103/F407 板上实测。
4. 一位 8.6805 µs，一个字符 10 位 = 86.805 µs；40 个字符 = 3.472 ms。3.299 s 是阻塞版在长按静默段等 4200 ms 才到的下一个字节（901–4200 ms 没有字节），3.472 ms 是 40 个字符必须占用的线上时间；前者是等待，后者是传输。
5. 中位 1.49 ms 对 1.60 ms，区间 0.71–1.85 ms 对 0.41–5.24 ms，后者把前者整个包住，最大值还约为前者的 2.8 倍。行序只改平均启动时刻，不改最长单圈决定的上界，所以不是优先级。
6. 私栈（每个任务独立的调用栈与局部变量）、TCB（身份、状态、优先级、栈顶指针）、PendSV 切换（保存/恢复现场）。成本是每任务一个栈加一个 TCB，队列、信号量、定时器再从 heap 池子里切；切换本身也有开销。
7. 任务数值大者先：KEY=2 先于 LED/UART=1，idle=0 最后。NVIC 数值小者急：0 最急，5 是 FromISR 起点，15 最缓。两套编号方向相反，不能直接比大小。
8. 约束是 NVIC 逻辑优先级 ≥5。`0x50` 是 `5 << (8-4)` 的 8 位 IP 原始值，十进制 80；80 是原始值，不是逻辑值。NVIC 逻辑优先级只有 0–15，把 80 当逻辑阈值会写出无法配置的比较。
9. SysTick 给内核 1 kHz，HAL 时基改 TIM4。两个都用 SysTick 时，HAL 的计数没人推进或处理函数被内核接管，`HAL_Delay` 会卡住。共用时要核对处理函数、频率与调度器启动前后的行为，不能只替换其中一个处理函数。
10. `vTaskDelay(n)` 从调用时刻再等 n 个 tick；调用可能落在 tick 边界后的任意位置，1 kHz 下 `vTaskDelay(1)` 的等待落在 (0,1] ms。固定周期用 `vTaskDelayUntil`，以上次计划唤醒点为锚；实际入口仍有抖动或超期。
11. 128 字 ×4 B = 512 B。F103 根书例程是 128/192/256 字 = 512/768/1024 B；F407 lab 场景 1 是 256/256/320 字 = 1024/1024/1280 B。两个工程的任务与配置不同，数字不能互换。
12. 水位用 `uxTaskGetStackHighWaterMark()`，返回剩余最小空闲字数；溢出检查用 `configCHECK_FOR_STACK_OVERFLOW=2`，创建任务时用 0xA5 填充栈，溢出时检查栈尾模式并调用 `vApplicationStackOverflowHook`。
13. 池子覆盖动态创建的任务栈、TCB、队列、信号量、定时器等。F103 根书例程 10240 B；F407 lab 16 KiB = 16384 B。池尽时 `xTaskCreate` 返回负的错误码 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`（-1），不是 `pdFAIL`(0)；判断用 `!= pdPASS`。
14. `ΣWCET ≤ min(T)`：所有任务的最坏执行时间之和必须塞进最短周期，否则同时就绪时至少有一个任务错过期限。平均利用率低不代表最坏时刻不超期；三个任务同时就绪时，和可能超过最短周期。
15. 不该上：固定周期轻松跑完、没有硬期限、RAM 吃紧、其实只有一件事只是比较长。该上：硬实时、任务独立且周期不同、有等待但不想拖垮别人。判据：裸机管顺序，RTOS 管期限。
16. 根书引 FreeRTOS V11.3.2；lab 与本章的源码行号与宏语义按 V11.1.0 对账，V11.3.2 与 V11.1.0 两版行号不混排。混排会把不同版本的宏语义与行号错配，排障时对不上源码。
17. 第 22 章展开 TCB、就绪表与调度器；第 23 章展开 PendSV、软硬栈帧与 `ARM_CM3`/`ARM_CM4F` 移植。本章只回答"要不要上、先算什么"，不展开内核实现。
