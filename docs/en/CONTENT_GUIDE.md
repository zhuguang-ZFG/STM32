# Content style guide (required reading for contributors)

> 中文：[内容风格指南（贡献者必读）](../CONTENT_GUIDE.md)

This repo is an **STM32 textbook for learners who read Chinese**, from zero background up to building a project. It is organized the way [WaytoAGI](https://github.com/waytoagi/WaytoAGI) is organized:
a portal home page, chaptered lessons, visuals (animation, diagrams, board drawings), runnable code, and cheatsheets.

A reader may be a high-school student touching a circuit for the first time, or an engineer looking up a register. This file is the English edition of the guide. Please follow the rules below so the book works for both.

## 1. Files and names

- Chinese chapters live in `docs/`, named `NN-中文标题.md` (NN is two digits, for example `05-定时器与PWM.md`).
- English chapters live in `docs/en/`. Their names are the slugs in [contents.md](contents.md), for example [`05-timer-pwm.md`](05-timer-pwm.md).
- Example code lives in `examples/<module>/`. Each example directory contains `README.md` and `main.c` (a `Makefile` is optional).
- Chinese cheatsheets live in [`../../cheatsheets/`](../../cheatsheets/). English cheatsheets live next to these chapters: [`cheatsheets/hal.md`](cheatsheets/hal.md), [`cheatsheets/registers.md`](cheatsheets/registers.md), [`cheatsheets/bus-and-pins.md`](cheatsheets/bus-and-pins.md), [`cheatsheets/errors.md`](cheatsheets/errors.md).
- Images always use a **relative path**. From a chapter in `docs/en/`, that is `../../assets/animations/gpio-blink.svg`. Chinese chapters in `docs/` use `../assets/animations/gpio-blink.svg`.

## 2. The fixed skeleton of every chapter

The skeleton has two parts. The first part teaches, in the order a newcomer learns. The second part is the deep part, which pins the conclusions to one part number and one manual. A first-time reader can start the labs after the first part and come back for the second.

```markdown
# NN Title

> One sentence on what this peripheral or topic is for (40 words or fewer).

<p align="center">
  <img src="../../assets/animations/xxx.svg" width="760" alt="xxx animation">
  <br><sub>▲ Animation: xxx (vector drawing by the author)</sub>
</p>

## Learning goals
Before this chapter: which chapters and which basics it needs (send a newcomer to "Zero-background primer" in chapter 00).
- [ ] Goal 1: something the reader can do and check after the chapter
- [ ] Goal 2

## Core ideas
**In one sentence: ...**

### An analogy first
One everyday analogy. The last sentence says where the analogy stops.

### 1. The first subsection
Order the subsections from easy to deep: what it is and why, then how to set it up, and only then registers and manual numbers.

## Hardware and wiring
| Board | Peripheral | Pin | Notes |
| --- | --- | --- | --- |
Then one `text` wiring diagram.

## Code
Complete HAL code that builds, followed by "Piece by piece", then a register or LL counterpart. The full project is under `../../examples/...`.

## Hands-on labs
1 to 3 labs, easy then harder. Each lists "Expected / How to check / If it fails, check first".

## Self-test
3 to 5 questions, followed by answers. Show the arithmetic for calculations.

## Recommended videos
Generated by `tools/gen_video_links.py`; do not edit by hand.

## Principle and scope
> [!NOTE]
> The deep-part lead (see below).
Pin the conclusion to one orderable part, one clock, and one manual revision; say which sentence stops holding when the family changes.

## Key figures
A figure drawn for this book, a caption that names its sources, and one plain paragraph on what the figure shows.

## Timing and state
One timing table or state table you can calculate back from. If there is no electrical timing, write the state transitions, and do not leave the heading empty.

## Pitfalls and sources
| Symptom | Cause | What to do | Source | What the source supports |
| --- | --- | --- | --- | --- |

## Related resources
- The official reference-manual chapter, the datasheet chapter, and links to related chapters
```

A few more rules:

- If a chapter has `<!-- video: -->` … `<!-- /video: -->`, it follows the opening animation. A script writes the narration; do not edit it by hand. The skeleton above does not include the narration script or the `<!-- video: -->` comment.
- The first lines of "Principle and scope" are always this callout:

  ```text
  > [!NOTE]
  > From this section to "Pitfalls and sources" is the deep part. It pins the conclusions above to one part number, one manual section, and numbers you can recompute. On a first read you can skip it and come back after the labs.
  ```

- Each row of "Pitfalls and sources" states one claim. The source cell is a link to `#source-{id}`, where `{id}` is an id already listed under `sources` in both manifests; after the build it points at the Appendix E card `id="source-{id}"`. The last column says which part of the claim that source actually supports. Leave out what it does not support.
- "Pitfalls and troubleshooting" is no longer a skeleton heading. Every pitfall goes into "Pitfalls and sources"; do not keep two names.
- "Recommended videos" lists only public Bilibili or YouTube videos that have been checked. The data lives in `stm32-book/video-links.json`, and every entry records when and how it was checked. A video is not a source card: it does not go into the manifest `sources`, and the numbers in the text still come from the manuals.
- From chapter 20 on, the tool, board-map, and pin chapters have no four-part deep section and follow their own structure, but they still need learning goals, a self-test, and recommended videos.

## 3. How to write

1. **Easy to deep.** Each chapter first says what a thing is and why it exists, then how to set it up and write it, and only then the manual details. Explain a term where it first appears: the full name, then one plain sentence on what it does.
2. **An analogy first, then the real thing.** Core ideas opens with an everyday analogy, and its last sentence says where the analogy breaks. The analogy builds intuition; never derive a conclusion from it.
3. **Conclusion first, then the mechanism.** The first sentence of each section is something you can use immediately.
4. **Every number has a home.** Electrical values, timings, addresses, and register bits name the manual, the table or section, and the revision they come from. Mark a rule of thumb as a rule of thumb and an example setting as an example setting; do not pass either off as a manual number.
5. **Tables come with words.** Say at least one sentence before or after a table about how to use it. Do not stack three tables in silence. Parameters, register bits, and trap checklists still belong in tables.
6. **Match words to pictures.** Every animation or diagram the text mentions appears once in the chapter, with a `<sub>` caption.
7. **Code must compile.** Samples are real HAL you can build (the `HAL_` prefix), with the headers, `main()`, and the comments you need. Do not write pseudocode. Parameters are macros, so there are no magic numbers. After the code, a "Piece by piece" list explains the key lines.
8. **Labs can be checked.** Each lab says what you should see, how to confirm it (a stopwatch, a multimeter, a logic analyzer, serial output), and where to look first when it fails.
9. **Self-tests come with answers.** Answers show the arithmetic and the reason, so a reader can see which step went wrong.
10. **Label the pictures honestly.** Every figure in this repo is an **author-drawn vector (SVG) or a program-generated GIF**, not a vendor photograph. If you want a photograph, link the official product page (in a "Board and documents" subsection). Do not call a drawing a photograph. The chapter videos are program-generated frames, not filmed footage.
11. Use the same words: `GPIO`, timer (`TIM`), interrupt (`IRQ`), `DMA channel`, `HAL / LL / registers`.
12. Line width is not limited. Do not use an HTML `<script>`, and do not use images hosted off-site (GitHub's proxy will fail).
13. **Voice.** Write by [`.claude/skills/plain-voice/SKILL.md`](../../.claude/skills/plain-voice/SKILL.md). No emoji in headings or text; callouts are `> [!NOTE]`, `> [!TIP]`, and `> [!WARNING]`. Run `python -X utf8 tools/slop_lint.py` before you commit. When you rewrite a whole section or chapter, also run the vendored sepia skill: review first, then a minimal refactor, as "The second pass: sepia" in the same SKILL describes.
14. **Chinese and English move together.** When a Chinese chapter changes a fact, a number, or its structure, the English chapter in `docs/en/` changes in the same commit.

## 4. Visual-asset inventory (generated by scripts under `tools/`; do not edit the files by hand)

See [`../../assets/README.md`](../../assets/README.md). A chapter may cite only filenames that are already on that list. If you truly need a new figure, say so in an issue or a pull request, or generate it with [`../../tools/svgkit.py`](../../tools/svgkit.py) and then cite it.

## 5. Commit style

```text
docs(05): add the PWM duty-cycle formula and the breathing-LED animation
fix(gif): fix led-blink.gif timing so it matches the 1 Hz note
```

One commit does one thing. For images, especially GIFs, check that the file is under 500 KB.
