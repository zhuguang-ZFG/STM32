# 嵌入式 C 的内存模型与指针

> 在电脑上，数组越界换来的是一个段错误弹窗；在单片机上，越界的那次写可能落在隔壁外设的寄存器上，电机转一下，没有弹窗。本章把变量的住址、初值的来路和指针的宽度算清楚。

## 本章罗盘

- **问题**：`int g_init = 5;` 上电后为什么能读到 5，而 RAM 里原本并没有这个 5？为什么给一张 256 字节的表加上 `const`，它就从 RAM 里消失？为什么 `int *p` 的 `p + 1` 不是加 1 字节？三个问题分别指向段的分工、初值的搬运和指针的步长。
- **交付**：能用 `size`、`nm`、`readelf`、`objdump` 四条命令查清任意变量的段归属、运行地址、存储地址与初值来源；能按“地址 + 宽度 + 纪律”读明白一条寄存器访问语句；能算 `const` 对 RAM 与 Flash 的账。
- **边界**：本章以 Cortex-M 裸机、无 OS 为前提，例子取自 F407 与 F103C8 的来源记录，不把这些数字当成其它型号的保证。具体型号的存储器容量、完整地址地图与时钟树放在[第 8 章][ch08]；`volatile` 的完整访问合同与未定义行为放在[第 2 章](./02-c-volatile-ub.md)；链接脚本与启动文件的逐行讲解放在[第 6 章](./06-linker-startup-map.md)；结构体与寄存器映射放在[第 3 章](./03-struct-abi-registers.md)。PC 宿主上量到的指针大小也不能直接搬回 MCU。
- **依据锚点**：C0《为什么嵌入式 C 是另一种 C》（`mcu/docs/c/00-c-in-mcu.md`）、C1《内存模型：一个全局变量的三段旅程》（`mcu/docs/c/01-memory-model.md`）、C2《指针：点灯公式的全部秘密》（`mcu/docs/c/02-pointer.md`）；根书第 02 章《芯片选型与存储器时钟》的存储器映射与容量段（`docs/02-芯片选型与存储器时钟.md` 第 4 节）；Cortex-M4 复位行为引 RM0090 第 12.2 节，F103 存储器映射引 RM0008 第 2 章，二者均转引自上述来源。

## 先做出来

这一节不需要开发板，只需要一套 `arm-none-eabi` 工具链和一份已经链接好的 ELF。目标只有一个：亲眼看到同一个变量有两个地址，且文件里只带了它的一部分。

先看一份没有带初值全局变量的固件。来源工程的 `mcu/code/stm32/00-blink` 构建后，`arm-none-eabi-size build/blink.elf` 记录如下：

```text
   text    data     bss     dec     hex filename
    660       0    1536    2196     894 build/blink.elf
```

`data 0` 说明这个点灯工程没有带初值的全局变量；`bss 1536` 主要是链接脚本预留的 1 KB 最小栈加 512 B 最小堆。点灯程序本身没有全局变量，这 1536 字节是给栈和堆占的位子。

再看一个带初值的对象。来源取证工程 `mcu/code/c/01-memory-model` 的 `mem_probe.c` 里，`int g_init = 5;` 和几个同伴一起编译链接后，三条命令给出下面三组输出：

```console
$ arm-none-eabi-nm -n --print-size build/mem_probe.elf | grep g_init
20000000 00000004 D g_init

$ arm-none-eabi-readelf -W -l build/mem_probe.elf | sed -n '/Program Header/,/Section to Segment/p'
  Type           Offset   VirtAddr   PhysAddr   FileSiz MemSiz  Flg Align
  LOAD           0x001000 0x08000000 0x08000000 0x002a0 0x002a0 R E 0x1000
  LOAD           0x002000 0x20000000 0x080002a0 0x0000c 0x0002c RW  0x1000
  LOAD           0x00002c 0x2000002c 0x080002ac 0x00000 0x00604 RW  0x1000

$ arm-none-eabi-objdump -s -j .data build/mem_probe.elf
Contents of section .data:
 20000000 05000000 01000000 68690000           ........hi..
```

三组输出说的是同一件事：

- `nm` 给出的 `20000000 00000004 D g_init` 是它出生后的住址：RAM 开头的第一个字，4 字节，`D` 表示住在 `.data` 段、全局可见。
- `readelf` 的第二条 `LOAD` 行把同一段东西拆成两个地址：`VirtAddr 0x20000000` 是运行时住的 RAM，`PhysAddr 0x080002a0` 是烧录时压着的 Flash；文件里只带 `FileSiz 0x0000c` 共 12 字节，RAM 里却要 `MemSiz 0x00002c` 共 44 字节。
- `objdump` 把那 12 字节的初值备份摊开：`05000000` 是 `g_init` 的 5，`01000000` 是 `g_flag` 的 1，`68690000` 是 `g_msg` 的 `"hi"` 加一个对齐填充字节。`.bss` 的对象一个都不在这里，它们的初值全是 0，存进 Flash 是纯浪费。

你自己的工程里，地址和大小会随链接脚本、对齐和对象数量变化；要看的形状是 VMA 落在 RAM、LMA 落在 Flash、`FileSiz` 小于 `MemSiz`。下面把形状背后的机制拆开。

## 机制

### 没有 OS 的世界

电脑上运行一个 C 程序，`main` 之前站着一整座运行时大厦：装载器把 ELF 映射进虚拟地址空间，动态链接器解析符号，CRT 初始化堆，最后才 `__libc_start_main → main`。程序崩溃时，内核送来段错误弹窗，进程尸体被收走，世界照旧。

单片机上没有这座大厦。上电那一刻，Cortex-M4 内核只做两件硬件规定的事（RM0090 第 12.2 节，具体值以你手上芯片的参考手册为准）：

1. 从 Flash 起始的向量表第 0 项取出初始栈顶地址，装进 MSP；
2. 从第 1 项取出复位处理函数 `Reset_Handler` 的入口地址，跳过去。

没有装载器、没有堆初始化、没有任何人替你准备 C 语言的运行前提。`Reset_Handler` 必须亲手做完三件事，`main` 里的第一行 C 才合法：

- 使能 FPU。复位后 CP10/CP11 默认关闭，浮点指令一碰就触发 UsageFault。
- 把 `.data` 段（有初值的全局变量）从 Flash 搬到 RAM。
- 把 `.bss` 段（无初值或零初值的全局变量）清零。

崩溃的形态也完全不同。越界写在 PC 上，内核通过 MMU 拦截，进程死给你看；越界写在裸机上，没有 MMU，写谁就是谁：写到隔壁外设的寄存器，电机可能真的转一下；写到向量表映射区，下一次中断就跳进荒野。内核唯一的兜底是 HardFault，一张没有弹窗、没有日志、只有调试器才看得到的死亡通知。

资源观也跟着变。F407ZGT6 的 SRAM 按 KB 计，来源工程给出的是 128 KB；一张未压缩的 320×240 灰度图就要 76.8 KB。栈默认 1 KB 起步，链接脚本给堆的最小预算只有 512 字节（`_Min_Heap_Size = 0x200`）。`malloc` 不是想用就能用：堆没有操作系统替你扩，碎片化了没有交换分区兜底；RAM 摆不下时链接器直接报错，把“运行时踩内存”提前成“链接期拒签”。

C 与硬件之间是一条直线。寄存器就是有名字的地址：GPIOF 的 BSRR 住在 `0x40021418`，`*(volatile uint32_t *)0x40021418 = 1UL << 22;` 编译出来就是一条 `str` 指令，高级语言到硬件之间没有中间商。那个 `volatile` 不是装饰，它是告诉编译器“每次都真去访存，不许缓存、不许合并、不许删”的合同条款；为什么是三条、边界在哪，[第 2 章](./02-c-volatile-ub.md)用反汇编逐条取证。

工具链则决定了你看待芯片的方式。你在 PC 上敲 `gcc hello.c`，编译器默认目标是本机；嵌入式里这句默认不再成立，你在 x86_64 的电脑上为一颗 Cortex-M4 产代码，这叫交叉编译。来源工程的四件套是：

| 角色 | 来源工程里的身份 | 决定什么 |
| --- | --- | --- |
| 编译器 | `arm-none-eabi-gcc` 15.2.1 | C→汇编→目标文件，`-mcpu=cortex-m4` 指明目标内核 |
| 链接器 | 同一驱动加 `-T stm32f407xx.ld` | 按链接脚本把 `.o` 拼成落在 `0x08000000` 的固件 |
| 二进制工具 | `arm-none-eabi-objcopy / objdump / size` | ELF 与 bin/hex 互转、反汇编取证、体量统计 |
| 烧录与调试 | OpenOCD、ST-Link、`arm-none-eabi-gdb` | 把 ELF 写进 Flash，从复位向量单步 |

同一份 C 源码，换一组 `-mcpu` 和链接脚本，就是另一颗芯片的世界。工具链的每一项配置都在替你回答：目标是谁、代码放哪、初值谁来搬、错了怎么看。

### 五段地图：Flash 存粮，RAM 住人

先看架构给的地址边界。Cortex-M 把 4 GB 地址空间固定划分为六段（根书第 02 章第 4 节）：

| 地址范围 | 区域 | 内容 |
| --- | --- | --- |
| `0x0000_0000–0x1FFF_FFFF` | Code | 别名到 Flash 或系统存储区，中断向量表 |
| `0x2000_0000–0x3FFF_FFFF` | SRAM | 片上 SRAM |
| `0x4000_0000–0x5FFF_FFFF` | Peripheral | 所有外设寄存器 |
| `0x6000_0000–0x9FFF_FFFF` | 外部 RAM | FSMC/FMC 扩展 |
| `0xA000_0000–0xDFFF_FFFF` | 外部设备 | 外部设备接口 |
| `0xE000_0000–0xFFFF_FFFF` | 系统 | NVIC、SysTick、SCB（PPB） |

这六段是架构边界，不是某一颗芯片的完整地图。来源里有两个能对账的例子：F103C8 的 Flash 是 64 KB、起始 `0x0800_0000`，SRAM 是 20 KB、起始 `0x2000_0000`；F407ZGT6 的 Flash 是 1024 KB、SRAM 是 128 KB，另有一块 64 KB 的 CCM 在 `0x1000_0000`，只有 CPU 能直接访问，DMA 够不着。具体型号把哪些外设放在 `0x4000_0000` 之后、时钟怎么配，[第 8 章][ch08]再展开。

链接脚本在 Flash 与 RAM 之上再切给 C 的对象。五段地图如下：

| 段 | 住哪 | 文件里有没有货 | 谁负责 |
| --- | --- | --- | --- |
| `.text` | Flash | 有，`PROGBITS` | 链接器排布 |
| `.rodata` | Flash（本工程并入 `.text`） | 有，`PROGBITS` | 链接器排布 |
| `.data` | RAM 本体，Flash 另存初值副本 | 有副本，`PROGBITS` | `Reset_Handler` 搬运 |
| `.bss` | RAM | 无，`NOBITS` | `Reset_Handler` 清零 |
| 堆与栈 | RAM | 无，`NOBITS` | 运行期生长 |

先记住 `.isr_vector`：它住在 `0x08000000`，来源工程里是 392 字节。Cortex-M 复位后先从这里第 0 个字取栈顶、第 1 个字取复位入口，这时候 C 运行时还不存在，`.data` 里一个变量都没就位。

- `.text` 放能执行的指令。来源工程的链接脚本把 `*(.rodata)`、`*(.rodata*)` 收进了 `.text` 输出段（`stm32f407xx.ld:48-49`）。功能完全正常，但“代码段只读、数据段另立”的边界就没了，后面看 `nm` 字母时会被它骗一次。
- `.rodata` 放只读常量和字符串字面量。本工程把它并进 `.text`，所以 `const int g_ro` 的符号字母是 `T`，地址却在 `0x08000298` 的 Flash 里。把 `.rodata` 单列重链，同一个符号字母变成 `R`，地址一格不动。字母说的是“在哪个输出段、什么属性”，不是“是函数还是数据”。
- `.data` 放有非零初值的全局变量。它必须同时住两边：RAM 里住本体，Flash 里住初值备份。这份“双重户籍”由链接脚本的 `>RAM AT> FLASH` 建立，`.data` 在 ELF 里的类型是 `PROGBITS`，因为文件里确实带着那 12 字节初值。
- `.bss` 放初值全零的全局变量，类型是 `NOBITS`，文件里一个字节都不给。它只是链接器给启动代码留的一张便条：这段 RAM 请你清零。`.bss` 不占 Flash，但照占 RAM。
- 堆与栈同住 `._user_heap_stack` 输出段，也是 `NOBITS`。来源工程按 `_Min_Heap_Size = 0x200` 加 `_Min_Stack_Size = 0x400` 预留下限；栈从 `_estack = 0x20020000`（RAM 顶）向下长，堆从 `_ebss` 之后向上长，中间是它们还没碰面的空地。

函数里的自动变量既不在 ELF 也不在段表，它在栈上，函数返回即蒸发。写在函数里的 `static` 变量例外：寿命全程序、可见性本文件，所以它有固定地址，`nm` 里是小写字母的局部符号。

### `int g_init = 5;` 的三段旅程

#### 第一程：源码里，它只是一行声明

```c
int g_init = 5;               /* 文件作用域，有初值 */
```

此刻它有三个信息：类型（`int`，4 字节）、初值（5）、存储期（全程序）。第三个信息决定了它后面所有的遭遇：全局变量的存储期要求编译器为它预先定址，不能像自动变量那样在运行时算。

#### 第二程：ELF 里，它有了“户口”和“仓库”两个地址

编译链接后先查门牌：

```console
20000000 00000004 D g_init
```

地址 `0x20000000`，RAM 开头第一个字节，字母 `D`。这是它出生后的住址，不是它出生前的所在地。出生前它在哪里，要看程序头：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| VirtAddr | `0x20000000` | VMA：运行时这段要在哪（RAM） |
| PhysAddr | `0x080002a0` | LMA：烧录时这段实际压在哪（Flash 尾部） |
| FileSiz | `0x0000c` | 文件里真有 12 字节 |
| MemSiz | `0x0002c` | RAM 里要 44 字节（`.data` 12 加 `.bss` 32） |

烧进 Flash 的固件里，`0x080002a0` 处躺着 12 个字节，它们是 `.data` 段的初值备份。把这份备份单独抠出来看：

```console
Contents of section .data:
 20000000 05000000 01000000 68690000           ........hi..
```

四个字节四个字节地读：`0500 0000` 是 `g_init` 的 5，`0100 0000` 是 `g_flag` 的 1，`6869 0000` 是 `g_msg` 的 `"hi"` 加一个对齐填充字节。正好 12 字节。`.bss` 的对象一个都不在这里，它们的初值全是 0，存进 Flash 是纯浪费空间，所以只在符号表里留个名字。

为什么 `VirtAddr` 和 `PhysAddr` 能不一样？链接脚本里两个词：

```ld
  _sidata = LOADADDR(.data);
  .data : {
    . = ALIGN(4);  _sdata = .;  *(.data)  *(.data*)  . = ALIGN(4);  _edata = .;
  } >RAM AT> FLASH
```

`>RAM` 说“运行时在 RAM”，定下 VMA；`AT> FLASH` 说“存储时在 Flash”，定下 LMA；`_sidata = LOADADDR(.data)` 把这个 LMA 变成一个符号交给启动代码。三个符号对上实测：`_sidata = 0x080002a0`（Flash）、`_sdata = 0x20000000`、`_edata = 0x2000000c`。

#### 第三程：上电瞬间，搬运工逐字拷进 RAM

`Reset_Handler` 的反汇编里，那几个 `.word` 就是链接脚本发下来的地址条：

```asm
 8000270:  20020000        @ _estack  → 装栈顶
 8000274:  e000ed88        @ SCB->CPACR → 使能 FPU
 8000278:  20000000        @ _sdata   → 拷贝目标起点
 800027c:  2000000c        @ _edata   → 拷贝目标终点
 8000280:  080002a0        @ _sidata  → 拷贝源起点（Flash！）
 8000284:  2000000c        @ _sbss    → 清零起点
 8000288:  2000002c        @ _ebss    → 清零终点
```

循环本体从 `0x080002a0` 读、往 `0x20000000` 写，跑 `(0x2000000c - 0x20000000) / 4 = 3` 圈，正好 12 字节。接着把 `0x2000000c..0x2000002c` 这 32 字节扫成 0。然后 `bl main`。`main` 里第一次读 `g_init` 拿到 5，靠的全是这 3 圈加 8 圈。

这就是“三段旅程”：源码声明，链接器分两个地址，启动代码搬运。三个环节缺一个，`g_init` 读到的就不是 5。

#### 回头清点：另外几个对象的归宿

- `int g_zero = 0;` 在 `.bss`，不在 `.data`。它明明写了初值，但 GCC 一看初值是 0，“清零”这件事 `.bss` 顺手就办了，何必占 Flash 四个字节再拷一遍。判据是“初值是不是全零”，不是“有没有写等号”。
- `volatile int g_flag = 1;` 照样在 `.data`。`volatile` 不改住址，只改访问方式：它管的是“每次都要真访存”，跟“住在哪”是两个正交的问题。
- 函数里的 `static uint8_t s_local[8]` 在 `.bss`，字母 `b`；同一个函数里的 `int auto_var = 3;` 连符号都没有，`nm` 查无此人。它活在栈帧里，链接期根本不存在。
- `const int g_ro` 的地址是 `0x08000298`，在 Flash 里，`nm` 的字母却是 `T`。原因就是链接脚本把 `.rodata` 并进了 `.text` 输出段。同一行代码里，字符串字面量 `"flash"` 住在 `0x08000290` 的 Flash，指向它的指针 `lit` 却是自动变量，活在栈上：字符串和指针分住两种介质。

### `const` 的 RAM 经济学

一张 256 字节的查找表，两种写法，各编译一次。来源 `lut_probe.c` 的实测值，一张表就值一个词：一个 `const` 换 256 字节 RAM。

| 写法 | `.text` | `.data` | `lut` 的 `nm` 行 | 第二个 LOAD 段 |
| --- | --- | --- | --- | --- |
| `uint8_t lut[256] = {1,2,3};` | 148 | 256 | `20000000 00000100 D lut` | `VirtAddr 0x20000000 PhysAddr 0x0800021c FileSiz 0x100 MemSiz 0x700` |
| `const uint8_t lut[256] = {1,2,3};` | 404 | 0 | `0800021c 00000100 T lut` | `VirtAddr 0x20000000 PhysAddr 0x0800031c FileSiz 0x00000 MemSiz 0x600` |

三个数对着读：

- **RAM 从 256 字节变成 0 字节**。`.data` 那一列从 256 塌到 0，第二个 LOAD 段的 `FileSiz` 从 `0x100` 变成 `0x00000`，Flash 里不再需要为它存备份，启动代码也少拷 64 个字。一个 `const` 换 256 字节 RAM，这笔交易的金额由表的大小和你的 RAM 总量决定：在 128 KB 的 F407 上不算什么，在 RAM 只有几十 KB 的小型号上就是两位数的家底。
- **Flash 从 148 涨到 404**。`.text` 多出 256 字节，表还在，只是只住 Flash 了。所以“加 const 省一半”的说法要看口径：省的是 RAM 那一半，Flash 那一半本来就要花，初值也得存。
- **`MemSiz` 从 `0x700` 降到 `0x600`**。可写版的 `MemSiz` 是 256 字节 `.data` 加 `0x600` 的堆栈预留；只读版只剩堆栈预留。链接器的 RAM 记账直接少了一笔。

为什么 `const` 数组该留 Flash：查表是只读行为，从 Flash 读和从 RAM 读，Cortex-M 都支持直接寻址，结果一模一样；差别只在访问速度。Flash 有等待周期，RAM 没有，具体差多少取决于 `FLASH_ACR` 的配置与主频，本章不填数字，[第 8 章][ch08]算这笔时间账。用一点访问延迟换整块 RAM 归还，是嵌入式里最划算的一笔常规交易。

反过来，什么时候 `const` 不该乱加？表要被运行时改写（比如自动校准出来的补偿表）就不能 `const`，只能用 `__attribute__((section(".data")))` 或者干脆普通全局；`const` 数组想“存初值 + 运行时改”，就得自己写“从 Flash 模板拷一份到 RAM 工作区”的两段式，这正是[第 17 章][ch17]里出厂参数的标准做法。[第 2 章](./02-c-volatile-ub.md)会展开 `const` 的语义细节、它与 `volatile` 的组合以及相关未定义行为。

### 指针：地址、宽度、步长

先拆一条点灯语句：

```c
*(volatile uint32_t *)0x40021418 = 1UL << 22;
```

从右往左读：

| token | 人话 |
| --- | --- |
| `0x40021418` | 门牌号：GPIOF 基址 `0x40021400` 加 BSRR 偏移 `0x18` |
| `(volatile uint32_t *)` | 给裸地址装上类型：32 位宽的钥匙，加 `volatile` 的叮嘱 |
| `*` | 解引用：这一次真的要登门访存 |
| `= 1UL << 22` | 一次 32 位写：BSRR 高 16 位的 BR6，PF6 拉低，红灯亮 |

指针从来只管三件事：地址、宽度、纪律。地址定位置，类型定宽度，`volatile` 定纪律。

类型定宽度不是修辞，是指令层面的分叉。来源 `probe.c` 用 `arm-none-eabi-gcc -std=c11 -Wall -Wextra -O2 -mcpu=cortex-m4 -mthumb -S` 编译，六个函数的汇编是：

| 指向类型 | 读指令 | 写指令 | `p + 1` 的地址增量 |
| --- | --- | --- | --- |
| `uint8_t *` | `ldrb` | `strb` | +1 字节 |
| `uint16_t *` | `ldrh` | `strh` | +2 字节 |
| `uint32_t *` | `ldr` | `str` | +4 字节 |

后缀即宽度：`B` 是 8 位字节，`H` 是 16 位半字，无后缀是 32 位字。同一个 `*p`，类型换了，生成的指令就换。F407 的 GPIO 寄存器全是 32 位，所以点灯宏一律用 `uint32_t`；你若用 `uint16_t *` 去写 BSRR，编出来是 `strh`，只写低 16 位，高 16 位的复位区根本够不着。若值写成 `1U << 22`，截成 16 位后是 0，这一行实际往低 16 位写 0，什么都不会发生。

指针声明也有读法。先找到变量名 `p`，从 `p` 向右看有没有 `[]` 或 `()`；没有就向左走，每遇到一个 `*` 记一层指针，遇到 `const` 或 `volatile` 就看它贴在 `*` 的哪一边。`volatile uint32_t * const p` 里，`const` 贴在 `p` 这一侧，锁的是指针；`volatile` 贴在 `uint32_t` 这一侧，锁的是目标。`const uint8_t *p` 则相反，`const` 锁目标，指针可以改指。口诀是“从右往左念，`const` 锁左边最近的那个”：

| 写法 | 锁住的 | 放行的 |
| --- | --- | --- |
| `const int *p`（同 `int const *p`） | `*p = x`，透过指针改目标 | `p = &b`，换指向 |
| `int * const p` | `p = &b`，换指向 | `*p = x`，改目标 |
| `const int * const p` | 全锁 | 只能读 |

三条越界全部在编译期拦截，来源宿主上用 gcc 16.1.0 跑出三条 `assignment of read-only` 错误；合法半边真跑通过。`const` 不要钱，跑都不用跑，错在编译期就死了。驱动里满街是 `volatile uint32_t * const`：指针本身锁死，这个句柄永远指向 GPIOF，不许被改去指别人；目标保持 `volatile`，硬件会绕过 CPU 改它。两个限定词各管一件事，叠在一起恰好是寄存器句柄的完整语义。

步长的真相在汇编里。C 标准把 `p + 1` 定义为前进一个指向对象，不是前进一个字节，编译器干脆把步长折进寻址偏移：

```asm
next8:                          next16:                         next32:
        ldrb    r0, [r0, #1]            ldrh    r0, [r0, #2]            ldr     r0, [r0, #4]
        bx      lr                      bx      lr                      bx      lr
```

对 `uint32_t *p`，`p + 1` 加 4 字节；对 `int *p` 同理，Cortex-M 上 `int` 是 4 字节（`g_init` 的 `00000004` 就是对账）。宿主侧真跑的输出是 `sizeof: uint8_t=1 uint16_t=2 uint32_t=4`，同一份输出里指针自身 8 字节，那是 x86-64 宿主的口径，不能搬回 Cortex-M。指针自身多大由目标 ABI 决定，本章只谈它指向对象的宽度。

这一步直接通往寄存器块的索引写法：

```c
((volatile uint32_t *)0x40021400)[6]   /* 地址 = 0x40021400 + 6×4 = 0x40021418 = BSRR */
```

`6 × sizeof(uint32_t) == 0x18` 这条等式用 `_Static_assert` 锁死在 `probe.c` 里，随每次编译校验。更硬的证据在汇编：索引写法与宏写法编出逐字节相同的机器码，编译器把最终地址 `0x40021418` 拆成“字面值 `0x40021000` 加 12 位偏移 `1048`”：

```asm
        str     r2, [r3, #1048]        @ 0x40021000 + 0x418 = 0x40021418
```

两种 C 写法零差别，选哪个是风格问题，不是正确性问题。`p + 6` 与 `(char *)p + 6` 就不同了：前者是 `0x40021418`，后者是 `0x40021406`。单位是指向对象，不是字节。

野指针三宗罪，来自同一份来源的代码分析：

1. **HardFault**：访问了不存在的地址，比如未使能时钟的外设区、保留区、越出存储映射。总线错误升级成 HardFault，当场死给你看，这是最好的一种。
2. **静默改写**：地址合法但指错了对象，写穿到隔壁变量、别的外设寄存器。没有任何异常，系统在几天后、另一个看似无关的功能里爆雷，排查成本以天计。
3. **碰巧能用**：最可怕的一种。野到的内存当前恰好无害，功能“正常”，换优化档、换芯片、加一行代码才复发。运气不是设计。

来源工程里还有个细节值得记住：宿主运行只敢对 `0x40021400` 取地址做算术，从不敢解引用，因为那个地址在 Windows 宿主上摸不得。“合法的 C 指针值”与“可访问的地址”是两回事，指针合法性的最终裁判是存储映射，不是编译器。防御纪律就三条：指针必先初始化再使用；地址常量集中在一处定义，别满篇魔法数；需要按地址打印或存储时用 `uintptr_t`，需要表偏移差用 `size_t` 或 `ptrdiff_t`。

## 测量与证据

本章的数字都来自来源记录：C0、C1、C2 的工具链实测，以及根书第 02 章的存储器映射与容量。工具链是 xPack `arm-none-eabi-gcc 15.2.1`，编译参数 `-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard -O0 -g3`，链接 `-T stm32f407xx.ld`。你的构建会因版本、优化档和链接脚本不同而变化，判读方法不变。

四条命令可以回答大部分关于“它住在哪、花多少”的问题：

| 想知道 | 命令 | 来源实测里看哪一行 |
| --- | --- | --- |
| 每段多大、住在哪 | `size -A build/mem_probe.elf` | `.data 12 / .bss 32 / ._user_heap_stack 1540` |
| 某个变量住哪个段、几个字节 | `nm -n --print-size build/mem_probe.elf` | `20000008 00000003 D g_msg`（3 字节，不是 4） |
| 文件里到底有几字节货 | `readelf -W -l build/mem_probe.elf` | 第二 LOAD 行 `FileSiz 0x0000c / MemSiz 0x0002c` |
| 初值备份长什么样 | `objdump -s -j .data build/mem_probe.elf` | `05000000 01000000 68690000` |
| 谁在拷它 | `objdump -d build/mem_probe.elf`，找 `Reset_Handler` | 字面量池里 `080002a0` |
| 全工程最大对象是谁 | `-Wl,-Map=...` 产出的 map 文件 | `.bss` 段最大项是 `s_buf` 16 字节 |

`nm` 的字母表要背下来，但别把它当段名：

| 字母 | 含义 | 本章实例 |
| --- | --- | --- |
| `T`/`t` | 代码段（含本工程并入的 `.rodata`） | `T probe`、`T g_ro`（数据！） |
| `D`/`d` | `.data`（有非零初值） | `D g_init` |
| `B`/`b` | `.bss`（零初值） | `B g_zero`、`b s_buf` |
| `R`/`r` | 只读段 | `R _estack`、`r g_pfnVectors` |
| `A` | 绝对值符号（不是地址，是常量） | `A _sidata`、`A _Min_Heap_Size` |
| `W`/`w` | 弱符号 | `W Reset_Handler` |

两条读表纪律：

1. **字母会骗人，地址不会。** 判断“占 Flash 还是占 RAM”唯一可靠的依据是地址前缀：`0x0800xxxx` 是 Flash，`0x2000xxxx` 是 RAM。`g_ro` 顶着 `T` 却住在 Flash，就是 `.rodata` 并入 `.text` 的直接后果。先查链接脚本，再下结论。
2. **`nm` 的总和不等于固件大小。** `size -A` 里的 `.debug_*` 是调试信息，`objcopy -O binary` 之后全部蒸发。来源工程的 `size -A` Total 是 26775，而真正进 Flash 加 RAM 的只有 `392 + 280 + 12 + 32 + 1540 = 2256` 字节。想知道烧进去多少，用 `.bin` 的文件大小，或者挑那五行加总。

`_Min_Stack_Size` 那 1 KB 是链接期下限检查，不是运行期上限：链接时 RAM 剩余装得下 `._user_heap_stack` 就放行，运行期栈真溢出它不管。来源工程实测预留段跑到 `0x20000630`，离 `_estack = 0x20020000` 还有约 126.5 KB 空地。想把这个数变成硬约束，得自己在链接脚本加 `ASSERT`，见[第 6 章](./06-linker-startup-map.md)。

有板的人可以再加一道复核：GDB 里 `p &g_init` 与 `p _sidata`，一个应落在 `0x2000xxxx`、一个应落在 `0x0800xxxx`；`set g_init = 99` 后 `monitor reset` 再读，预期值回到 5，因为 Flash 里的备份没动。这一步需要接板和 ST-Link，本章的工具链证据不依赖它。

## 失败分支

| 现象 | 原因 | 区分证据 | 下一动作 |
| --- | --- | --- | --- |
| 以为 `int x = 0;` 在 `.data` | 初值全零，链接器把它放进 `.bss` | `nm` 给 `B`/`b`，不是 `D` | 按“初值是否全零”判断，不按有没有写 `=` |
| 以为 `.bss` 不占空间 | 它不占 Flash，但照占 RAM | `size -A` 的 `.bss` 行 | 大缓冲先算 RAM；需要硬约束就在链接脚本加 `ASSERT` |
| 全局变量初值全是随机值 | 删掉或写错 `.data` 的 `AT> FLASH`，LMA 与 VMA 相同 | `readelf -l` 第二 LOAD 行的 `PhysAddr` | 恢复 `AT> FLASH`；确认 `_sidata = LOADADDR(.data)` |
| 偶发读到垃圾全局变量 | 中断在 `Reset_Handler` 搬完 `.data` 之前就被使能 | 启动文件里拷贝循环与开中断的先后 | 外设初始化放到 `main` 之后，别塞进启动文件搬运前 |
| `T g_ro` 被当成函数 | `.rodata` 并进了 `.text` 输出段 | 地址在 `0x0800xxxx`，或单列 `.rodata` 重链后字母变 `R` | 先读链接脚本，再改代码 |
| 拿 `volatile` 当段归属开关 | `volatile` 只改访问方式，不改住址 | `volatile int x = 1;` 仍在 `.data` | 要换段用 `__attribute__((section(".xxx")))` |
| 大 `const` 表想运行时改 | `const` 对象不可写 | 编译期报只读赋值错误 | 改成 RAM 工作副本，启动时从 Flash 模板拷入 |
| BSRR 写了没反应或灯亮得下不来 | 指针类型太窄，`uint32_t *` 变成 `uint16_t *` | 反汇编是 `strh` 而不是 `str`；`1U << 22` 截成 0 | 寄存器访问一律用定宽 `uint32_t` |
| `p + 1` 被当成加一字节 | 指针加减的单位是指向对象 | 汇编里 `#1/#2/#4`，或 `p + 6` 与 `(char *)p + 6` 的差 | 要按字节走就转成 `char *` |
| `nm` 里找不到明明定义了的变量 | `-fdata-sections` 加 `--gc-sections` 删掉了无人引用的对象 | 链接 map 与 `nm` 对不上 | 加 `__attribute__((used))` 或写一个真实的引用者 |
| 把调试信息当固件体积 | `size -A` 的 Total 包含 `.debug_*` | `.bin` 大小或那五行加总远小于 Total | 报体积用 `.bin`，或按段加总 |

野指针的三种下场已经在机制一节拆过：HardFault、静默改写、碰巧能用。它们不是段归属问题，但排查时同样先找地址证据：先确认指针值落在哪个区间，再看那次访问的宽度，最后才怀疑业务逻辑。

## 离开检查

合上本章前，先回答这七个问题；答不上来的，回到对应小节找证据。

1. `int g_init = 5;` 的 5 在烧录文件里和上电后各在哪？谁搬的？
2. `int g_zero = 0;` 在哪个段？它的 0 是谁写的？
3. `volatile int g_flag = 1;` 在哪个段？`volatile` 改变了什么、没改变什么？
4. 256 字节的 LUT 加上 `const` 后，RAM、Flash、启动拷贝各变多少？
5. `uint32_t *p = (uint32_t *)0x40021400;` 时，`p + 6` 与 `(char *)p + 6` 各是多少？
6. 野指针三宗罪里哪一种最难排查？为什么？
7. `0x0800...` 与 `0x2000...` 前缀分别说明什么？`nm` 的 `T` 为什么可能是数据？

<details>
<summary>对照答案</summary>

1. 文件里在 Flash 的 LMA `0x080002a0` 处存着 `.data` 的初值备份；上电后 `Reset_Handler` 把它搬进 RAM 的 `0x20000000`，本例拷 3 个字。
2. 在 `.bss`。它的初值全零，不占 Flash 副本，由 `Reset_Handler` 在启动时现场清零。
3. 在 `.data`。`volatile` 改的是访问方式，要求每次真访存、不许缓存合并删除；它不改变变量的段归属和地址。
4. RAM 从 256 字节变 0，Flash 的 `.text` 从 148 涨到 404（多 256 字节），启动拷贝少 64 个字；`MemSiz` 从 `0x700` 降到 `0x600`。
5. `p + 6` 是 `0x40021418`（6×4 字节），`(char *)p + 6` 是 `0x40021406`。单位是指向对象的大小。
6. “碰巧能用”。它没有当场异常，功能看起来正常，换优化档、换芯片或改一行代码才复发，没有稳定的失败信号可追。
7. 前缀 `0x0800` 是 Flash，`0x2000` 是 RAM；`T` 说的是符号落在 `.text` 输出段，本工程把 `.rodata` 并了进去，所以数据也可以顶着 `T`。判断介质看地址前缀。

</details>

动作验收：在自己的工程上跑一遍 `size`、`nm`、`readelf`、`objdump`，找出一个 `.data` 对象和一个 `.bss` 对象，记录它们的 VMA、LMA、`FileSiz` 与 `MemSiz`；再给一张至少 64 字节的只读表加上 `const`，重新链接一次，比较 `.data` 与 `.text` 两列的变化。
