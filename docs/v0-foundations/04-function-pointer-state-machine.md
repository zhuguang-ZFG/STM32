# 函数指针、状态机与调用约定

> 中断到来时，硬件只做一件事：从向量表里取出一个地址跳过去。跳过去之后，参数在哪、局部变量住哪、函数怎么回来，全部由 AAPCS 说了算。本章把“跳过去”和“跳过去之后”接起来：函数指针、状态机、环形缓冲，以及一次函数调用的栈账。

## 本章罗盘

- **问题**：`void (*table[8])(void)` 到底怎么读，`typedef` 改了什么？为什么说向量表就是 Flash 里的函数指针数组？`fsm_feed` 里一行查表调用，编译出来是什么？环形缓冲的读写指针相等时，到底是空还是满？函数指针跳过去之后，前四个参数凭什么正好在 r0–r3、第 5 个凭什么在栈上、局部变量凭什么随 sp 自动回收？中断服务函数为什么必须写成 `void f(void)`？
- **交付**：能读、能写函数指针声明与 `typedef`；能把“串口命令解析”落成状态×事件的动作表；能为环形缓冲选定满/空规则并说清容量代价；能拿 `-O2` 汇编指出参数落位、栈帧大小与返回地址位置；能按向量表槽位写出签名正确的 ISR，并说清它为什么只做记账。
- **边界**：本章的逐条汇编取证来自 Cortex-M4（F407 目标）与宿主 x86-64 两套产物；F103 侧只取根书第 04 章的 ISR 签名与“只置标志”写法，没有对应的逐条汇编对照。AAPCS 规则可跨 ARM Cortex-M 复用，但具体指令形状、向量表大小与硬浮点寄存器不搬运。NVIC 优先级、EXTI 通道与寄存器细节留给[第 10 章][ch10]；寄存器、时钟与引脚差异指向卷 4 的[第 28 章](../v4-platforms/28-chip-migration-differences.md)与[第 29 章](../v4-platforms/29-gd32-arm-riscv.md)。共享变量的 `volatile` 合同见[第 2 章](./02-c-volatile-ub.md)，结构体布局与寄存器映射见[第 3 章](./03-struct-abi-registers.md)。
- **依据锚点**：C5《函数指针、状态机与环形缓冲》（`mcu/docs/c/05-func-pointer.md`）；C6《调用约定与栈帧》（`mcu/docs/c/06-abi-stack.md`）；根书第 04 章《中断与 NVIC》（`docs/04-中断与NVIC.md`）的驱动基本功与中断服务函数签名部分；AAPCS 条款与 PM0056 的 NVIC 章节均转引自上述来源。

## 先做出来

这一节不需要开发板，只需要一个宿主 `gcc`。两个取证工程各跑一条命令：先看函数指针与状态机的行为断言，再对一次函数调用的栈账。

```bash
cd mcu/code/c/05-func-pointer
sh probe.sh
cd ../06-abi-stack
sh probe.sh
```

跑之前押两个数字：8 格物理容量的环形缓冲，A 派（牺牲一格）与 B 派（单调索引）各能存几笔？非叶子函数只开了一个 `buf[16]`，它在 Cortex-M4 上的一帧是多少字节？第一个问题对着 05 的输出第二行看，第二个对着 06 的交叉汇编找 `push {r4, lr}` 与 `sub sp, sp, #16`。

05 的关键输出：

```text
== 断言通过 560/560 ==
环形缓冲容量对照：A 派（牺牲一格）可用 7 格，B 派（单调索引）可用 8 格
```

工具链在 `PATH` 时，反汇编段会出现两次间接调用，这就是函数指针在机器码层面的样子：

```text
94:  9e:	4798		blx	r3
133:  22:	4798		blx	r3
```

06 的关键输出（宿主 gcc 16.1.0 实测，每条都是真跑出来的数）：

```text
一帧吃掉的栈          = 64 字节（两次 sp 之差，含返回地址+保存寄存器+buf）
buf 距 sp(non_leaf)   = 32 字节
sum6(1,2,3,4,5,6)     = 21（第 5、6 个参数 5、6 是走栈送进去的）
add64(0x100000000, 0x200000001) = 0x300000001（64 位结果走寄存器对回来）
== 断言通过 9/9 ==
```

64 字节是宿主编译器的一帧；同一个 `non_leaf` 编到 Cortex-M4 是 24 字节。字节账随目标与编译器而变，机制不变：**sp 一根指针的移动，就是局部变量分配与释放的全部成本**。

## 机制

### 声明阅读法：从名字出发，先右后左

`probe.c` 里三种声明指向同一类东西：

```c
typedef void (*cb_t)(void);        /* cb_t = “指向 void(void) 函数的指针”这个类型 */
static cb_t key_table[8];                          /* 8 个函数指针 */
static void (*pick_raw(int id))(void);             /* 函数返回函数指针：裸写法 */
```

右左法则读 `void (*table[8])(void)`：从名字 `table` 出发，**先右**看到 `[8]`，说明 `table` 是数组；**再左**看到 `*`，说明元素是指针；**再右**看到 `(void)`，说明指针指向函数；**再左**看到 `void`，说明函数返回 `void`。合起来：`table` 是“8 个元素的数组，元素是返回 void 的无参函数的指针”。

`typedef` 只是给这个类型起名，不改语义。`probe.c` 用一条断言把两种写法等价钉住：

```c
cb_t via_typedef = on_press;
void (*via_raw)(void) = on_press;   /* 两种写法指向同一对象 */
CHECK(via_typedef == via_raw);
```

编译期还钉死了尺寸：`_Static_assert(sizeof(key_table) == 8 * sizeof(cb_t), ...)`；`nm` 显示 `key_table` 占 `0x20` = 32 字节，正好 8 × 4。类型不匹配的代价要在后面单独说：`void (*)()` 与 `void (*)(void)` 在旧代码里不是一回事，差一个参数就是未定义行为，编译器未必报警。

### 向量表：Flash 里的函数指针数组

回看四步构建里 `.isr_vector` 那 392 字节：它就是一个 `const` 函数指针数组，存在 Flash 起始处。启动文件里的每一行

```asm
.word EXTI0_IRQHandler
```

都是在表里填一个地址。`Reset_Handler` 是 `W`（弱符号），含义是“表里那个槽默认指向这里，你可以覆盖”：**弱符号 = 可被覆盖的函数指针槽位**。

所以“注册中断服务函数”这件事，在 C 层面根本不需要 API：你写出同名函数，链接器就把表里那格重定位到你函数的地址。这里没有类型检查兜底：表是汇编里的 `.word` 列表，链接器只认符号名，不认 C 的函数类型。签名对不对，靠本章后半程的调用约定纪律，不靠编译错误。

调用返回地址、参数与栈帧的规则，来自后面的 AAPCS 一节；向量表只负责“跳到哪”，跳过去之后的一切由调用约定接管。

### fsm_feed：状态×事件→动作表

![查表法状态机：状态×事件查表取出函数指针](/figures/c-05-fsm-table.svg)

`probe.c` 实现的是一个“串口命令解析”状态机：单行命令 `<字母><数字>\n`，字母 ∈ {R,G,B}，数字 ∈ 0..9。核心是一张 **状态 × 事件 → 动作** 的 `const` 表：

```c
typedef state_t (*trans_t)(fsm_t *f, char ch);   /* 动作 = 返回下一状态的函数 */

static trans_t const FSM[3][4] = {
    /*              EV_LETTER     EV_DIGIT      EV_LF       EV_OTHER  */
    /* S_IDLE */ { act_save_cmd, act_ignore,  act_ignore, act_ignore },
    /* S_ARG  */ { act_save_cmd, act_save_arg, act_error, act_error  },
    /* S_END  */ { act_error,    act_error,    act_exec,  act_error  },
};
```

整个“状态机”就是这一行：

```c
__attribute__((noinline))
static void fsm_feed(fsm_t *f, char ch)
{
    trans_t t = FSM[f->state][classify(ch)];
    f->state = t(f, ch);            /* ← 查表 + 间接调用：中断里只做这点事 */
}
```

交叉编译（`-O2`）后 `fsm_feed` 的机器码，把查表和跳转摊开：

```asm
00000070 <fsm_feed>:
  70:	b510		push	{r4, lr}
  ...
  92:	eb03 0382	add.w	r3, r3, r2, lsl #2			@ r3 ← state*4 + ev
  96:	4a05		ldr	r2, [pc, #20]	; (ac <fsm_feed+0x3c>)	@ r2 ← FSM 基址
  98:	4620		mov	r0, r4
  9a:	f852 3023	ldr.w	r3, [r2, r3, lsl #2]	@ 查表：取出函数地址
  9e:	4798		blx	r3				@ 间接调用
  a0:	7020		strb	r0, [r4, #0]		@ 返回值写回 f->state
  a2:	bd10		pop	{r4, pc}
```

三点值得注意：

1. **`blx r3` 就是“函数指针”在机器码层面的全部含义**：跳到寄存器里的地址。源码里的每一次“回调”，交叉编译后都是这条指令。
2. `f->state = t(f, ch)` 被翻译成 `strb r0, [r4, #0]`：**动作函数的返回值直接就是下一状态**。整张表不需要任何“转移逻辑”代码，表驱动。
3. **`classify(ch)` 被完全内联掉了**（没有 `bl` 调用），只剩 `cmp`/`beq`/`bls`/`ite` 一串比较。`-O2` 会把短小的分类函数摊平。

`const` 的价值在这里是硬的：`nm` 显示 `FSM` 是 `r` 类型（只读），落在 `.rodata`，**48 字节（3×4×4）一个字节都不占 RAM**。对比 `key_table`（运行时要注册，非 const）：`b` 类型，老实占 `.bss` 的 32 字节。

行为断言把“状态活在数据里”钉死：

- `"R5\n"` → `n_exec==1`，`cmd=='R'`，`arg==5`，回到 `S_IDLE`；
- 逐字节喂 `'R'`、`'4'` 跨调用续命：喂完 `'4'` 时 `state==S_END`，再喂 `'\n'` 才让 `n_exec` 加一：**状态活在结构体里，不在调用栈上**，这正是中断分片处理的必要条件；
- `"R\n"`（缺参数）、`"R5X\n"`（参数后混垃圾）→ `n_err` 加一、状态复位，不崩溃不死等。

一次 `fsm_feed` 的全部工作量，就是“一次查表 + 一次间接调用 + 一次 `strb`”：机器码 4 条有效指令。这就是中断预算的基准线：几十个时钟周期。

### 环形缓冲两派：满/空判定

![环形缓冲两派动画：读写指针相等时是空还是满](/anim/ring-buffer.svg)

单生产单消费环形缓冲的经典难题：**读写指针相等时，是空还是满？** 两派各有一个答案，`probe.c` 两派都实现，用同一组测试对照。

**A 派（牺牲一格）**：留一个空位当哨兵：

```c
if ((uint8_t)((w + 1) % RB_CAP) == q->r) return false;   /* 满 */
...
if (r == q->w) return false;                             /* 空 */
```

8 格物理容量，**只能用 7 格**（实测输出 `A 派可用 7 格`）。代价是浪费一格，好处是判定逻辑直白。

**B 派（单调索引）**：指针永不取模，交给 `uint8_t` 自然溢出，用“在飞元素数”判满：

```c
uint8_t w = q->w;
if ((uint8_t)(w - q->r) >= RB_CAP) return false;         /* 满：无符号减法天然抗回绕 */
q->data[w % RB_CAP] = v;                                 /* 只在寻址时才取模 */
```

**8 格全部可用**（实测输出 `B 派可用 8 格`）。妙处在于 `(uint8_t)(w - q->r)`：即使 `w` 从 255 回绕到 0，无符号减法的模 256 语义让“在飞数量”依旧正确，不用写任何回绕判断。两派的空判定都是 `w == r`，区别只在满：A 派把“差一格”当满，B 派把“在飞数量等于容量”当满。

两派共用的发布/获取顺序，是“中断生产、主循环消费”的正确性关键：

```c
q->data[w % RB_CAP] = v;                          /* 先写数据 */
atomic_signal_fence(memory_order_release);        /* 屏障：数据先于写指针发布 */
q->w = (uint8_t)(w + 1);                          /* 再发布写指针 */
```

消费者对称：先读 `r`，再 `atomic_signal_fence(memory_order_acquire)`，最后取数据。**顺序反了就是“读到空槽”的经典 bug**（对应 C3 的屏障一节，[第 2 章](./02-c-volatile-ub.md)已把访存合同讲清）。

长跑验证（两派各 600 步、塞取交错）：序号对 256 取模后与读出值逐一比对，`n_put == n_get`（一个不多一个不少）。B 派额外断言 `n_put > 256`：确实跨过了 255→0 回绕，且 `q.w == n_put mod 256`、`q.r == n_get mod 256`。A 派额外断言“满写被拒”路径真的触发过（`n_refused > 0`）。

前提也要说清：单生产单消费成立的前提是“生产者只有一个、消费者只有一个”。一旦中断和主循环都要改同一个索引（双向队列，或多优先级中断都往里塞），就必须上临界区；重入与互斥的展开在[第 10 章][ch10]，RTOS 队列的版本在[第 24 章](../v3-rtos/24-queue-semaphore-notification.md)。

### 中断礼仪：查表一跳，记账不办事

| 组件 | 中断里做什么 | 主循环做什么 |
| --- | --- | --- |
| 函数指针（向量表/分发表） | 一跳到位，不做判断 | 注册/替换处理函数 |
| 状态机 | 只改 `f->state`、搬一字节 | 读 `state`/`n_exec` 决定业务 |
| 环形缓冲 | 只 `put` 一个字节 | 循环 `get` 出来慢慢处理 |

为什么不能恋战：`fsm_feed` 的全部工作量是 4 条有效指令，中断预算以几十个时钟周期计。一旦在中断里加 `printf`、`delay`、浮点运算，预算立刻爆掉；来源 C5 引 C3 的记录：`-O0` 下 `printf` 要几百微秒。中断里只做快递分拣，不下厨房。

### AAPCS：参数落位与返回值

![AAPCS 参数落位：前四个参数进 r0-r3，第五个起压栈；栈帧里还有 LR、旧 FP 与局部变量](/figures/c-06-abi-stack.svg)

启动文件里一行 `bl main` 为什么能成？编译器是 gcc，启动文件是手写汇编，两者从没见过面，能接上头全靠 **AAPCS**（Procedure Call Standard for the ARM Architecture）：ARM 公布的调用约定，gcc / clang / IAR / Keil 全都遵守。它规定四个问题：参数放哪、返回值放哪、哪些寄存器用完要复原、栈怎么对齐。

核心寄存器分工：

| 寄存器 | 别名 | 职责 | 调完还有效吗 |
| --- | --- | --- | --- |
| r0–r3 | a1–a4 | 前 4 个参数 / 临时 scratch；r0（64 位时 r0:r1）带回返回值 | 被调方随便改，调用方自保 |
| r4–r8、r10、r11 | v1–v8 | 长期变量 | 被调方想用就得先存后恢复 |
| r9 | v6/sb | 平台保留 | 被调方保存 |
| r12 | ip | 链接器贴片用的 scratch | 被调方随便改 |
| r13 | sp | 栈指针，公共接口处 8 字节对齐 | 调用期间由被调方移动 |
| r14 | lr | 返回地址，`bl` 时硬件写入 | 每次调用都被覆盖 |
| r15 | pc | 程序计数器 | `pop {…, pc}` 改写它完成返回 |

**参数落位铁律**：r0–r3 装前 4 个参数，第 5 个起走栈。`sum6` 有 6 个 int 参数，被调方汇编里前 4 个在 r0–r3，第 5、6 个用 `ldr r2, [sp]` / `ldr r0, [sp, #4]` 从栈上读回；编译器注释 `@ args = 8` 标明栈上入参 8 字节，函数自己的帧是 0。调用方在 `bl sum6` 之前用一条 `strd r3, r2, [sp]` 把 5、6 写上栈顶。`sum6(1,2,3,4,5,6) = 21`，语义不因传参方式改变，变的只是成本：栈传参多出内存写和内存读。性能敏感的接口，参数控制在 4 个以内。

用哪几个寄存器接收栈上的值，是编译器的自由：来源记录里 10.3.1 给成 `ldr r2, [sp]`，别的版本可能是 `ldr r1, [sp]`。AAPCS 只承诺“前 4 个参数在 r0–r3，第 5 个起在栈上 `[sp]`/`[sp,#4]`”，剩下的它不管。

**64 位参数必须落在偶奇寄存器对**。`add64` 的两个 `long long`，x 在 r0:r1、y 在 r2:r3，返回值也在 r0:r1；`adds`/`adc` 进位链就是“两个 32 位寄存器扮一个 64 位数”的证据，宿主实测 `add64(0x100000000, 0x200000001) = 0x300000001`。真正的反直觉点在 `mix(int tag, long long v)`：tag 占了 r0，v **不能**放 r1:r2，AAPCS 要求 64 位参数对齐到**偶数号**寄存器，于是 v 落 r2:r3，**r1 被跳过**。调用方汇编从头到尾没写 r1；此刻 r1 里是上一个函数的返回高半（垃圾值），而 `mix` 正确地对它视而不见。宿主断言 `mix(7, 0x100000000) = 0x100000007`。推论：给函数签名排序时把 64 位参数放前面、int 填后面，能少留寄存器空洞，ABI 不会替你重排。

**硬浮点 ABI** 另走一套：编译旗 `-mfpu=fpv4-sp-d16 -mfloat-abi=hard` 时，单精度走 s0–s15、双精度走 d0–d7。`add_d(double, double)` 的两个 double 从 d0、d1 进来，汇编里 `vmov r0, r1, d0` / `vmov r2, r3, d1` 把 d0/d1 搬进内核寄存器，再 `bl __aeabi_dadd`：fpv4-sp 只有单精度硬件，double 加法得调软件库，软件库按 r0:r1/r2:r3 收参是它自己的内部约定。对照 `-mfloat-abi=soft`，double 按 64 位整数规则直接走 r0:r1。两种 ABI 编出的目标文件**不能混链**，链接器会报 VFP 参数 mismatch。宿主断言 `add_d(0.5, 0.25) == 0.75`。

### 栈帧：push {r4, lr} … pop {r4, pc}

![函数调用栈帧动画：参数装车、保护现场、局部变量占坑、满血返回](/anim/stack-frame.svg)

`non_leaf` 内部还要 `bl sink`、`bl add2`，每次 `bl` 都会覆盖 lr，所以 prologue 必须先把 lr 存起来；它还带着 r4，因为 `sink` 标了 `__attribute__((noipa))`，调用方只能按 ABI 做最坏假定：r0–r3、r12 全被改写，想活过这次调用的值只能放进被调方保存寄存器。完整帧：

```asm
non_leaf:
	push	{r4, lr}        @ 8 字节：保存 r4 与返回地址
	sub	sp, sp, #16     @ 16 字节：buf[16] 的家
	@ …
	bl	sink
	bl	add2
	pop	{r4, pc}        @ 恢复 r4，返回地址直接弹进 PC——连 bx lr 都省了
```

**返回地址弹进 PC** 是 Thumb-2 的经典收尾：弹栈与跳转合一。这个 Cortex-M4 帧 = push 8 + sub 16 = **24 字节**。对照组 `add2` 是叶子函数，不调用任何人，编译器直接注释 `@ link register save eliminated.`，全身就 `add r0, r0, r1` + `bx lr` 两条指令。计数核对：全文件 `push {r4, lr}` 恰出现 1 次、`pop {r4, pc}` 恰出现 1 次，正是 `non_leaf` 这一对；`strd , [sp]` 也恰 1 次，就是 `sum6` 那次的栈传参。

宿主 gcc 16.1.0 真跑 `non_leaf`，探针读数为：`sp(main)` 到 `sp(non_leaf)` 一帧 **64 字节**，`buf` 距 `sp(non_leaf)` **32 字节**；sp 向下走（`sp_callee < sp_main`），帧差是 8 的倍数，因为 AAPCS 要求公共接口处 sp 8 字节对齐。64 字节与 24 字节的差别只在目标与编译器，机制不变：**sp 一根指针的移动 = 分配与释放的全部成本**。递归无界就是栈溢出；裸机没有 MMU 兜底，症状往往是“变量莫名其妙变了”，HardFault 都不一定报。现场定位见[第 19 章](../v2-reliability/19-watchdog-reset-hardfault.md)，中断切换栈的完整现场见[第 23 章](../v3-rtos/23-context-switch-porting.md)。

### 中断服务函数：签名为什么必须符合调用约定

根书第 04 章给出的写法：

```c
static volatile uint8_t g_key_flag = 0;   /* ISR 与主循环共享，必须 volatile */

void EXTI0_IRQHandler(void)
{
    if (__HAL_GPIO_EXTI_GET_IT(KEY_PIN) != RESET)
    {
        __HAL_GPIO_EXTI_CLEAR_IT(KEY_PIN);   /* 必须清标志，否则反复进中断 */
        g_key_flag = 1;                      /* 只置标志，不做耗时操作 */
    }
}
```

这个签名不是风格问题，是调用约定问题。硬件从向量表槽位跳过来，没有 C 调用方，也没有任何人往 r0–r3 里放参数；函数返回时，硬件也不读 r0 当返回值。所以处理函数必须是 `void f(void)`：

- 参数写多了，编译器会按 AAPCS 去 r0–r3 或栈上取“参数”，取到的是被中断程序留下的值；链接器不会拦，因为向量表里只有一个符号名。
- 返回值写非 void，不会有人消费；更糟的是签名与槽位约定不一致，和函数指针类型不匹配一样，属于未定义行为。
- 函数必须是外部链接、且与启动文件里的槽位同名（`EXTI0_IRQHandler`）；弱符号机制只认名字，`static` 或拼错名字，覆盖就不会发生。

进入函数之后，编译器把它当普通函数编译：用到 r4–r11 就按 AAPCS 先保存、返回前恢复；调用点上栈保持 8 字节对齐。异常入口的现场压栈由硬件负责（8 个寄存器，流程细节见[第 10 章][ch10]），ISR 的栈帧叠在被中断者的栈上，所以栈预算要算上最坏中断嵌套。函数内部违反调用约定（手写汇编忘了保存 lr 或被调方寄存器），坏的是被中断程序，不是 ISR 自己。

正文纪律也来自同一份来源：先清中断标志，再置 `volatile` 标志，然后立刻返回。`HAL_Delay()` 依赖 SysTick 中断，在 ISR 里调用可能死等；`printf` 这类慢操作留给主循环。主循环与 ISR 共享多字节数据时，读快照要进临界区（`__disable_irq()` / `__enable_irq()`），单字节标志用 `volatile` 就够，这条边界在[第 2 章](./02-c-volatile-ub.md)已经逐条对过。

| 事项 | 谁负责 | 依据 |
| --- | --- | --- |
| 入口地址 | 向量表槽位；弱符号可被同名函数覆盖 | C5 |
| 参数与返回 | 没有：签名必须是 `void f(void)` | C5、根书第 04 章 |
| 现场保存 | 硬件压栈 + 编译器按 AAPCS 保存被调方寄存器 | 根书第 04 章、C6 |
| 退出 | 硬件按异常返回流程恢复现场 | 根书第 04 章 |
| 时长 | 只记账：清标志、置 flag、搬一字节 | 根书第 04 章、C5 |

## 测量与证据

本章数字来自 C5、C6 的取证工程。C6 记录的环境：宿主 MinGW-Builds gcc 16.1.0（x86_64-posix-seh），交叉 GNU Arm Embedded Toolchain 10.3.1，编译旗 `-mcpu=cortex-m4 -mfloat-abi=hard -O2 -S`。C5 的 `probe.sh` 默认 `-O2`，交叉工具链在 `PATH` 时附送反汇编。换编译器、换版本、换优化档，指令形状会变，判读方法不变。

| 取证项 | 命令 | 来源记录里的结果 |
| --- | --- | --- |
| 回调表尺寸 | `_Static_assert` + `nm` | `key_table` 占 `0x20` = 32 字节 = 8 × 4 |
| 状态机表落点 | `nm build/probe.m4.o` | `FSM` = `r`（`.rodata`，48 字节）；`key_table` = `b`（`.bss`，32 字节） |
| 查表分派 | `sh probe.sh` 反汇编段 | `ldr.w r3, [r2, r3, lsl #2]`（`0x9a`）+ `blx r3`（`0x9e`） |
| 状态机行为 | `sh probe.sh` | 560/560；`"R5\n"` 执行一次；跨调用状态续命；错误输入不崩溃 |
| 环形缓冲容量 | `sh probe.sh` | A 派 7 格，B 派 8 格 |
| 环形缓冲回绕 | `sh probe.sh` | 600 步，`n_put == n_get`；B 派 `n_put > 256` |
| 第 5、6 个参数走栈 | `sh probe.sh`（06） | `sum6(1,2,3,4,5,6) = 21` |
| 64 位寄存器对 | 同上 | `add64(0x100000000, 0x200000001) = 0x300000001` |
| 64 位参数跳过 r1 | 同上 | `mix(7, 0x100000000) = 0x100000007`，调用方未写 r1 |
| 硬浮点 ABI | 同上 | `add_d(0.5, 0.25) = 0.75`，double 从 d0/d1 进 |
| ABI 行为断言 | `sh probe.sh`（06） | 9/9 |
| 宿主栈帧 | `probe.c` 探针 | 一帧 64 字节，`buf` 距 sp 32 字节 |
| Cortex-M4 栈帧 | `probe.sh` 寄存器取证 | `push {r4, lr}` 8 字节 + `sub sp, #16` = 24 字节 |
| push/pop 计数 | `probe.sh` | `push {r4, lr}`、`pop {r4, pc}`、`strd , [sp]` 各恰 1 次 |

`fsm_feed` 的查表两行连起来读：`ldr.w r3, [r2, r3, lsl #2]` 从 `FSM` 基址加 `(state*4 + ev)*4` 取出函数地址，下一条 `blx r3` 就跳过去。源码里的 `t(f, ch)` 在机器码层面就是这么两条指令。

判断“真的会了”：给你一个没见过的声明，能在十秒内用右左法则读出来并写成 `typedef`；给你一段 `-O2` 反汇编，能指出参数从哪进、栈帧多大、返回地址压在栈上哪个字；给你一个向量表槽位，能写出签名正确、只做记账的 ISR，并说清签名写错的后果。

## 失败分支

| 现象 | 原因 | 区分证据 | 下一动作 |
| --- | --- | --- | --- |
| 回调偶尔跳飞，换个优化档又正常 | 函数指针签名不匹配，调用是 UB | 类型声明逐字对比；旧代码 `void (*)()` 与 `void (*)(void)` 不同 | 统一 `typedef`，所有注册点用同一类型 |
| 未注册的槽一调用就进地址 0 | 分派前没判空 | `probe.c` 的 `if (key_table[i] != NULL)`；汇编 `cbz r3, ...` 后才 `blx r3` | 分派前判空，空槽跳过或走默认处理 |
| 状态机喂到一半丢状态 | 状态放在局部变量，跨调用就没了 | 跨调用断言：喂完 `'4'` 后 `state==S_END` 才继续 | 状态放进 `fsm_t`，随句柄传递 |
| 状态机里做长延时，整机像死机 | 中断/主循环被拖死 | `fsm_feed` 所在上下文出现 `HAL_Delay`/`printf` | 延时改成“等超时事件”的状态 |
| 环形缓冲偶尔读到旧数据 | 发布/获取顺序反了，或读写指针交叉修改 | 检查屏障位置与指针归属 | 生产者只动 `w`、消费者只动 `r`；先数据后指针 |
| 8 格缓冲只能存 7 笔，以为算错 | A 派牺牲一格当哨兵 | 容量对照输出 `A 派 7 格` | 接受代价，或换 B 派单调索引 |
| B 派过了 255 就错乱 | 用有符号减法或提前取模判满 | `(uint8_t)(w - r) >= RB_CAP` 是否保留无符号语义 | 用无符号减法算在飞数量，只在寻址取模 |
| 查表数组忘加 `const`，RAM 白吃 | 表落在 `.bss` | `nm` 字母：`r` = Flash，`b`/`d` = RAM | 能 const 的表全加 const |
| `mix` 的 long long 按 r1:r2 找值，找到垃圾 | 64 位参数落偶奇寄存器对，r1 被跳过 | 调用方汇编没写 r1；被调方从不读入参 r1 | 按 r2:r3 读；签名排序把 64 位参数放前面 |
| 手写汇编函数返回后乱飞 | 非叶子函数没保存 lr | prologue 缺 `push {…, lr}` | 非叶子函数先存 lr；或让编译器生成 |
| ISR 反复进，主循环拿不到执行 | 中断标志没清 | 处理函数里缺 `__HAL_GPIO_EXTI_CLEAR_IT` | 入口先清标志，再置事件 flag |
| ISR 里调用 `HAL_Delay()` 死等 | 它依赖 SysTick，可能被同级/更高级屏蔽 | 看 ISR 是否依赖 SysTick 计数 | 慢操作搬回主循环 |
| 递归深了变量莫名其妙变 | 栈溢出踩到堆/全局区，裸机没有 MMU 兜底 | 栈用量与最坏中断嵌套对不上 | 禁无界递归；算最坏栈预算 |
| 中断嵌套后返回地址不对 | ISR 使用了被破坏的栈或被调方寄存器 | 检查 ISR 栈帧与手写汇编的保存纪律 | 按 AAPCS 保存；栈预算含最坏嵌套 |

## 跨平台边界

本章可带走的结论是语言与架构级的：函数指针与 `typedef` 是标准 C；向量表是“Flash 里的函数指针数组”这一机制来自 Cortex-M 启动文件；AAPCS 的参数落位、被调方保存、8 字节栈对齐是 ARM 公布的调用约定，gcc / clang / IAR / Keil 都遵守。两平台的 C 编译器都受它约束，所以“前 4 个参数进 r0–r3、第 5 个起走栈、64 位占偶奇对、sp 移动即栈帧生灭”这套算法可以带着走。

不能带走的是取证形状与芯片细节。本章逐条汇编来自 Cortex-M4（F407 目标）与宿主 x86-64：`.isr_vector` 的 392 字节、`FSM` 的 48 字节、`non_leaf` 的 24 字节、`d0/d1` 的硬浮点路径，都是这套工具链与这颗内核的读数。F103 侧只取根书第 04 章的 ISR 签名与“只置标志”写法，来源没有给出 F103 的逐条汇编对照，本章不把 M4 的指令形状、向量表大小或硬浮点寄存器当成 F103 的实测。`EXTI0_IRQHandler` 这样的槽位名与 IRQ 编号属于芯片家族的启动文件，NVIC/EXTI 的完整流程在[第 10 章][ch10]；寄存器名、时钟与引脚差异指向卷 4 的[第 28 章](../v4-platforms/28-chip-migration-differences.md)与[第 29 章](../v4-platforms/29-gd32-arm-riscv.md)，本章不泛化。

| 事项 | 本章的证据范围 | 跨平台时的处理 |
| --- | --- | --- |
| 函数指针与 `typedef` | 标准 C，两平台通用 | 直接复用 |
| 向量表机制 | F407 工程 `.isr_vector` 392 字节；启动文件弱符号 | 机制可复用，表大小与槽位名按芯片启动文件对账 |
| AAPCS 参数/栈帧 | 规则来自 AAPCS；汇编取自 Cortex-M4 与宿主 | 规则可复用，指令形状不搬运 |
| 硬浮点 d0/d1 | C6 的 `-mfloat-abi=hard` M4 证据 | F103 未取证，按目标芯片编译选项核对 |
| ISR 签名 | 根书第 04 章的 F103 例子 `void EXTI0_IRQHandler(void)` | 槽位名与 IRQ 编号按芯片启动文件 |
| NVIC/EXTI 细节 | 本章不展开 | [第 10 章][ch10] |
| 寄存器、时钟、引脚 | 本章未展开 | [第 28 章](../v4-platforms/28-chip-migration-differences.md)、[第 29 章](../v4-platforms/29-gd32-arm-riscv.md) |

## 离开检查

1. `void (*table[8])(void)` 用右左法则怎么读？`typedef` 改变了什么，没改变什么？
2. 向量表为什么是“Flash 里的函数指针数组”？从 `.word EXTI0_IRQHandler` 到你的同名函数被调用，中间发生了什么？
3. `fsm_feed` 的查表与跳转各是哪条机器指令？为什么说“状态活在结构体里，不在调用栈上”？
4. 8 格物理容量的环形缓冲，A 派与 B 派各能存几笔？两派的满判定分别是什么，B 派为什么不怕 255→0 回绕？
5. `sum6` 的第 5、6 个参数怎么进函数？`mix(int, long long)` 的 long long 为什么在 r2:r3，此刻 r1 里是什么？
6. `non_leaf` 在 Cortex-M4 上的一帧 24 字节由哪两部分组成？叶子函数 `add2` 为什么不保存 lr？`pop {r4, pc}` 一条指令完成了哪两件事？
7. 中断服务函数为什么必须写成 `void f(void)`？签名写错、名字写错、函数体里做慢操作，各会坏在哪？

<details>
<summary>对照答案</summary>

1. 从 `table` 出发：右看 `[8]` 是数组，左看 `*` 元素是指针，右看 `(void)` 指向函数，左看 `void` 函数返回 void。合起来是“8 个元素的数组，元素是指向无参、返回 void 的函数的指针”。`typedef` 只给这个类型起名，不改语义；两种写法指向同一对象，`sizeof` 仍是 8 × 4。
2. 向量表在 Flash 起始处，每一项是一个函数地址；启动文件用 `.word EXTI0_IRQHandler` 填槽，`Reset_Handler` 是弱符号，槽位默认可被覆盖。你写出同名函数，链接器把槽位重定位到你的函数地址；硬件取向量时直接跳过去，不需要 C 层注册 API。
3. 查表是 `ldr.w r3, [r2, r3, lsl #2]`，跳转是 `blx r3`。状态存在 `fsm_t` 结构体里，`fsm_feed` 只改 `f->state`；函数返回后状态仍在，所以可以一个字节一个字节地跨中断喂，调用栈上不留状态。
4. A 派 7 格（留一格当哨兵：`(w+1) % CAP == r` 判满），B 派 8 格（`(uint8_t)(w - r) >= CAP` 判满）。两派空判定都是 `w == r`。B 派用无符号减法的模 256 语义算在飞数量，`w` 从 255 回绕到 0 时差值依旧正确，不用写回绕判断。
5. 前 4 个在 r0–r3；第 5、6 个由调用方 `strd` 写上栈，被调方用 `ldr [sp]` / `ldr [sp,#4]` 取回，编译器注释 `@ args = 8`。`mix` 的 long long 必须落偶奇寄存器对，tag 占了 r0 后只能放 r2:r3，r1 被跳过；调用方没写 r1，里面是上一个函数返回的高半垃圾值，`mix` 不读它。
6. `push {r4, lr}` 8 字节（保存 r4 与返回地址）+ `sub sp, sp, #16` 16 字节（`buf[16]`），合计 24 字节。`add2` 是叶子函数，不调用任何人，lr 不会被覆盖，编译器注明 `@ link register save eliminated.`。`pop {r4, pc}` 恢复 r4，并把返回地址直接弹进 pc，弹栈与跳转合一。
7. 硬件从向量表跳过来，没有 C 调用方，不填参数、不读返回值；处理函数必须是 `void f(void)`，名字与槽位一致且外部链接。签名写错，编译器按 AAPCS 去读没人填过的参数，链接器不拦；名字写错或 `static`，弱符号覆盖不发生，中断跳进默认处理；函数体做慢操作或忘了清标志，会拖死主循环或反复进中断。

</details>
