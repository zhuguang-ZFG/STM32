1. 环境这章只追一个问题：你写下的 C，怎样变成芯片里正在跑的程序。中间就是编译、链接、烧录、复位运行。工具可以换，这四步不会换。
2. Keil、CubeIDE、PlatformIO 都能走完这四步。差别只是谁帮你填启动文件和链接脚本。先选一个能单步的，不要三个一起装到怀疑人生。
3. 复位之后，内核先读向量表。第零个字是栈顶，第一个字才是复位入口。进 main 之前，启动文件还要配时钟、搬数据段、清 BSS。
4. 这一帧是仓库里的启动顺序动画，不是芯片照片。你只要记住：还没进 main，该做的家务启动文件已经做完一轮。单步时别以为第一行就是上电第一件事。
5. 下载靠 SWD。F103 上 PA13 是数据线，PA14 是时钟。把这两只脚让给别的功能，下次探针就连不上。救砖时先把 BOOT0 拉高，再重新接上。
6. Cube 生成的工程，用户代码写在它留的标记中间。时钟改了就重新生成，不要在启动文件里打补丁。临时文件和编译产物不要提交进版本库。
7. 第一次下载只做三件事：接上调试器，确认软件认出芯片型号，再下一个只点灯的空工程。连芯片都认不出，就先别查业务代码。
8. 口诀：先认出芯片，再谈业务。调试器连不上的时候，查线、查供电、查 BOOT，不要先重写 main。线都没通，改代码是在安慰自己。
9. 这章结束，你的文件夹里应该有一个能单步的工程。你要能说出向量表前两个字是什么，也要能指出 SWD 占用的两只脚。
10. 合上书，三问。向量表第零个字是什么？第一个字是什么？SWD 占哪两只脚？答不上来，就把启动文件再单步一遍。

## 学习目标

读这一章之前：会在电脑上安装软件、解压文件，认得 `0x08000000` 这样的十六进制地址（不熟的话先读第 00 章的「零基础预备」）。手边准备一块 BluePill（STM32F103C8T6）和一只 ST-LINK V2 调试器。

- [ ] 说出 C 源码变成芯片里正在跑的程序要经过的四步：编译、链接、烧录、复位运行，以及每一步由哪个工具完成
- [ ] 在 Keil MDK、STM32CubeIDE、VS Code + PlatformIO、CLion 里选定一套，并说出选它的理由
- [ ] 用 STM32CubeMX 生成一个能直接编译的点灯工程，并且 SYS Debug 选的是 Serial Wire
- [ ] 按接线表连好 SWD，在 STM32CubeProgrammer 里读到芯片的 Device ID
- [ ] 在调试器里打开地址 `0x08000000`，读出向量表的前两个字，说出哪个是栈顶、哪个是复位入口
- [ ] 遇到「连不上目标」「下载失败」「芯片被读保护」时，按接线、供电、BOOT 跳线、软件的顺序排查

## 核心原理

**一句话结论：不管用哪种 IDE，底下都是同一条路：编译、链接、烧录、复位运行。IDE 只决定由谁替你执行这四步；其中任何一步断了，程序都跑不起来。**

### 先打个比方

把做一个程序想成出一本书。

- **编译**：把手稿（C 源码）逐章翻译成印刷厂认得的版面（目标文件 `.o`）。每章各翻各的，互相不知道对方排在第几页。
- **链接**：按一张装订单（链接脚本）把各章排进同一本书，定下每段文字落在第几页（地址）。
- **烧录**：把排好的书印到纸上（写进芯片的闪存）。
- **复位运行**：读者翻开书。芯片有个固定的读法：先看第 0 页写的书签位置（栈顶），再看第 1 页写的「正文从第几页开始」（复位入口），然后翻过去读。

比方到这里为止。书印好就改不了，闪存却能擦掉重写，[DS5319 Rev 20](#source-ds5319) 表 29 保证至少 1 万次擦写；而且 CPU 不会一页页往下翻，它按地址跳着读。

### 1. 四步：编译、链接、烧录、复位运行

结论：四步各有各的产物。程序没跑起来时，看产物停在哪一步，就知道该查哪里。

```text
源码 .c/.h
   │  编译（arm-none-eabi-gcc 或 Keil 的 armclang）
   ▼
目标文件 .o
   │  链接（ld 或 armlink）+ 链接脚本（.ld 或 .sct）
   ▼
可执行文件 .elf ──► .hex / .bin
   │  烧录（ST-LINK 经 SWD；工具用 CubeProgrammer、OpenOCD 等）
   ▼
闪存 0x08000000
   │  复位
   ▼
CPU 读向量表 → Reset_Handler → main()
```

图里的几个词：

- **编译器（compiler）**：把 C 翻译成机器码的程序。STM32 常用两种：arm-none-eabi-gcc 是 GNU 的 Arm 裸机编译器，名字里的 none 表示「没有操作系统」，eabi 是 Arm 规定的二进制接口；Keil 用 Arm 自家的 Arm Compiler（armclang）。
- **链接器（linker）**：把一堆 `.o` 和库拼成一个完整程序，并按链接脚本给每段代码、每个变量分配地址。GCC 的链接脚本是 `.ld` 文件，Keil 的叫分散加载文件（`.sct`）。
- **ELF**：链接的产物。里面除了机器码，还有调试要用的函数名、变量名和行号。`.hex`、`.bin` 只留下要写进闪存的字节。
- **烧录（下载）**：经调试器把这些字节写进芯片的闪存。
- **复位运行**：芯片复位后，从向量表开始执行。第 7 节细讲。

下表把四步并排。读法：程序没跑起来时，从左往右找第一个没有产出的步骤。

| 步骤 | 输入 | 输出 | 典型工具 | 这一步坏了时的样子 |
| --- | --- | --- | --- | --- |
| 编译 | `.c`、`.h` | `.o` | arm-none-eabi-gcc、armclang | 语法错误、找不到头文件 |
| 链接 | `.o`、库、链接脚本 | `.elf`，再转 `.hex`/`.bin` | ld、armlink | `undefined reference`、闪存放不下（`region 'FLASH' overflowed`） |
| 烧录 | `.elf`/`.hex`/`.bin` | 闪存里的字节 | ST-LINK + CubeProgrammer 或 OpenOCD | 连不上目标、下载失败 |
| 复位运行 | 闪存里的向量表 | 程序在跑 | 芯片自己 | 不进 `main`、卡在 HardFault |

### 2. 工具和它们各自的活

结论：一套能用的环境由几样东西拼成：生成代码的配置工具、编译器、调试器硬件、调试服务程序、烧录工具。IDE（集成开发环境）是把它们装进同一个窗口的外壳。

| 工具 | 是什么 | 管四步里的哪一段 |
| --- | --- | --- |
| STM32CubeMX | ST 的图形化配置工具：选芯片、点引脚、配时钟，生成初始化代码和工程 | 编译之前，生成代码 |
| STM32CubeIDE | ST 的免费 IDE，基于 Eclipse，自带 GCC 和 GDB | 编译、链接、烧录、调试 |
| arm-none-eabi-gcc | GNU 的 Arm 裸机编译器，Arm 以 Arm GNU Toolchain 的名字发布（旧名 GNU Arm Embedded Toolchain） | 编译、链接 |
| ST-LINK | ST 的调试器硬件，也叫调试探针：一头插电脑 USB，一头接芯片的 SWD 线 | 烧录和调试走的物理通道 |
| STM32CubeProgrammer | ST 的烧录工具：擦除、写闪存、改选项字节（读保护就在这里改） | 烧录、解锁 |
| OpenOCD | 开源的调试服务程序：驱动 ST-LINK 等探针，给 GDB 开一个端口（默认 3333），也能直接写闪存 | 烧录、调试 |
| GDB | GNU 调试器：打断点、单步、看变量。它不直接碰芯片，要经 OpenOCD 或 ST 的 GDB 服务程序 | 调试 |

用法：先找到你卡住的是哪一步，再看这一步归哪个工具管，去那个工具里找报错。老教程里的 ST-LINK Utility，ST 已经建议改用 STM32CubeProgrammer。

> [!NOTE]
> STM32CubeIDE 1.x 里内置了 CubeMX。2025 年 11 月发布的 STM32CubeIDE 2.0 把它拆了出去：先在独立的 STM32CubeMX 里配置、生成工程，再用 CubeIDE 打开。网上很多截图还是 1.x 的界面，在 2.0 里找不到引脚视图，不是安装出了问题。

### 3. 四种开发环境怎么选

下表比较四种常见环境。先看「适合谁」一行挑出一两个，再看授权和系统是否满足你的条件。授权条款会变，这一行按 2026 年 10 月各家官网的说明写。

| 维度 | Keil MDK | STM32CubeIDE | VS Code + PlatformIO | CLion + OpenOCD |
| --- | --- | --- | --- | --- |
| 授权 | 收费；社区版不限代码大小，只限非商业用途；评估版限 32 KB 代码 | 免费（ST 官方） | 免费开源 | 商用收费；非商业用途免费 |
| 编译器 | Arm Compiler 6（armclang），老工程用 Arm Compiler 5（armcc） | GCC（arm-none-eabi） | GCC | GCC |
| 上手难度 | 低，中文资料多 | 低 | 中，要写 `platformio.ini` | 中高，要懂 CMake |
| 调试 | 强，寄存器窗口齐全 | 强，自带调试器 | 够用，靠扩展插件 | 强 |
| 系统 | µVision 只有 Windows 版 | Windows、Linux、macOS | 全平台 | 全平台 |
| 适合谁 | 教学、公司老项目 | 新手、跟着 ST 官方例程走的人 | 习惯命令行、要做自动化构建的人 | 习惯 CMake 的 C/C++ 开发者 |

**选择建议：新手用 STM32CubeIDE，配合 STM32CubeMX 生成工程；已有 Keil 授权的沿用 Keil；需要能审查、能进 CI（持续集成，每次提交自动编译）的构建时，用同一套 CMake Preset 驱动 CLion 或 VS Code。PlatformIO 是另一套包管理与构建路线，不要和手工 CMake 工程混在一起。**

### 4. 工程里有哪些文件

结论：工程里大部分文件是生成的，你写的代码只在 `Core/` 下，而且要写在 CubeMX 留的标记中间。

```text
Core/          Inc/  Src/          ← 你的代码（main.c、中断、外设初始化）
Drivers/       CMSIS/  STM32F1xx_HAL_Driver/
Middlewares/   （可选，如 FreeRTOS、FatFs）
Startup/       startup_stm32f103xb.s
STM32F103C8TX_FLASH.ld           ← 链接脚本（GCC）
<工程名>.ioc                      ← CubeMX 工程文件
```

目录结构画在 [`assets/diagrams/project-structure.svg`](../assets/diagrams/project-structure.svg)（作者自绘矢量图）。下表说每个关键文件管什么、该不该手改：

| 文件 | 作用 | 要不要手改 |
| --- | --- | --- |
| `<工程名>.ioc` | CubeMX 的工程配置，改完可以重新生成代码 | 在 CubeMX 里改 |
| `startup_stm32f103xb.s` | 启动汇编：定义向量表和复位入口 | 一般不改 |
| `STM32F103C8TX_FLASH.ld` | GCC 链接脚本：闪存和 RAM 的布局 | 很少改 |
| `<工程名>.sct` | Keil 的分散加载文件，作用同上 | 很少改 |
| `system_stm32f1xx.c` | `SystemInit()`：复位后最早被调用的 C 函数 | 一般不改 |
| `stm32f1xx_hal_conf.h` | HAL 模块开关，关掉不用的模块可以减小体积 | 按需改 |
| `Core/Src/main.c` 等 | 你的代码 | 写在 `/* USER CODE BEGIN */` 和 `/* USER CODE END */` 之间 |

两条规矩：时钟、引脚要改，回 CubeMX 改完重新生成，不要在启动文件里打补丁；重新生成时，标记之外的代码会被覆盖。启动文件名里是 `xb` 不是 `x8`，因为 ST 的头文件把 64 KB 的 x8 和 128 KB 的 xB 归在同一个器件宏 `STM32F103xB` 下，两者的容量差别写在链接脚本里。

### 5. 用 STM32CubeMX 生成工程

按下表从上往下点。最后一列是这一步最容易选错的地方。

| 步骤 | 操作 | 关键选项 |
| --- | --- | --- |
| 1 | New Project，搜索并选中芯片 | 选 `STM32F103C8Tx` |
| 2 | Pinout 视图配置引脚 | 例：PC13 设为 `GPIO_Output` |
| 3 | System Core → RCC | HSE 选 `Crystal/Ceramic Resonator`（BluePill 上有 8 MHz 晶振） |
| 4 | System Core → SYS | Debug 选 `Serial Wire` |
| 5 | Clock Configuration | HSE 8 MHz → PLL ×9 → SYSCLK 72 MHz；APB1 选 /2，让 PCLK1 不超过 36 MHz（第 02 章细讲） |
| 6 | Project Manager → Project | 名称、路径；Toolchain/IDE 选 `STM32CubeIDE`、`MDK-ARM`，新版本还能选 `Makefile` 或 `CMake` |
| 7 | Project Manager → Code Generator | 勾选「Copy only necessary library files」，并让每个外设生成单独的 .c/.h |
| 8 | GENERATE CODE | 生成后就能编译 |

> [!WARNING]
> SYS Debug 一定要选 **Serial Wire**。选 No Debug 时，CubeMX 在 `HAL_MspInit()` 里生成 `__HAL_AFIO_REMAP_SWJ_DISABLE()`，它把 AFIO_MAPR 寄存器的 SWJ_CFG 写成 100，JTAG 和 SWD 都关掉，PA13/PA14 变成普通 IO（[RM0008 Rev 21](#source-rm0008) 第 9.4.2 节）。程序一跑起来，调试器就连不上了。救回来的方法见第 8 节。

### 6. 编译、烧录、调试三个动作

同一个动作在四种环境里的入口如下。表按行读：先找你要做的动作，再找你用的环境。

| 动作 | Keil | CubeIDE | CLion + CMake | VS Code + CMake |
| --- | --- | --- | --- | --- |
| 编译 | F7 / Build | Ctrl+B | 选好 CMake Preset 后 Build | `Ctrl+Shift+B` 调用 CMake 任务 |
| 烧录 | F8 / Download | Run：先下载再运行 | OpenOCD Download & Run | Cortex-Debug 启动配置 |
| 调试 | Ctrl+F5 / Start Debug | F11 / Debug：下载后停在 `main` | OpenOCD + `arm-none-eabi-gdb` | Cortex-Debug + OpenOCD |
| 复位运行 | Reset 按钮 | Run 按钮 | Run 配置 | Run and Debug 配置 |

后面两列用到 CMake。CMake 是生成构建脚本的工具：你在 `CMakeLists.txt` 里写清楚有哪些源文件、用什么编译选项，它生成 Ninja 或 Makefile 去真正调用编译器。CMake Preset（`CMakePresets.json`）把一套配置存成有名字的预设，命令行、CLion、VS Code 读的是同一份。

#### CLion：以 CMake 为准，IDE 只负责调用

完整可编译的入口见 [`examples/spl-f1-blink/`](../examples/spl-f1-blink/)。这个例程用 SPL（Standard Peripheral Library，ST 早年的标准外设库，F1 版停在 V3.5.0，见 [STSW-STM32054](#source-stsw-stm32054)），命令行、CLion 和 VS Code 共用同一个 `CMakePresets.json`、同一份 GNU Arm 工具链文件、同一个链接脚本和同一份 OpenOCD 配置。这样能避免「IDE 里能编，CI 里编不过」。

1. 安装 Arm GNU Toolchain、CMake、Ninja、OpenOCD。先在命令行确认 `arm-none-eabi-gcc --version` 和 `openocd --version` 都有输出。
2. 设置依赖根目录（这个例程是冻结的 SPL V3.5.0，变量名 `SPL_ROOT`），从这个终端启动 CLion，再打开例程目录。
3. CLion 选 `BluePill SPL Debug` 这个 CMake Preset。构建日志里的编译器必须是 `arm-none-eabi-gcc`，产物必须是 `.elf`，不能是电脑本机的 `.exe`。
4. 新建 **OpenOCD Download & Run**：Target 选 CMake 目标，Executable 选 ELF，Board config 选仓库里的 `openocd/bluepill-stlink.cfg`，GDB 选 `arm-none-eabi-gdb`。
5. Run 依次做「编译、写入、校验、复位」；Debug 再多三步：OpenOCD 在 3333 端口等 GDB，GDB 加载同一个 ELF，停在 `main`。

#### VS Code：用任务编译，用 Cortex-Debug 调试

1. 安装 C/C++、CMake Tools、Cortex-Debug 三个扩展。Cortex-Debug 负责启动 OpenOCD 和 GDB。从设置过依赖环境变量的终端执行 `code .`。
2. `.vscode/tasks.json` 只调用 `cmake --preset debug` 和 `cmake --build --preset debug`，不在 JSON 里另抄一套编译器参数。
3. `.vscode/launch.json` 只写调试需要的几项：ELF 路径、OpenOCD 配置、`arm-none-eabi-gdb`、构建前要跑的任务。
4. 先用 `Ctrl+Shift+B` 单独验证构建，再运行 Cortex-Debug。构建和调试分开验，才能分清是编译器错误、链接脚本错误，还是探针连接错误。
5. 只有 IntelliSense（VS Code 的补全和红线提示）报红、CMake 构建却成功时，先执行 `CMake: Configure`，让语言服务读到编译数据库；不要靠手写 `includePath` 掩盖真实的构建参数。

下表是这两种环境最常见的失败。第二列是出错的那一层，先查它：

| 失败表现 | 出错的那一层 | 处理 |
| --- | --- | --- |
| CMake 报依赖根目录为空 | IDE 没有继承环境变量 | 从设置过变量的终端启动 IDE，或在 CMake Profile 里显式设置 |
| 生成了电脑本机的 `.exe` | 工具链文件没有生效 | 删掉这个 build 目录，用 preset 重新 configure，检查日志里识别出的编译器 |
| 编译通过，链接报中断函数重复定义 | 同一个中断有两个强定义 | 只保留一个；SPL 例程用自己的 `stm32f10x_it.c` 替换模板文件 |
| ELF 已生成，OpenOCD 连不上 | 已经不是构建的问题 | 查 SWD 接线、供电、目标配置文件和 ST-LINK 固件，不要再改 C 代码 |
| 下载成功，程序不进 `main` | 启动文件、链接脚本或复位路径 | 核对向量表、`Reset_Handler`、闪存和 RAM 的区域、BOOT0 |

官方说明见 [CLion 的嵌入式开发与 OpenOCD 文档](#source-clion-embedded) 和 [PlatformIO 的 VS Code 集成文档](#source-platformio-vscode)。

### 7. 复位之后发生了什么：向量表、启动文件、链接脚本

**结论：CPU 复位后从 `0x00000000` 读两个字：第 0 个字是栈顶，装进 MSP；第 1 个字才是复位入口 `Reset_Handler`。BOOT0=0 时，这个地址是闪存 `0x08000000` 的别名，不是另一块存储器。**

先解释几个词：

- **向量表（vector table）**：放在程序最前面的一张地址表。第 0 项是栈顶地址，第 1 项是复位入口，后面依次是各个异常和中断的入口地址。
- **栈和 MSP**：栈是一块 RAM，函数调用时在这里存局部变量和返回地址。MSP（Main Stack Pointer，主栈指针）是 CPU 里记住栈顶位置的寄存器。
- **别名（alias）**：同一块存储器在两个地址上都能读到。BOOT0=0 时，从 `0x00000000` 读到的字节，和从 `0x08000000` 读到的完全一样。
- **BOOT0、BOOT1**：两只启动选择脚。BOOT0 是第 44 脚；BOOT1 和 PB2 共用第 20 脚。BluePill 用两个跳线帽设置它们，平时都放在 0。

复位后谁先谁后，见下表（GCC 工程，以 STM32CubeIDE 生成的为例）。读法：从上往下是时间顺序，`main()` 是第 5 步，不是第 1 步。

| 顺序 | 谁在做 | 做了什么 |
| --- | --- | --- |
| 1 | 硬件 | 从 `0x00000000` 读第 0 个字装进 MSP，从 `0x00000004` 读第 1 个字，跳到 `Reset_Handler` |
| 2 | 启动文件调用 `SystemInit()` | Cube 的新版本里它基本只在需要时设向量表位置（`SCB->VTOR`）；SPL 的 `SystemInit()` 会直接把时钟配到 72 MHz |
| 3 | 启动文件 | 把 `.data` 的初值从闪存拷到 RAM，把 `.bss` 清零 |
| 4 | `__libc_init_array` | 跑 C++ 全局构造函数和 C 库的初始化 |
| 5 | `main()` | 你的代码。Cube 工程的时钟在这里由 `SystemClock_Config()` 配到 72 MHz，之前一直是复位后的 HSI 8 MHz |

`.data` 放有初值的全局变量（比如 `int a = 5;`），初值存在闪存里，上电后要拷进 RAM；`.bss` 放没写初值的全局变量，C 语言规定它们从 0 开始，所以要清零。Keil 工程把第 3、4 步交给 C 库的入口 `__main`：启动文件跳到 `__main`，它做完拷贝和清零再调用 `main()`。具体顺序以你工程里的 `startup_*.s` 为准，老版本的 Cube 启动文件先拷数据、后调 `SystemInit()`。

外设中断的入口不是 `0x08000000 + 4×IRQn`。向量表前面有 16 项属于栈顶和系统异常，所以入口地址是 `VTOR + 4×(IRQn + 16)`。例：USART1 的 IRQn 是 37，入口在 `0x08000000 + 4×53 = 0x080000D4`，和 [RM0008 Rev 21](#source-rm0008) 表 63 里 USART1 的 `0x0000_00D4` 对得上。复位后 VTOR 是 0，向量表就在 `0x00000000`（[PM0056 第 2.3.4 节](#source-pm0056-vector)），BOOT0=0 时那里正是闪存的别名。

链接脚本给闪存和 RAM 划地盘。F103C8 的闪存是 64 KB，从 `0x08000000` 起；SRAM 是 20 KB，从 `0x20000000` 起。栈从 RAM 顶往下长：

```ld
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
  RAM (xrw)   : ORIGIN = 0x20000000, LENGTH = 20K
}
_estack = ORIGIN(RAM) + LENGTH(RAM);
```

`_estack` = `0x20000000 + 20×1024` = `0x20000000 + 0x5000` = `0x20005000`，这就是 GCC 工程向量表第 0 个字的值。第 1 个字是 `Reset_Handler` 的地址再加 1：PM0056 规定向量的最低位必须是 1，表示这是 Thumb 指令，所以你在内存窗口看到的是个奇数。链接脚本里放向量表的 `.isr_vector` 段要用 `KEEP` 包住，否则链接器回收没被引用的段时（`--gc-sections`），会把 C 代码从没直接调用过的向量表扔掉，上电就跑飞。

启动方式由两只 BOOT 脚决定，见 [RM0008 Rev 21 第 3.4 节表 9](#source-rm0008-boot)：

| BOOT1（第 20 脚） | BOOT0（第 44 脚） | 启动区 | 从 `0x00000000` 读到的是 |
| --- | --- | --- | --- |
| 任意 | 0 | 主闪存 | `0x08000000` 起的闪存（平时都用这一行） |
| 0 | 1 | 系统存储器 | `0x1FFFF000` 起的 ST 出厂引导程序，它等着从 USART1 接收新程序 |
| 1 | 1 | 内置 SRAM | 不做别名，SRAM 只在 `0x20000000` 上；程序要自己把 VTOR 指到 SRAM 里的向量表 |

表这样用：先看 BOOT0，它是 0 就从闪存跑；它是 1 时再看 BOOT1。BOOT 脚的电平在复位后第 4 个 SYSCLK 上升沿被锁存，之后再拔跳线不影响这一次启动。

### 8. SWD 连接、救砖和 SWO 打印

**结论：SWD 只要两根信号线：PA13 是数据，PA14 是时钟。程序可以把这两只脚收回去当普通 IO，那样调试器就连不上；救回来的办法是让你的程序没有机会运行。**

- **SWD（Serial Wire Debug，串行线调试）**：Arm 定义的两线调试接口。SWDIO 是双向数据线，SWCLK 是时钟线。F103 上它们是 PA13 和 PA14（[RM0008 Rev 21](#source-rm0008) 第 31.4.2 节表 219）。
- 复位后，PA13、PA14、PA15、PB3、PB4 五只脚都归调试口。程序可以写 AFIO_MAPR 的 SWJ_CFG，把其中几只或全部还给 GPIO（表 220）。只用 SWD 时写 010，PA15、PB3、PB4 让出来，PA13、PA14 留给调试器。
- 芯片在 SWDIO 上内置上拉、在 SWCLK 上内置下拉（第 31.4.3 节），所以这两根线不用外接电阻。

调试口已经被程序关掉、连不上了，有两条路：

1. **带复位连接（connect under reset）**：接上 NRST，在 CubeProgrammer 里把连接模式选成 Under reset，再点 Connect。调试器先按住复位，在复位期间切到 SWD、在复位向量上设断点，然后松开复位，内核停在第一条指令之前（[RM0008 Rev 21](#source-rm0008) 第 31.4.4 节）。SWJ_CFG 本身会被系统复位清回 000，你那段关调试口的代码还没机会执行。连上后整片擦除，再下载改好的程序。
2. **BOOT0 拉高**：BOOT0 跳线拉到 1、BOOT1 保持 0，按一次复位。CPU 从系统存储器取指，闪存里的程序不运行，调试口保持复位时的状态。连上后整片擦除，再把 BOOT0 放回 0。

调试时常用的几个手段：

| 手段 | 怎么做 |
| --- | --- |
| 断点 | 在可疑行打断点，停下后看变量和寄存器 |
| 变量观察 | 把全局变量和局部变量加进 Watch 窗口 |
| 寄存器查看 | 打开外设寄存器窗口（GPIO、RCC 等），对照手册看每一位 |
| SWO 打印 | 不占串口的 `printf`，见下文 |
| 反汇编 | 看 C 代码对应的汇编，理解编译器优化了什么 |

SWO（Serial Wire Output，串行线输出）是一根单向的跟踪输出线，在 F103 上是第 39 脚 PB3。它复位后的默认功能是 JTDO，调试器打开异步跟踪后才输出 TRACESWO（表 219）。SWO 不是 SWD 两根线里的一根：要用它，探针要多接一根线到 PB3。不少便宜的 ST-LINK V2 克隆版根本没有 SWO 引脚（经验）。ITM（Instrumentation Trace Macrocell，仪器化跟踪单元）是内核里的一个模块，程序把字符写进它的端口，字符就从 SWO 发出去。打开 PB3 的跟踪输出由调试器负责（写 DBGMCU_CR 的 TRACE_IOEN，第 31.16.3 节）；你只要在 IDE 的调试配置里打开 SWV，内核时钟填对（例程设定 72 MHz）。

```c
#include "main.h"   /* 带进 CMSIS 的 core_cm3.h，里面有 ITM_SendChar() */

/* GCC 的 printf 最后调用 _write()。这里把每个字符交给 ITM，从 SWO 脚发出 */
int _write(int fd, char *ptr, int len)
{
    (void)fd;
    for (int i = 0; i < len; i++)
    {
        ITM_SendChar((uint8_t)ptr[i]);
    }
    return len;
}
```

调试器没有打开 ITM 时，`ITM_SendChar()` 直接返回，不会卡住程序。Keil 的 C 库不走 `_write()`，要改写 `fputc()`。

### 9. 常见报错和下载算法

下表把常见报错按「先查什么」排好。第一次连不上时，从第一行往下查，不要先改代码。

| 报错 | 常见原因 | 先查 |
| --- | --- | --- |
| 找不到 ST-LINK | USB 线或驱动 | 换 USB 口；在设备管理器里看 ST-Link 是否出现；重装驱动 |
| `No STM32 target found`、`No target connected` | SWD 线没接好、目标没供电，或 PA13/PA14 被程序改作他用 | 先查四根线和 3.3 V，再试带复位连接 |
| `Cannot access target` | 目标掉电，或一直处在复位 | 查供电和 NRST |
| `Flash Download failed`（Keil） | 下载算法没选或选错；芯片处于读保护 | 在 Flash Download 设置里加对算法；读保护按第 10 节解除 |
| `Core is locked up` | 内核锁死：在 HardFault 处理过程中又出错。闪存是空的或向量表错了时常见 | 带复位连接后擦除重下；查指针和栈 |

锁死（lockup）的定义见 [PM0056](#source-pm0056) 第 2.4.4 节：处理 NMI 或 HardFault 时又发生 HardFault，处理器就停止执行指令。

Keil 下载闪存要选对下载算法（Flash Algorithm），按芯片容量档选：

| 芯片 | Keil 下载算法 | 容量 |
| --- | --- | --- |
| F103C8 | STM32F10x Med-density Flash | 64 KB |
| F103RC | STM32F10x High-density Flash | 256 KB |
| F401 | STM32F4xx Flash（按容量选） | 视型号 |

F1 按闪存容量分档：64–128 KB 是中容量（medium density），256–512 KB 是大容量（high density），见 [RM0008 Rev 21](#source-rm0008) 第 2.3 节的术语表。

### 10. 读保护和解锁

**结论：F103 的读保护只有一个「无保护」值：`0xA5`。其他任何值都算保护，包括擦除后的 `0xFF`。把它改回 `0xA5` 会先整片擦除主闪存。**

- **读保护（readout protection，RDP）**：开启后，调试器读不出闪存里的程序，防止程序被拷走。
- **选项字节（option bytes）**：闪存里一小块独立的配置区，F1 的在 `0x1FFFF800`。RDP 是其中的一个字节。

规则出自 [PM0075](#source-pm0075-rdp) 第 2.4.1 节表 6：RDP 等于 `0xA5`（手册印成 `0x00A5`）时不保护，其他值都保护。`0xAA` 是 F4 等系列的「无保护」编码（[RM0090](#source-rm0090) 第 3.7.3 节），搬到 F103 上，它只是一个「不等于 0xA5 的值」，写进去照样保护。

用 STM32CubeProgrammer 解除：

1. 选 ST-LINK 连接，点 Connect。连不上就用第 8 节的带复位连接。
2. 左侧 `Option bytes` → Read Out Protection 改成无保护，写入的字节是 `0xA5`。有的界面只显示 Level 0，写进去的仍是这个字节。
3. 点 `Apply`。**解除读保护会整片擦除主闪存**，程序要重新下载。
4. 断电再上电一次。PM0075 要求上电复位，新的 RDP 才生效；经系统存储器的引导程序解除时，系统复位就够。
5. 重新下载程序。

命令行等价（OpenOCD）：

```bash
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "init; reset halt; stm32f1x unlock 0; reset; shutdown"
```

命令里的 `0` 是 OpenOCD 给闪存分的 bank 编号，不是 RDP 的值。跑完同样断电再上电一次。

口诀：**第 0 项是栈，第 1 项才是复位；先认出芯片，再查代码。**

## 硬件与接线

SWD 只需要四根线（3.3 V、GND、SWDIO、SWCLK），NRST 可选，接上后能用带复位连接。下表按 ST-LINK V2 克隆版的 10 针口写；原装 ST-LINK/V2 是 20 针口，按它自己的说明书对针位。

| ST-LINK 引脚 | BluePill 引脚 | 信号 | 说明 |
| --- | --- | --- | --- |
| 3.3V | 3.3 V | 电源 | 可选，板子也可以由 USB 供电 |
| GND | GND | 地 | **必须接**，共地 |
| SWDIO | PA13（第 34 脚） | 数据 | 双向数据线 |
| SWCLK | PA14（第 37 脚） | 时钟 | 调试时钟 |
| RST | NRST（第 7 脚） | 复位 | 建议接，带复位连接要用它 |
| 5V | — | — | 一般不用 |

```text
ST-LINK V2（克隆版 10 针口）            BluePill
  3.3V   ──────────────────────────  3.3 V
  SWDIO  ──────────────────────────  SWDIO = PA13，第 34 脚
  SWCLK  ──────────────────────────  SWCLK = PA14，第 37 脚
  GND    ──────────────────────────  GND
  RST    ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  NRST，第 7 脚（可选）

BluePill 跳线：BOOT0 = 0，BOOT1 = 0 → 从闪存运行（平时就放这里）
```

BluePill 短边那排 4 针就是调试口，各家丝印写法不同，按 3.3 V、SWDIO、SWCLK、GND 的含义对上即可。接线前先断电；数芯片引脚时，SWCLK 在第 37 脚，别数成旁边的第 35、36 脚，那两只是电源脚。

和本章有关的芯片引脚如下，脚号来自 [DS5319 Rev 20 表 5](#source-ds5319-swd)：

| 引脚 | LQFP48 脚号 | 本章的用途 |
| --- | --- | --- |
| PA13 | 34 | SWDIO |
| VSS_2、VDD_2 | 35、36 | 电源脚，接地和接 3.3 V |
| PA14 | 37 | SWCLK |
| NRST | 7 | 复位 |
| BOOT0 | 44 | 启动选择 |
| PB2 / BOOT1 | 20 | 启动选择 |
| PB3 | 39 | SWO（可选） |

驱动和固件：

| 项目 | 操作 |
| --- | --- |
| 装驱动 | Windows 装 ST-LINK USB 驱动，设备管理器里出现 ST-Link 设备 |
| 升级固件 | 工具提示固件过旧时，用 ST-LINK Upgrade 或 CubeProgrammer 里的固件升级 |
| 检查连接 | 在 STM32CubeProgrammer 里 Connect，读到 Device ID `0x410` 就通了 |
| Linux 权限 | 加 udev 规则，免得每次都要 sudo |

`0x410` 是中容量 F1 的器件号（DBGMCU_IDCODE 的 DEV_ID，[RM0008 Rev 21](#source-rm0008) 第 31.6.1 节）。读到别的值，板上的芯片可能不是 ST 原装（经验）。

## 代码实现

下面是 CubeMX 工程里一个完整的 `main.c`：时钟配到 72 MHz，PC13 的板载灯以 1 Hz 闪烁。用到的 `main.h`、`stm32f1xx_hal_msp.c` 和 HAL 库由 CubeMX 生成。同样的程序见 [`examples/gpio-blink/`](../examples/gpio-blink/)。

```c
/* main.c：CubeMX 工程里的点灯程序（STM32F103C8T6，HSE 8 MHz） */
#include "main.h"

#define LED_PORT       GPIOC
#define LED_PIN        GPIO_PIN_13    /* 板载灯，低电平亮 */
#define BLINK_HALF_MS  500U           /* 亮 500 ms、灭 500 ms，周期约 1 s（例程设定） */

void SystemClock_Config(void);
static void MX_GPIO_Init(void);

int main(void)
{
    HAL_Init();               /* Flash 预取、NVIC 分组、1 ms 的 SysTick，最后调用 HAL_MspInit() */
    SystemClock_Config();     /* 时钟从复位后的 HSI 8 MHz 换到 PLL 72 MHz */
    MX_GPIO_Init();           /* PC13 推挽输出 */

    while (1)
    {
        HAL_GPIO_TogglePin(LED_PORT, LED_PIN);
        HAL_Delay(BLINK_HALF_MS);
    }
}

void SystemClock_Config(void)
{
    RCC_OscInitTypeDef osc = {0};
    RCC_ClkInitTypeDef clk = {0};

    osc.OscillatorType = RCC_OSCILLATORTYPE_HSE;
    osc.HSEState       = RCC_HSE_ON;
    osc.HSEPredivValue = RCC_HSE_PREDIV_DIV1;
    osc.HSIState       = RCC_HSI_ON;
    osc.PLL.PLLState   = RCC_PLL_ON;
    osc.PLL.PLLSource  = RCC_PLLSOURCE_HSE;
    osc.PLL.PLLMUL     = RCC_PLL_MUL9;            /* 8 MHz × 9 = 72 MHz */
    if (HAL_RCC_OscConfig(&osc) != HAL_OK)
    {
        Error_Handler();
    }

    clk.ClockType      = RCC_CLOCKTYPE_HCLK | RCC_CLOCKTYPE_SYSCLK
                       | RCC_CLOCKTYPE_PCLK1 | RCC_CLOCKTYPE_PCLK2;
    clk.SYSCLKSource   = RCC_SYSCLKSOURCE_PLLCLK;
    clk.AHBCLKDivider  = RCC_SYSCLK_DIV1;         /* HCLK 72 MHz */
    clk.APB1CLKDivider = RCC_HCLK_DIV2;           /* PCLK1 36 MHz，不能超过 36 MHz */
    clk.APB2CLKDivider = RCC_HCLK_DIV1;           /* PCLK2 72 MHz */
    if (HAL_RCC_ClockConfig(&clk, FLASH_LATENCY_2) != HAL_OK)   /* 72 MHz 要 2 个等待周期 */
    {
        Error_Handler();
    }
}

static void MX_GPIO_Init(void)
{
    GPIO_InitTypeDef io = {0};

    __HAL_RCC_GPIOC_CLK_ENABLE();                 /* 先开端口时钟，配置才写得进去 */
    HAL_GPIO_WritePin(LED_PORT, LED_PIN, GPIO_PIN_SET);   /* 先写高，上电时灯是灭的 */

    io.Pin   = LED_PIN;
    io.Mode  = GPIO_MODE_OUTPUT_PP;
    io.Pull  = GPIO_NOPULL;
    io.Speed = GPIO_SPEED_FREQ_LOW;
    HAL_GPIO_Init(LED_PORT, &io);
}

void Error_Handler(void)
{
    __disable_irq();          /* 停在这里，调试器一暂停就能看到卡在哪 */
    while (1)
    {
    }
}
```

逐段看：

- `HAL_Init()` 不复位外设。它打开 Flash 预取，设好 NVIC 优先级分组，用复位后的 HSI 时钟启动 1 ms 一次的 SysTick，最后调用 `HAL_MspInit()`。
- `HAL_MspInit()` 在 CubeMX 生成的 `stm32f1xx_hal_msp.c` 里，SYS Debug 的选择就落在这里：选 Serial Wire 生成 `__HAL_AFIO_REMAP_SWJ_NOJTAG()`，只关 JTAG、留 SWD；选 No Debug 生成 `__HAL_AFIO_REMAP_SWJ_DISABLE()`，两样都关。
- `SystemClock_Config()` 才把时钟换到 72 MHz。在它之前，程序跑在 HSI 8 MHz 上。72 MHz 要 2 个 Flash 等待周期，第 02 章细讲。
- `HAL_Delay(500)` 靠 SysTick 计数。翻转一次等 500 ms，亮、灭各一次合起来就是 1 s。

同样关掉 JTAG、保留 SWD，寄存器写法如下：

```c
__HAL_RCC_AFIO_CLK_ENABLE();                          /* 先给 AFIO 开时钟 */
AFIO->MAPR = (AFIO->MAPR & ~AFIO_MAPR_SWJ_CFG)
           | AFIO_MAPR_SWJ_CFG_JTAGDISABLE;           /* SWJ_CFG = 010：关 JTAG，留 SWD */
```

SWJ_CFG 三位只能写，读回来的值不确定（[RM0008 Rev 21](#source-rm0008) 第 9.4.2 节）。以后用寄存器改 MAPR 的其他重映射位时，不要直接 `|=`，要把 SWJ_CFG 一起写成你要的值，否则读回来的随机值可能顺手把 SWD 关掉。

```bash
# 任何能产出 ELF 的工程（Makefile、CMake）：用 OpenOCD 写入、校验、复位

  -c "program build/firmware.elf verify reset exit"
```

## 动手实验

1. **实验一：环境打通，PC13 以 1 Hz 闪烁。** 用 CubeMX 生成工程，填入上面的代码，编译并下载到 BluePill。
   - 预期现象：板载灯亮约 0.5 s、灭约 0.5 s，循环不停。
   - 怎么确认：用手机秒表数 10 次闪烁，应在 10 s 左右；有逻辑分析仪就量 PC13 的周期，应接近 1 s。
   - 没成功先查：CubeProgrammer 能否读到 Device ID；SYS Debug 是不是 Serial Wire；板载灯是低电平亮，写 1 是灭。
2. **实验二：读出向量表的前两个字。** 用调试模式下载，停在 `main` 后打开 Memory 窗口，地址填 `0x08000000`。
   - 预期现象：第一个字是 `0x20005000`；第二个字是个奇数，形如 `0x0800xxxx`。
   - 怎么确认：`0x20005000` = `0x20000000 + 20 KB`，就是链接脚本里的 `_estack`；第二个字减 1，应等于符号表里 `Reset_Handler` 的地址（`arm-none-eabi-nm` 加你的 ELF 文件名，再找 `Reset_Handler`）。再把地址改成 `0x00000000`，内容和 `0x08000000` 一样，这就是别名。
   - 没成功先查：链接脚本是不是 C8 的（RAM 写错，栈顶就不是这个值）；Keil 工程的栈由分散加载文件安排，第一个字不一定是 `0x20005000`。
3. **实验三：复现「连不上」，再救回来。** 在 CubeMX 里把 SYS Debug 改成 No Debug，生成、下载一次，再试着连接。
   - 预期现象：下载那一次能成功；之后普通连接失败，报找不到目标。
   - 怎么确认：用带复位连接（Under reset），或把 BOOT0 拉到 1 再按复位，就能重新连上；整片擦除后改回 Serial Wire 再下载，一切恢复。
   - 没成功先查：带复位连接要接 NRST；BOOT0 拉高后有没有按复位键；救回来以后记得把 BOOT0 放回 0。

## 自测

1. 编译全部通过，最后报 `region 'FLASH' overflowed`。问题出在四步里的哪一步？该看哪个文件？
2. USART1 的 IRQn 是 37。向量表放在 `0x08000000` 时，USART1 的中断入口在哪个地址？
3. BluePill 的 BOOT1 跳线在 0。你把 BOOT0 拉到 1，再按复位。CPU 在跑什么？闪存里的程序还在吗？
4. 用 CubeProgrammer 把选项字节整块擦除后，RDP 读出来是 `0xFF`。芯片现在有没有读保护？
5. 链接脚本里 RAM 的 `LENGTH = 20K`，起点 `0x20000000`。GCC 工程向量表的第 0 个字应该是多少？

参考答案：

1. 链接。编译只负责把单个 `.c` 变成 `.o`，闪存放不下是链接器按链接脚本分配地址时才发现的。看 `.ld` 里 FLASH 的 `LENGTH` 和链接生成的 map 文件，删掉不用的代码，或打开优化。
2. `4×(37 + 16) = 4×53 = 212 = 0xD4`，`0x08000000 + 0xD4 = 0x080000D4`。RM0008 Rev 21 表 63 里 USART1 的位置正是 `0x0000_00D4`。
3. CPU 在跑系统存储器里的 ST 出厂引导程序（`0x1FFFF000` 起），它等着从 USART1 接收新程序。闪存里的程序还在，只是这次没有被取指。BOOT0 放回 0 再复位就回来了。
4. 有。PM0075 规定只有 RDP 等于 `0xA5` 才不保护，`0xFF` 也算保护，所以擦除选项字节不会触发整片擦除。要解除，得再写入 `0xA5`，然后断电重新上电。
5. `0x20000000 + 20×1024 = 0x20000000 + 0x5000 = 0x20005000`，也就是 `_estack`。

## 原理与适用范围

> [!NOTE]
> 从这一节到「常见坑与出处」是深入部分，把前面的结论落到具体订货号、手册章节和能复算的数字上。第一次读可以先跳过，做完动手实验再回来对照。

这一章的调试和启动结论钉在订货号 STM32F103C8T6、封装 LQFP48 上，也就是 BluePill 上那颗。

**调试脚。**复位后，调试口在第 34 脚 PA13 = SWDIO 和第 37 脚 PA14 = SWCLK。两者中间隔着第 35 脚 VSS_2 和第 36 脚 VDD_2，它们是电源脚，接地和接电源，不能悬空，也不能拿来接探针。把第 35 脚当成 SWCLK，是关键插图上画的失败路径。第 7 脚 NRST 建议接，但它不是 SWD 的第三根信号线。第 44 脚是 BOOT0。脚位见 [DS5319 Rev 20 表 5](#source-ds5319-swd)。

**调试口会被程序关掉。**SYS Debug 要选 Serial Wire。关掉之后，第 34 脚和第 37 脚变成普通 GPIO，下一次 SWD 连接就失败。

**向量表的两个字。**BOOT0=0 时，CPU 从 `0x00000000` 读到的是闪存 `0x08000000` 的别名。第 0 个字是 MSP 初值；第 1 个字在 `0x00000004`，是 `Reset_Handler`。外设中断入口不是 `0x08000000 + 4×IRQn`，而是 `VTOR + 4×(IRQn + 16)`。见 [PM0056 的向量表](#source-pm0056-vector)。

**两只 BOOT 脚。**BOOT1=0 且 BOOT0=1 时，CPU 仍从 `0x00000000` 取指，取到的是系统存储器 `0x1FFFF000`。闪存里的程序还在，只是没有被取指。要以内置 SRAM（`0x20000000`）启动，BOOT1 和 BOOT0 都得是 1。只说「BOOT0=1 就是 SRAM 启动」的说法作废。见 [RM0008 Rev 21 表 9](#source-rm0008-boot)。

**读保护的值。**无保护是 RDP = `0xA5`，不是 `0xAA`。手册把这个键印成 `0x00A5`，低字节仍是 `0xA5`。把它写回去，会先整片擦除主闪存。`0xAA` 是别的系列的编码，在这颗料上作废：写进去照样算保护。选项字节界面若只显示 Level 0，写进去的字节仍是 `0xA5`。见 [PM0075](#source-pm0075-rdp)。

**容量。**这颗 C8 是 64 KB 闪存、20 KB SRAM；xB 的 128 KB 在这颗料上作废。链接脚本里的 `LENGTH = 64K` 和 `LENGTH = 20K` 跟这两个数一致。

**跟踪脚。**跟踪输出在第 39 脚 PB3，它的默认功能是 JTDO，重映射一栏里才有 TRACESWO。它不是 PA13，也不是 PA14。SWO 打印放在核心原理里讲，不进主图的正常路径；第 17 章的 `debug-swo.svg` 不在这里重画。

**换芯片时。**换封装，第 7、34、35、36、37、44 脚都要回表 5 重查；换系列，RDP 的编码和 BOOT 脚的规则都以那颗芯片自己的手册为准。

## 时序与状态

下表从上往下是一次复位的时间顺序，标「失败」的两行是配置或跳线错了时会走到的岔路。BOOT 脚的锁存时刻和三种启动区来自 [RM0008 Rev 21 第 3.4 节表 9](#source-rm0008-boot)，两个字来自 [PM0056 的向量表](#source-pm0056-vector)。

| 阶段 | BOOT / Debug | 读到的地址 | 状态 |
| --- | --- | --- | --- |
| 锁存 BOOT | 复位后第 4 个 SYSCLK 上升沿 | — | 之后再动跳线，不影响这一次启动；从待机模式唤醒时会重新采样 |
| 复位，BOOT0=0 | 第 44 脚 BOOT0 = 0 | `0x00000000` 别名 `0x08000000` | 物理存储器是 64 KB 闪存 |
| 第 0 字 | 向量表第 0 项 | `0x00000000` | MSP 初值，GCC 工程里是 `0x20005000` |
| 第 1 字 | 向量表第 1 项 | `0x00000004` | `Reset_Handler`（最低位为 1），然后才到 `main` |
| 失败：Debug 关掉 | 第 34 脚和第 37 脚变成 GPIO | PA13 / PA14 不再是 SWD | SWD 连接失败 |
| 失败：系统存储器 | BOOT1=0 且 BOOT0=1 | `0x1FFFF000` | 不是 SRAM。闪存里的程序还在，只是没有被取指 |
| SRAM | BOOT1=1 且 BOOT0=1 | `0x20000000` | 两只 BOOT 都为 1 才以 SRAM 启动 |
| IRQ | 外设中断 | `VTOR + 4×(IRQn + 16)` | 不是 `0x08000000 + 4×IRQn` |
| 容量 | C8 | 64 KB 闪存，20 KB SRAM | 128 KB 在这颗料上作废 |

这张表不写工具链菜单。第 35 脚是 VSS_2，第 36 脚是 VDD_2，第 7 脚是 NRST。

## 常见坑与出处

| 现象 | 原因 | 处理 | 出处 | 出处能证明的部分 |
| --- | --- | --- | --- | --- |
| 烧录一次后再也连不上 | PA13/PA14 被配成了普通 GPIO | SYS Debug 留在 Serial Wire，SWD 留在第 34 脚和第 37 脚 | [DS5319](#source-ds5319-swd) | LQFP48 第 34 脚是 PA13/SWDIO，第 37 脚是 PA14/SWCLK，第 35 脚是 VSS_2 |
| 调试口已被程序关掉，想救回来 | 程序一启动就写了 SWJ_CFG | 接上 NRST 用带复位连接；或 BOOT0 拉高后复位，连上后整片擦除 | [RM0008 第 31.4.4 节](#source-rm0008) | 系统复位期间五只 SWJ 脚都归调试口，调试器能在复位向量上停住内核 |
| 探针接在 PA13 旁边那只脚上，没有时钟 | 第 35 脚被当成了 SWCLK | 探针不要落在第 35、36 脚（VSS_2、VDD_2 仍接地和电源），SWCLK 改接第 37 脚 | [DS5319](#source-ds5319-swd) | 第 35 脚是 VSS_2，第 36 脚是 VDD_2，第 37 脚才是 SWCLK。这两只电源脚不能悬空 |
| BOOT0 拉高后，跑的既不是闪存里的程序，也不是 SRAM | BOOT1 仍是 0 | BOOT1=0 时这是系统存储器。要以 SRAM 启动，两只 BOOT 都拉高 | [RM0008](#source-rm0008-boot) | BOOT1=0 且 BOOT0=1 时别名到 `0x1FFFF000`。SRAM 启动还要 BOOT1=1 |
| 按 `AA` 解除读保护，芯片仍保护着，或擦除结果对不上 | 无保护键不是 `0xAA` | 无保护键写成 `0xA5`。解除时主闪存会被整片擦掉 | [PM0075](#source-pm0075-rdp) | RDP 为 `0xA5` 才允许读出。编程回 `0xA5` 会先整片擦除。`0xAA` 在这颗料上作废 |
| 擦掉选项字节，以为解了锁，读出来仍保护 | 擦除后 RDP 是 `0xFF`，也算保护 | 擦除后再写入 `0xA5`，然后断电重新上电 | [PM0075](#source-pm0075-rdp) | 擦除态 `0xFF` 是保护值，不会触发整片擦除；解除后要上电复位才生效 |
| 向量表第 0 字被当成复位入口 | 第 0 字是栈 | 第 0 字是 MSP，第 1 字才是 `Reset_Handler` | [PM0056](#source-pm0056-vector) | 向量表第 0 项是栈初值，第 1 项是复位。IRQ 入口要先加上 16 个系统异常 |
