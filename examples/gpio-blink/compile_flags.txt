# clangd / 静态检查用的解析参数，等价于 CMakeLists.txt 里 gpio-blink.elf 目标的
# include 集合与宏定义。不参与构建：固件构建仍走 CMake + dependencies.lock.json。
#
# README 要求把 STM32CubeF1 v1.8.6 取到 <仓库根>/.temp/STM32CubeF1；没取时这些
# -I 指向不存在的目录，clangd 只会说「找不到头文件」——那是环境没准备，不是代码问题。
#
# 两点说明：
# 1. 不列 tests/。那里的 stm32f1xx_hal.h 是宿主测试用的桩，只有 blink-tests 目标
#    才把 tests 放进 include 路径；列进来会让 `#include "stm32f1xx_hal.h"` 命中桩
#    而不是真 HAL，GPIO_TypeDef 被定义两次。
# 2. 这里不定义 USE_HAL_DRIVER。CMakeLists 在真实构建里定义它，作用是让
#    CMSIS 的 stm32f1xx.h 顺手把头文件 stm32f1xx_hal.h 引进来。本工程的源文件
#    都是自己显式 #include "stm32f1xx_hal.h"，不依赖这个副作用，因此静态检查
#    不需要它。
#
#    更要紧的是：带上这个宏会让 include/stm32f1xx_hal_conf.h 走进循环包含
#    （conf → hal_rcc → hal_def → stm32f1xx → hal → conf），该头是 ST 的
#    「配置片段」、不是编译单元，于是 arm-none-eabi-gcc、clang 单独编译它都会报
#        error: unknown type name 'HAL_StatusTypeDef'
#    而 clangd 会报 main file cannot be included recursively。去掉这个宏后，
#    两种编译器单独编译该头均 0 error，main.c 与 stm32f1xx_it.c 也仍然干净。
# 同一组路径写两种基准：相对本目录（clangd 按 compile_flags.txt 所在目录解析）
# 和相对仓库根（有些分析器按工作目录解析）。不存在的 -I 目录编译器会直接跳过，
# 所以多写一份不影响任何真实构建，只是让两种解析基准都能命中。
-Iinclude
-Iexamples/gpio-blink/include
-I../../.temp/STM32CubeF1/Drivers/CMSIS/Include
-I.temp/STM32CubeF1/Drivers/CMSIS/Include
-I../../.temp/STM32CubeF1/Drivers/CMSIS/Device/ST/STM32F1xx/Include
-I.temp/STM32CubeF1/Drivers/CMSIS/Device/ST/STM32F1xx/Include
-I../../.temp/STM32CubeF1/Drivers/STM32F1xx_HAL_Driver/Inc
-I.temp/STM32CubeF1/Drivers/STM32F1xx_HAL_Driver/Inc
-DSTM32F103xB
-std=c11
